# Node 1.6: Reflection and properties (plan, ahead-work)

**Status: draft: rewrite when the node starts.** Written 2026-11-20 from `CAPABILITY_ROADMAP.md` Part 5 (node 1.6) and `ROADMAP.md` (row 1.6: `not started`). No code, no downloads and no repo exists yet. Everything below is a plan: the program names, flags, fixture names and test names in section 1 are the ones the briefs in section 7 create, and they are not real until those briefs merge. Numbers marked "plan value" are guesses to be replaced by the brief that first measures them.

- Build (roadmap): type introspection so structs become editable, serializable and scriptable automatically.
- Done when (roadmap): any annotated struct appears in an auto-generated inspector, saves/loads, and is scriptable with no hand-written glue.
- Needs (roadmap): 0.5. See section 3: the Done-when needs only a small versioned text format, which this node writes for itself.

**Product intent this plan respects** (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared core data model live, with no export or import. The core API must be language-neutral (C ABI and serializable data), because upper layers may use other languages. Reflection is the mechanism by which a mode sees core data it did not define: it is the **bridge between the core model and every mode**. So this node owns **no scene, mesh, material or sim type**. It owns the machinery (type descriptors, values, paths, a text format, an inspector description, change events, a C ABI) and a few sample types used only to test it. Three consequences are built in from the first commit and are checked: (1) a type's descriptor has a version and a hash, so a mode can see that the core's layout changed (a cross-shard change in the harness's terms); (2) all access to a field, from a script, an inspector or a C caller, goes through one function that validates and announces the change, so a live edit is seen by every mode; (3) nothing in the generic modules may name a sample type (check 1.6.7 proves it).

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test reflect`; a program goes through `broadsword run reflect -- cargo run --offline --release --example reflect_demo -- <flags>`. Programs run with the project folder (`projects/reflect`) as the working folder, so fixture paths below are relative to it.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword run` prints its own job lines first and `--- summary ---` and `run: ok (...)` or `run: FAILED (exit N)` last; "PRINTS" means the program's own lines between them. `broadsword test` has no name filter: it runs the whole suite, prints one `test <name> ... ok` line per test, then `test: ok — N passed, 0 failed`. A check that needs one test looks for that test's own line.
- Program contract (created by briefs R9 and R10): `reflect_demo` is `examples/reflect_demo.rs` in the `reflect` crate. Flags: `--expect-schema <Type> <file>`; `--expect-inspector <Type> <file>`; `--roundtrip <Type> <file>`; `--load <Type> <file>`; `--script <file> <expected-file>`; `--glue-proof`; `--watch`; `--inject-fault`. Exit code 0 means PASS, 1 means a compared value broke its rule (FAIL), 2 means a usage error (never a silent skip). Every flag a check uses is required; the program has no defaults. The exact output line formats are written into `docs/NODE16.md` by R9 and R10, so a check cannot pass on a reworded message.
- Types used by the checks: `Vehicle` (a car-like sample: name, mass in kg with a range, a position `[f64; 3]`, a list of `Wheel` structs with radius, an optional note, a drive-mode enum), `VehicleWide` (the same plus one extra field, `armor_rating`), all declared through the `reflect!` macro in `src/sample.rs` and nowhere else.
- Blocks marked **[human]** need Lazlo. Blocks marked **[quiet board]** are timing and run only when no other job is running (confirm by reading the job list under `state/jobs/`).

### 1.6.2 A struct's descriptor is generated from its declaration and matches a hand-written file

```check 1.6.2
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --expect-schema Vehicle fixtures/vehicle.schema.txt > scratch/reflect16-2.txt 2>&1
PASS: the file contains `run: ok` and the program line `schema Vehicle version=1 fields=6 hash=<16 hex digits> expected=fixtures/vehicle.schema.txt result=PASS`.
PRINTS: the line above, one line. The fixture is written by hand from the `reflect!` declaration, before the program is run; the program compares its generated text to the file byte for byte, and the hash is FNV-1a 64 over that text.
```

Reason: the first half of "no hand-written glue" is that the descriptor comes from the declaration. A hand-worked expected file means the match has an answer no program produced. The hash is the version signal for the shared core (section 2 of the product intent above).

### 1.6.3 The inspector is generated from the descriptor alone

```check 1.6.3
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --expect-inspector Vehicle fixtures/vehicle.inspector.txt > scratch/reflect16-3.txt 2>&1
PASS: the file contains `run: ok` and the program line `inspect Vehicle widgets=<n> expected=fixtures/vehicle.inspector.txt result=PASS`, with n equal to the number of `widget` lines in the fixture (plan value 9: the six top-level fields plus the three fields of one `Wheel` row).
PRINTS: the line above, one line. The inspector is a plain text description (one `widget path=... kind=... label=... [unit=...] [min=...] [max=...] [readonly]` line per editable field), not a window: node 1.5 (editor shell) draws it later.
```

Reason: no UI exists until 1.5, and the Done-when's "auto-generated inspector" is about generating what a UI needs (what widget, what label, what range) from the type. A text widget list is checkable now and is the same data a window will consume. Hidden fields must be absent and read-only fields marked, both covered by the fixture.

### 1.6.4 Save and load round trip is byte-identical

```check 1.6.4
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --roundtrip Vehicle fixtures/vehicle.v2.txt > scratch/reflect16-4.txt 2>&1
PASS: the file contains `run: ok` and the program line `roundtrip Vehicle bytes=<n> golden=true text_identical=true value_equal=true result=PASS`, where `golden=true` means the saved text equals the hand-written `fixtures/vehicle.v2.txt` byte for byte, `text_identical=true` means save, load, save gives the same bytes, and `value_equal=true` means the loaded value equals the original field by field.
PRINTS: the line above, one line.
```

The format is a small versioned text format defined in this node (section 3). The same wording as node 0.5's Done-when ("save/load round-trips are byte-identical") is used on purpose: this check proves it for this format. Floats are written with Rust's shortest round-trip form; NaN and infinity are refused by the writer and the reader with a named error (never saved as a surprise).

### 1.6.5 A file from an older schema version still loads

```check 1.6.5
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --load Vehicle fixtures/vehicle.v1.txt > scratch/reflect16-5.txt 2>&1
PASS: the file contains `run: ok` and the program line `load Vehicle file=fixtures/vehicle.v1.txt from_version=1 to_version=2 defaulted=1 renamed=1 ignored=1 result=PASS` (plan values: one new field took its declared default, one field was found under its `renamed_from` name, one unknown field was reported and dropped), and the loaded `mass_kg` equals the value written in the v1 file.
PRINTS: the line above, then one `note: <what happened to which field>` line per defaulted, renamed or ignored field.
```

Reason: this is node 0.5's second Done-when clause, needed here because a mode must keep loading data after the core adds a field. The v1 fixture is hand-written and was never produced by this program's writer. A file with a version newer than the type's is refused with a named error, not guessed at (covered by `text_rejects_newer_version` in R4).

### 1.6.6 A script edits a struct with no per-type code

```check 1.6.6
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --script fixtures/edit.script fixtures/edit.expected.txt > scratch/reflect16-6.txt 2>&1
PASS: the file contains `run: ok` and the program line `script fixtures/edit.script commands=<n> ok=<m> errors=<k> expected=fixtures/edit.expected.txt result=PASS`, with `errors` equal to the number of lines in the script marked `# expect-error` (plan value 3: an unknown path, an index out of range, a value over the field's maximum), and the final saved state equal to the hand-written expected file.
PRINTS: the line above, then one `error line <n>: <named error>` line per expected error.
```

"Scriptable" here means a plain text command language (`set vehicle.wheels[1].radius 0.34`, `get vehicle.mass_kg`, `add vehicle.wheels`, `remove vehicle.wheels[0]`, `save <file>`) that works on any reflected struct. The path rules and error names are in `docs/NODE16.md`. Real scripting languages (Python, Lua) reach the same operations through the C ABI (check 1.6.9).

### 1.6.7 A new field needs no other change (the "no glue" proof)

```check 1.6.7
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --glue-proof > scratch/reflect16-7.txt 2>&1
PASS: the file contains `run: ok` and the program line `glue-proof types=Vehicle,VehicleWide extra_field=armor_rating schema_diff_lines=1 inspector_diff_lines=1 save_diff_lines=1 script_ok=true generic_modules_clean=true result=PASS`. The two types go through the same generic code; the one added field shows up as exactly one new line in the schema text, one in the inspector text and one in the saved text, and a script can set it by path. `generic_modules_clean=true` means a scan of `src/{text,path,script,inspector,watch,abi,registry}.rs` found none of the sample type or field names (the unit test `no_fixture_names_in_generic_modules` does the same scan and is also run by check 1.6.1).
PRINTS: the line above, one line.
```

This is the check for the sentence "with no hand-written glue". It compares what changes when one field is added, which is the property that matters, instead of trusting that the generic code looks generic.

### 1.6.8 A live edit is announced to every watcher

```check 1.6.8
build/bin/broadsword.exe run reflect -- cargo run --offline --release --example reflect_demo -- --watch > scratch/reflect16-8.txt 2>&1
PASS: the file contains `run: ok` and the program line `watch Vehicle sets=4 accepted=3 rejected=1 events=3 first="vehicle.mass_kg 1200 -> 1350" result=PASS` (plan values): two watchers registered on the same value both receive each of the 3 accepted changes in order, and the rejected set (value over the maximum) produces no event and leaves the field unchanged.
PRINTS: the line above, then one `event <n> watcher=<a|b> path=<p> old=<v> new=<v>` line per delivery.
```

Reason: "every mode edits live" needs every change to a field to be visible to the other modes. The one set function is where it is announced, so a script, an inspector edit and a C caller all announce the same way. Undo and redo are not in this node's Done-when and are not planned here (a journal of these events is what they would use; see section 8).

### 1.6.9 A program in another language uses the C ABI (build, then call)

```check 1.6.9a
build/bin/broadsword.exe build reflect > scratch/reflect16-9a.txt 2>&1
PASS: the file ends with a `build: ok` line and `build/debug/reflect.dll` exists afterwards (the crate builds as `cdylib` as well as `rlib`; the exact output path is confirmed in R1 and corrected here).
PRINTS: broadsword's build job lines.
```

```check 1.6.9b
build/bin/broadsword.exe run reflect -- python -I scripts/abi_check.py --dll ../../build/debug/reflect.dll > scratch/reflect16-9b.txt 2>&1
PASS: the file contains `run: ok` and the line `abi python=<version> abi_version=1 types=<n> fields=<m> set_ok=true get=1350 error_code_ok=true result=PASS`: Python `ctypes` loads the DLL, lists the registered types and fields by name through `extern "C"` functions only, sets `vehicle.mass_kg` to 1350 by path, reads it back, and gets a nonzero error code (not a crash) for a null pointer, a bad path and an out-of-range value.
PRINTS: the line above, one line.
```

Why it goes through `broadsword run`: like every other check, it gets the job log and a Git checkpoint, and the run is refused if the disk guard says so. The command is `python -I scripts/abi_check.py` with the project folder as the working folder (that is where `broadsword run reflect` starts it), so the script is `scripts/abi_check.py` and the DLL is `../../build/debug/reflect.dll` (the shared build folder is at the Broadsword root; R8 confirms the path with 1.6.9a). `python` must be found on PATH by the job. If `broadsword run` cannot start it, that is a fault of the machine to report, not a reason to run python directly.

Reason: the product intent asks for a language-neutral core API. A caller in a different language, using nothing but the exported functions and the text form of values, is the real test; a Rust test calling `extern "C"` functions (`abi_set_get_roundtrip`) is only the cheaper half. Python is used because it is already on the PC and `ctypes` needs no C compiler or extra package. If the Python on PATH has no `ctypes` (confirm in R8), this check is a FAIL of the machine, to be reported, and the plan does not substitute a Rust-only test for it.

## 2. Home

- **Repo and crate:** a new, separate repo `projects/reflect` with one library crate `reflect` (`crate-type = ["rlib", "cdylib"]`, so the C ABI can be loaded by other languages), examples `reflect_demo` and `bench`, and its own Cargo workspace (`[workspace]` in `Cargo.toml`, as `projects/render` and `projects/crash-sim` do). Created by the orchestrator at Lazlo's approval (decision D1); no repo is created by this plan.
- **ADR 0001 (Accepted, option a):** separate repos, file formats are the contract, no Cargo dependency (path or git) on another repo without a new ADR, which is Lazlo's call. This node needs nothing from any other repo: the text format, the path language and the sample types are written inside `projects/reflect`. Never a link into `projects/foundation`.
- **When another repo needs this code it fires an ADR 0001 trigger, and in this node that is certain.** Reflection only matters if modes use it, so every later node that edits core data (2.4 scene system, 1.5 editor shell, 1.7 node graph, the studios) needs `reflect` as a library. That is trigger 1 ("a second project must run ... as a library") at the first such node and trigger 2 ("a third Rust project needs the same ... parser") soon after. Either one means ADR 0002 and the move to option d2 (one workload repo, a Cargo workspace) before any of them depends on `reflect`. This plan does not plan that dependency and does not ask for it; section 8 lists it as the first thing that will break the plan. Of all the nodes, this is where Lazlo should expect the ADR 0002 decision to be forced, because the shared core model is by its nature one crate that every mode imports.
- **File formats and C ABI as the contract:** this node's contract with other repos and other languages is data, not Rust types: the descriptor text (`reflect schema` form, versioned and hashed), the value text format (section 1.6.4), and the C ABI declared in `include/reflect.h`. Another repo can read a saved file or a schema dump without linking the crate, and a non-Rust mode can call the C functions. That fits the product intent, where the core API is language-neutral.
- **No mode owns reflection data.** A mode registers the types it defines with the registry (`reflect_register` by descriptor text, or through the macro for Rust code). Modes never depend on each other's types; they meet only through descriptors and paths.

## 4. External needs

All of the following except std are decisions for Lazlo. Nothing is fetched until he approves (network access and new dependencies are "ask first").

- **D1. A new repo `projects/reflect`** (plan only).
- **D2. Crates: none in this plan.** The design deliberately uses a declarative macro (`reflect! { struct ... }`, written with `macro_rules!`) so that the node is std-only: no proc-macro crate, no `syn`, `quote` or `proc-macro2`, no `serde`. The cost is that the "annotation" is a wrapper around the struct declaration, not `#[derive(Reflect)]` on an ordinary struct, and a struct defined elsewhere cannot be annotated after the fact. Lazlo may later approve a derive macro (three Rust crates from the registry, vetted, pinned and vendored, plus a second proc-macro crate in the repo) if the wrapper form is a problem for modes; this plan does not assume it, and a derive form would be a later brief against the same descriptor type.
- **D3. Python `ctypes` for the ABI check (1.6.9b).** Python is already an approved tooling language (AGENTS.md, Languages). It uses only the standard library. Which Python is used is the one on PATH; R8 records its version. No C compiler is needed.
- **D4. C/C++ libraries: none.** `include/reflect.h` is a hand-written header (about 40 lines) for other languages to read; no generator such as cbindgen is used (it would be a crate decision), and the test `header_matches_exports` checks the header against the exported names instead.
- **GPU access and memory (graphics-heavy: no).** The node uses no GPU and little memory, so Lazlo does not need to move the RAM/GPU split for it.
- **Hardware:** none. No tablet, gamepad, audio device or second PC.
- **Network data and licences:** none. No crate is added, so no licence needs checking beyond the repo's own.

Output line formats are fixed in `docs/NODE16.md` (briefs R9 and R10) so a check cannot pass on a reworded message. Every check prints labelled values and fails on empty output: a missing program line is a FAIL, never a PASS.

Edge input the tests must name (what must never happen): a path with an empty segment, a leading or trailing dot, an index that is negative, non-numeric or overflows `usize`, a path longer than a limit read from `reflect.toml` (the repo's own config, see below); text values with CR or LF in a string (escaped, never raw), an unescaped quote, an invalid escape, a number with a sign or a leading zero that does not parse, NaN, infinity, an integer outside its type's range (never silently wrapped to 0); a field set to a value of the wrong kind; a set that would break a `range` annotation (rejected, field unchanged); a C call with a null pointer, a zero-length buffer, a buffer too small for the answer (the needed size is returned), non-UTF-8 bytes; a panic inside a call never unwinds across the C boundary (caught and returned as an error code). The limits (path length, text file size, list length, nesting depth) are **required keys** in the new repo's own config file, with no default in code. This repo has no `broadsword.toml` of its own, so R1 decides where they live (a `reflect.toml` read by the demo and tests, and passed to the library as a `Limits` value), and says so in `docs/NODE16.md`.

Known blind spots to carry into the briefs: golden files written by the same person who wrote the writer share that person's reading of the format, so each golden is worked from the format's written rule in `docs/NODE16.md` first. A Rust test calling `extern "C"` functions cannot catch an ABI mismatch with a real C or Python caller; that is why check 1.6.9b exists. The sample types are small; deep nesting and large lists are covered only by the limit tests, not by a realistic core scene.

## 6. Reference data

List only; nothing is downloaded. No test data from outside is used, with one exception: the published FNV-1a test vectors below (a few short constants, named with their URL). Every other input is generated in code or written by hand in the repo, and every expected value is hand-worked, so there is no other third-party data to licence. This is deliberate: the checks compare the node's own outputs to rules, and external data would add a licence and a download for no extra proof.

- **Rust Reference, `extern` functions and the C ABI, and `repr(C)`:** https://doc.rust-lang.org/reference/items/external-blocks.html and https://doc.rust-lang.org/reference/type-layout.html . ## 8. Risks and size

- **`macro_rules!` may not be enough.** A wrapper declaration is less natural than `#[derive]`, and the macro for nested and generic kinds (`Vec<T>`, `Option<T>`, `[T; N]`) may become long or hit recursion limits. If R3 finds that, the question for Lazlo is decision D2 (a derive macro needs crates). The plan does not decide that for him.
- **ADR 0001 trigger 1 fires as soon as a second repo wants this crate.** Every mode does. The plan works for this node alone; the next node that needs `reflect` stalls until ADR 0002 (Lazlo) moves the repos into one workspace. The API is data in and out and carries no mode types, so the code needs no change when that happens. This is the most likely point where the whole unified-tool idea is tested.
- **The format may collide with node 0.5.** If 0.5 later defines a different project-wide format, this node's text format either becomes a view of it or gets a converter; either way a check in 0.5 will need to read a file this node wrote. Mitigation: the header carries a format name and version from the first commit, and the format is documented in `docs/NODE16.md`.
- **Unified-tool intent.** The shared core's layout will eventually be defined by whoever owns the core crate. The descriptor hash makes a layout change visible, but nothing here forces a mode to re-check on a change; the harness rule for cross-shard changes is a separate piece of work. The C ABI's version number (`abi_version=1`) is likewise only a signal until a mode checks it.
- **C ABI safety.** Raw pointers, string lifetimes and ownership rules are where a bug becomes a crash in another language. Mitigation: every call returns a code, panics are caught at the boundary, the header documents who frees what, and 1.6.9b uses a real foreign caller. Not covered: concurrent calls from several threads. The plan assumes single-threaded use per registry and says so in `docs/NODE16.md`; thread safety is a later decision.
- **Python on this PC may lack `ctypes` or may be a 32-bit build** that cannot load a 64-bit DLL. Then check 1.6.9b fails for the machine and is reported, not replaced.
- **Check numbers are plan values.** The widget count (9), the counts in 1.6.5, 1.6.6 and 1.6.8, and the test count (29) are guesses until R9 and R10 fix them. A check whose value is changed to make it pass must say why in `docs/NODE16.md`.
- **Not in this node's Done-when and not planned:** undo and redo, a real inspector window (node 1.5), live reload of a changed schema in a running mode, maps and sets, references between objects, thread safety, a scripting language embedded in the program (checks use the line-command script and the C ABI). A rough estimate is 5 to 8 more briefs for these after the Done-when, not planned here.
- **Size.** Ten briefs reach the Done-when (R1 to R10), about 2,200 changed lines in total if each stays near 220 (fixtures and docs included). Of those, about seven are code and tests, two are harness and fixtures (R9, R10 in part), and one is the skeleton. R3 to R6 are the best candidates to run at once on idle slots.
