## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root, where `build/bin/broadsword.exe` is the Broadsword binary. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test raster`. A program goes through `broadsword run raster -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`). Read the file. The programs print their results to stdout, so nothing is written elsewhere.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. Rules that name a program line are judged with "contains".
- `python -I scripts/node_check.py 2.1 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text, including every `(human)` rule, is printed as "judge by hand". A command that exits non-zero is a FAIL unless its rule is `exit != 0`. A negative control (a check that must fail on purpose: d9 and d11) is written as `PASS: exit != 0`; its expected line is then read by hand from the saved file. A negative control means something only when its positive twin (d8 for d9, d10 for d11) has passed with the same example.
- Never use `--run --all` on this node: run one id at a time, and leave the `(human)` id (d13) to Lazlo.
- A rule ending `(quiet board)` is timing. Run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board.
- A rule ending `(GPU)` needs a working GPU adapter (wgpu, the 1.2 layer). With no adapter the check fails loudly; it is never skipped.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when: a 16k × 16k image with 50 layers stays interactive while painting and adjusting

The Done-when has three parts, and each gets its own checks. (1) The storage and maths that make a large multi-layer image possible: tiles, blend modes, masks, compositing, adjustments and painting. (2) A CPU benchmark of the full-size case, with a frame budget and a memory budget. (3) The same composite on the GPU (1.2), and the live window (interactive, human-checked).

**Scale arithmetic, the reason the design is tiled and sparse.** A 16384 × 16384 canvas has 16384 × 16384 = 268,435,456 pixels (computed with Python in this worktree). One layer of that size is 1.0 GiB at 4 bytes per pixel (RGBA8) and 4.0 GiB at 16 bytes per pixel (RGBA32F). Fifty full-coverage layers would be 50 GiB at RGBA8 and 200 GiB at RGBA32F. The PC has 111.6 GB of physical RAM (`Win32_ComputerSystem`, read with PowerShell on 2026-11-21), so a dense 50-layer image cannot be held in memory as float data. Sparse tiles are the only way the Done-when is reachable, and section 8 (risk K3) says what "50 layers" must mean.

**d1 Tile store round-trip.** Tiles are 256 × 256 pixels (an estimate: a common size in tiled editors, chosen so a 16k canvas is 64 × 64 = 4,096 tile slots per layer, and a tile is 256 KiB at RGBA8). A sparse layer stores only the tiles that were painted; a tile written and read back returns identical values.
```check d1
build/bin/broadsword.exe test raster > scratch/n21-d1.txt 2>&1
PASS: contains test tile_store_round_trip ... ok
```
Threshold reason: none needed; it is an exact round trip. FAIL: the line is missing (no such test) or the suite says FAILED.

**d2 Blend modes match the reference formulas.** The twelve separable blend modes of the W3C Compositing and Blending Level 1 specification (normal, multiply, screen, overlay, darken, lighten, color-dodge, color-burn, hard-light, soft-light, difference, exclusion) are checked against reference values in `tests/fixtures/blend_reference.txt`. The reference values are computed by hand from the spec's formulas in brief R3 and written into the fixture as text. Tolerance: 1e-6 absolute on f32 results. Reason: the formulas are closed form, and f32 rounding on one operation is about 6e-8, so 1e-6 leaves room for a few operations. The non-separable modes (hue, saturation, colour, luminosity) are out of this node's first cut; a later brief adds them with their own reference values.
```check d2
build/bin/broadsword.exe test raster > scratch/n21-d2.txt 2>&1
PASS: contains test blend_modes_match_w3c_reference ... ok
```

**d3 Masks and selections compose exactly.** The test composes a layer alpha with a mask and a selection and requires the result to equal the product of the three values. Values are chosen from 0.0, 0.5 and 1.0, which multiply exactly in f32, so the rule is exact equality. The test also requires a fully-masked pixel to stay fully transparent after any blend mode.
```check d3
build/bin/broadsword.exe test raster > scratch/n21-d3.txt 2>&1
PASS: contains test mask_and_selection_compose ... ok
```

**d4 Fifty layers composite to the dense reference.** A 768 × 512 canvas (3 × 2 tiles) with 50 sparse layers, each with a mask and a blend mode taken in turn from the twelve (layer i uses mode i mod 12, so modes repeat), is composited by the tile compositor and compared with a dense, unoptimised composite written inside the test. Tolerance: 1e-5 absolute per channel. Reason (estimate): each of 50 blends rounds once per channel, about 6e-8 each in f32, so the accumulated error is far below 1e-5; the tolerance is wide enough for a different summation order. R5 also checks that dropping one layer from the stack changes the output by more than 1e-2, so the test can see a dropped layer.
```check d4
build/bin/broadsword.exe test raster > scratch/n21-d4.txt 2>&1
PASS: contains test composite_50_layers_matches_dense_reference ... ok
```

**d5 Adjustments are non-destructive.** Three adjustments (brightness and contrast, a curve, hue and saturation) are applied as pure functions to a layer's tile, then removed. The source tiles must be byte-for-byte equal to their original values after removal, and the adjusted output of each tile must equal a dense per-pixel reference written inside the test from the same formulas (1e-6 absolute). Compositing the adjustments is d12's. Reason: the source is stored as f32 and never requantised, so equality is exact.
```check d5
build/bin/broadsword.exe test raster > scratch/n21-d5.txt 2>&1
PASS: contains test adjustments_are_non_destructive_round_trip ... ok
```

**d6 A stroke marks only the tiles it crosses.** A straight 500-pixel stroke from (100, 100) to (600, 100) with radius 8 has a bounding box from x 92 to 608 and y 92 to 108. Those cover tile columns 0 to 2 and tile row 0, so the stroke dirties exactly tiles (0,0), (1,0) and (2,0) (computed by hand: 92 / 256 and 608 / 256 round down to 0 and 2; the rows 92 to 108 all lie in row 0). The test lists these three tiles by hand. Reason: exact set equality; a stroke that dirties a whole layer would make every later frame re-composite 4,096 tiles.
```check d6
build/bin/broadsword.exe test raster > scratch/n21-d6.txt 2>&1
PASS: contains test stroke_marks_only_dirty_tiles ... ok
```

**d8 The full-size benchmark (quiet board).** The example builds a 16384 × 16384 canvas with 50 layers, each layer covering a 4096 × 4096 patch (`--layer-coverage 0.0625`, so 1/16 of the canvas; section 8 K3). It runs 600 frames; each frame paints one stroke into one layer, adjusts one layer, and composites a 1920 × 1080 viewport. It prints the frame p99 in milliseconds and the peak resident memory in GiB, and exits 0 only if p99 is at most `--frame-budget-ms` and resident memory is at most `--max-resident-gib`.
- Frame budget 16.7 ms: 1000 ms / 60 = 16.7 ms, one frame at 60 Hz. An estimate of "interactive", not a published benchmark; the first quiet-board run is recorded in `docs/nodes/2.1.md` and the budget revised with a reason, as node 1.1 does for its d3.
- Memory budget 16 GiB: about 14 percent of the 111.6 GB of RAM on this PC (see above). An estimate that leaves room for the build folder and other work; Lazlo may change it.
```check d8
build/bin/broadsword.exe run raster -- cargo run --offline --release --example bench_stack -- --size 16384 --layers 50 --layer-coverage 0.0625 --frames 600 --frame-budget-ms 16.7 --max-resident-gib 16 > scratch/n21-d8.txt 2>&1
PASS: contains bench_stack: ok size=16384 layers=50
```
(quiet board.) The program prints `bench_stack: ok size=16384 layers=50 frames=<n> p99_ms=<x> resident_gib=<x>` on success. On failure it prints `bench_stack: FAIL frame` (p99 over budget) or `bench_stack: FAIL memory` (resident over budget) and exits 1. FAIL: any other output.

## 2. Home

**A new repo, `projects/raster`, crate `raster` (library, Rust 2021, std only), created by brief R1.** `projects/raster` is its own Git repo, ignored by the Broadsword repo, like `projects/crash-sim` and `projects/render` (`broadsword.toml`, `projects_dir`). It is registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, so it does not join the Broadsword workspace. The orchestrator creates the repo and boards it as project `raster` after Lazlo approves a new repo, the same step as node 1.1's section 2.

Under ADR 0001 (option a, accepted, `docs/adr/0001-shared-core.md`):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` stays empty until brief R9 (check d7). The crate does not depend on `projects/gpu` (node 1.2), `projects/nodegraph` (node 1.7), any colour crate (node 1.11) or `projects/foundation`. The plan never links into `projects/foundation`.
- **No copies are needed for briefs R1 to R8.** Tiles, blend formulas, masks, the dense reference, adjustments and the paint stamp are plain `f32` arrays and std code. Nothing from 1.2, 1.7 or 1.11 is needed to pass d1 to d8, so none is copied.
- **Copies are refused for what R9 and R10 need.** Copying the GPU layer or the graph evaluator into this repo would make a second copy of code another node owns, which ADR 0001 rejects as a copy that drifts. So R9 and R10 wait for the decision below.

**ADR 0001 triggers this node fires, named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires twice. R9 (d10, d11) must call node 1.2's `gpu` crate in-process to composite on the GPU. R10 (d12, d13) must evaluate node 1.7's graph in-process, since a live graph cannot go through a file. Either one means the move to ADR 0002 (one workload repo with a Cargo workspace, option d2), which is Lazlo's decision and is not made by this plan. Until ADR 0002 is accepted, R9 and R10 do not start. ADR 0001 already names a spike for this move as follow-up F5 (`docs/adr/0001-shared-core.md` line 246), and ADR 0004 says that spike "may start now" (`docs/adr/0004-roadmap-repo-map.md` line 195). The spike is not part of this node's plan.
- **Trigger 2** ("a third Rust project needs the same ...") is not fired. The tile type is used only by this crate until node 3.8 (texture painting) or 4.4 (image studio) start, and they are not planned yet.
- **ADR 0004** (`docs/adr/0004-roadmap-repo-map.md`, Proposed) should list node 2.1 -> `raster` with trigger 1 above. This plan does not edit ADR 0004.

**Fit with the product intent.** The crate has four layers, so a mode never owns pixels and a test never needs a GPU:

1. *Data:* `Tile` (256 × 256, `f32` RGBA premultiplied), `TileStore` (sparse map from tile coordinates to tiles), `Layer` (opacity, blend mode, optional mask, offset), `Document` (canvas size and the layer list). Std only, no window.
2. *Maths:* `blend.rs` (the twelve separable modes), `mask.rs` (mask and selection values), `layer.rs` (the compositor over a `Document`). Pure functions.
3. *Edits:* `paint.rs` (stamps a stroke into tiles and reports the dirty tiles) and `adjust.rs` (pure per-tile functions for brightness and contrast, curves, hue and saturation). A mode asks the `Document` for tiles and edits through the API; it does not keep its own pixel buffers.
4. *Glue to other nodes:* `gpu_compose.rs` (R9, 1.2's GPU) and `graph_bridge.rs` (R10, 1.7's graph). These are the only files that will touch another repo's API, and they exist only after ADR 0002.

Modes receive a `Document` from the shell (node 1.5); they never open a window or run the compositor's private steps. That keeps "no mode depends on another mode" true for pixels as well as input.

## 5. Test harness

| Check | Kind of test | What it compares against |
|---|---|---|
| d1 | round trip, unit test | the values written, read back and compared for equality |
| d2 | reference-value tests for 12 blend modes | reference values in `tests/fixtures/blend_reference.txt`, computed by hand from the W3C formulas; tolerance 1e-6 |
| d3 | exact-product test on 0.0, 0.5 and 1.0 values | the product of the three inputs, exact in f32 |
| d4 | dense reference composite written inside the test, plus a drop-one-layer sensitivity test | tolerance 1e-5 per channel |
| d5 | byte equality of source tiles before and after adjustments | the original tile values |
| d6 | set equality of dirty tiles | the three tiles counted by hand: (0,0), (1,0), (2,0) |
| d7 | structure test reading `Cargo.toml` | empty dependency tables |
| d8, d9 | quiet-board benchmark with a frame and memory budget, and a negative control | 16.7 ms frame and 16 GiB resident (estimates, section 1); 0.001 ms must fail |
| d10, d11 | GPU output read back and compared with the CPU reference from R5, and an injected fault | tolerance 1e-5 absolute; `--inject-fault` must fail |
| d12 | evaluation counter in the graph evaluator | exactly 2 evaluations after one parameter change |
| d13 | human check with the printed summary line | Lazlo's eyes and the printed p99 and resident values |
| d14 | whole suite | every test above |

**Fixtures.** Text only, small, committed in the new repo: `tests/fixtures/blend_reference.txt` (hand-computed reference values for the 12 separable modes, a few input pairs each, written by R3 from the formulas in section 6). No image fixture and no golden image: every test builds its input in code from a fixed pattern, so the inputs are deterministic and small. A golden-image test (node 0.9's pattern) is not needed for this node's checks; a later node that writes images to disk may add one.

**Negative controls and mutation steps.** A check must be able to fail (playbook lesson 10). Three kinds:

- Negative controls on the same example: d9 (benchmark budget 0.001 ms) and d11 (`--inject-fault`). Each is valid only with its positive twin (d8, d10) passing.
- Mutation steps in the briefs, as node 1.1 does: R2 changes the tile round-trip to lose one value and shows d1 failing; R3 changes one blend formula (for example multiply) and shows d2 failing; R5 drops the last layer from the composite and shows d4 failing. Each step restores the code and saves the output in `scratch/`.
- d12's counter is written by hand in the test, so a graph that re-evaluates everything fails it.

**Where the CPU and the GPU are compared.** d4 is the CPU reference, written as dense code and never as the tile compositor's own output. d10 compares the GPU with that CPU reference, so a wrong tile compositor and a wrong GPU would both show up as a difference. Known blind spot: a formula that is wrong in both the CPU reference and the GPU shader is not caught by d4 or d10. d2 is the check against that, because its reference values come from the spec, not from this code.

## 8. Risks and size

**Risks, with what to do.** They are numbered K1 to K10 so they do not collide with the briefs R1 to R10.

- **K1 Prerequisites.** 1.2, 1.7 and 1.11 are not started, and 1.7's stage in ROADMAP.md reads `none`. The node prompt's stop rule would block the whole node. Ask Lazlo before R1 whether the CPU half (R1 to R8) starts now (section 3). Cost of asking: one message. Cost of not asking: a stopped coder, or work built on a plan that was never agreed.
- **K2 ADR 0002 gates R9 and R10.** d10 to d13 cannot pass until Lazlo decides ADR 0002 (section 2, trigger 1). The CPU checks d1 to d9 and d14's CPU tests do not depend on it, so they can finish first. This is the largest decision in the plan.
- **K3 What "50 layers" means, and memory.** Arithmetic (section 1): a full 16384 × 16384 layer is 1 GiB at RGBA8 and 4 GiB at RGBA32F, so 50 full layers are 50 GiB or 200 GiB. d8 uses 1/16 coverage per layer (a 4096 × 4096 patch, 16,777,216 pixels): 64 MiB per layer at RGBA8, 256 MiB at RGBA32F, so 3.1 GiB or 12.5 GiB for 50 layers (computed with Python in this worktree). At 12.5 GiB the 16 GiB budget leaves 3.5 GiB, and R2's choice of `f32` (exact round trips for d1 and d5) is what makes it tight. Lazlo decides two things: what coverage the Done-when means, and the storage precision. If he means full coverage, d8 fails by design, and the budget or the Done-when is changed with a written reason, never loosened silently.
- **K4 The CPU frame budget is probably too tight.** One full recomposite of a 1920 × 1080 viewport over 50 layers is 2,073,600 × 50 = 103,680,000 blends (about 1.04 × 10^8). At an **estimated** 2 to 5 ns per blend on one core (not measured on this PC), that is 0.2 to 0.5 s, 12 to 30 times the 16.7 ms budget. With the per-tile cache in R8, a frame recomputes only dirty tiles: one dab usually dirties 1 to 4 tiles, and one tile is 65,536 × 50 = 3,276,800 blends, about 6.6 to 16 ms at the same estimate. So d8 may **fail** on the CPU even with the cache. That result is recorded as it is, not tuned away; the GPU path (R9, d10) is the realistic route to 16.7 ms, and it is gated (K2).
- **K5 Job system not started.** Multithreading the CPU composite needs node 0.4, which is not started (ROADMAP.md line 14). Until then d8 is single-threaded. Lazlo's decision, as in node 1.1 (section 3): wait for 0.4 or accept a single-thread baseline.
- **K6 Viewport GPU memory and spill.** Section 4 estimates about 2 GiB of GPU-visible memory for 50 visible layers at RGBA32F. On an integrated GPU that memory is part of system RAM, so it competes with the CPU path. No spill is built. If R8 cannot meet its memory budget without one, the spill goes to the project's data folder (never `scratch/`, which can be wiped at any time), and a spilled tile is never the only copy of its pixels.
- **K7 The live window and the human check.** d13 needs a window (the 1.2 surface or 1.1) and Lazlo at a logged-in desktop. Until one of those exists, d13 cannot run, and it is reported as blocked, not passed.
- **K8 Cross-repo drift.** Nodes 1.2 and 1.7 are not built, so `gpu` and `nodegraph` have no API yet. The 1.2 plan says wgpu's API changes between releases. R9 and R10 read the pinned API when they start, and their briefs are rewritten at that point. This plan's text for them is a plan, not a contract.
- **K9 Colour is untested.** Node 1.11 has no plan, and its roadmap line wraps OpenColorIO, a C++ library (section 4). R5 defines the composite as linear `f32`, so nothing in d1 to d14 checks what the screen or a file shows. Any colour claim about 2.1 waits for 1.11's own checks.
- **K10 Scope of the blend modes.** d2 covers the twelve separable modes only. Hue, saturation, colour and luminosity are not checked by any check here. A user who picks one of them gets no check of its maths until a later brief adds it with its own reference values.

**Size.** Ten briefs (R1 to R10), about 250 lines each, so roughly 2,000 to 2,500 changed lines in all, counting tests, fixtures and the examples (estimate, from the same shape as 1.1's section 8). Allow about two fix-round tasks, most likely on R3 (the formulas), R5 (the composite) and R8 (the benchmark), since those are the places a first review is most likely to fail (playbook lesson 6). So about ten merged tasks plus two fix rounds to reach the Done-when on the CPU half, and two more gated tasks (R9, R10) after ADR 0002. Human checks: d13 only, run by Lazlo. Quiet-board runs: d8 and d9. The critical path is R1, R2, R4, R5, R8: five rounds, with R3, R6 and R7 beside them.
