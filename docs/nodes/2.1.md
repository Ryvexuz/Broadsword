## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root, where `build/bin/broadsword.exe` is the Broadsword binary. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test raster`. A program goes through `broadsword run raster -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`). Read the file. The programs print their results to stdout, so nothing is written elsewhere.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. Rules that name a program line are judged with "contains".
- `python -I scripts/node_check.py 2.1 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text, including every `(human)` rule, is printed as "judge by hand". A command that exits non-zero is a FAIL unless its rule is `exit != 0`. A negative control (a check that must fail on purpose: d9 and d11) is written as `PASS: exit != 0`; its expected line is then read by hand from the saved file. A negative control means something only when its positive twin (d8 for d9, d10 for d11) has passed with the same example.
- Never use `--run --all` on this node: run one id at a time, and leave the `(human)` id (d13) to Lazlo.
- A rule ending `(quiet board)` is timing. Run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board.
- A rule ending `(GPU)` needs a working GPU adapter (wgpu, the 1.2 layer). With no adapter the check fails loudly; it is never skipped.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when: a 16k × 16k image with 50 layers stays interactive while painting and adjusting

The Done-when has three parts, and each gets its own checks. (1) The storage and maths that make a large multi-layer image possible: tiles, blend modes, masks, compositing, adjustments and painting. (2) A CPU benchmark of the full-size case, with a frame budget and a memory budget. (3) The same composite on the GPU (1.2), and the live window (interactive, human-checked).

**Scale arithmetic, the reason the design is tiled and sparse.** A 16384 × 16384 canvas has 16384 × 16384 = 268,435,456 pixels (computed with Python in this worktree). One layer of that size is 1.0 GiB at 4 bytes per pixel (RGBA8) and 4.0 GiB at 16 bytes per pixel (RGBA32F). Fifty full-coverage layers would be 50 GiB at RGBA8 and 200 GiB at RGBA32F. The PC has 111.6 GB of physical RAM (`Win32_ComputerSystem`, read with PowerShell on 2026-11-21), so a dense 50-layer image cannot be held in memory as float data. Sparse tiles are the only way the Done-when is reachable, and section 8 (risk R3) says what "50 layers" must mean.

**d1 Tile store round-trip.** Tiles are 256 × 256 pixels (an estimate: a common size in tiled editors, chosen so a 16k canvas is 64 × 64 = 4,096 tile slots per layer, and a tile is 256 KiB at RGBA8). A sparse layer stores only the tiles that were painted; a tile written and read back returns identical values.
```check d1
build/bin/broadsword.exe test raster > scratch/n21-d1.txt 2>&1
PASS: contains test tile_store_round_trip ... ok
```
Threshold reason: none needed; it is an exact round trip. FAIL: the line is missing (no such test) or the suite says FAILED.

**d2 Blend modes match the reference formulas.** The twelve separable blend modes of the W3C Compositing and Blending Level 1 specification (normal, multiply, screen, overlay, darken, lighten, color-dodge, color-burn, hard-light, soft-light, difference, exclusion) are checked against reference values in `tests/fixtures/blend_reference.txt`. The reference values are computed by hand from the spec's formulas in brief R3 and written into the fixture as text. Tolerance: 1e-6 absolute on f32 results. Reason: the formulas are closed form, and f32 rounding on one operation is about 6e-8, so 1e-6 leaves room for a few operations. The non-separable modes (hue, saturation, colour, luminosity) are out of this node's first cut; a later brief adds them with their own reference values.
```check d2
build/bin/broadsword.exe test raster > scratch/n21-d2.txt 2>&1
PASS: contains test blend_modes_match_w3c_reference ... ok
```

**d3 Masks and selections compose exactly.** The test composes a layer alpha with a mask and a selection and requires the result to equal the product of the three values. Values are chosen from 0.0, 0.5 and 1.0, which multiply exactly in f32, so the rule is exact equality. The test also requires a fully-masked pixel to stay fully transparent after any blend mode.
```check d3
build/bin/broadsword.exe test raster > scratch/n21-d3.txt 2>&1
PASS: contains test mask_and_selection_compose ... ok
```

**d4 Fifty layers composite to the dense reference.** A 768 × 512 canvas (3 × 2 tiles) with 50 sparse layers, each with a different blend mode and mask, is composited by the tile compositor and compared with a dense, unoptimised composite written inside the test. Tolerance: 1e-5 absolute per channel. Reason (estimate): each of 50 blends rounds once per channel, about 6e-8 each in f32, so the accumulated error is far below 1e-5; the tolerance is wide enough for a different summation order. R5 also checks that dropping one layer from the stack changes the output by more than 1e-2, so the test can see a dropped layer.
```check d4
build/bin/broadsword.exe test raster > scratch/n21-d4.txt 2>&1
PASS: contains test composite_50_layers_matches_dense_reference ... ok
```

**d5 Adjustments are non-destructive.** Three adjustments (brightness and contrast, a curve, hue and saturation) are applied as nodes on a layer, then removed. The source tiles must be byte-for-byte equal to their original values after removal, and the rendered output with the adjustments present must equal the dense reference. Reason: the source is stored as f32 and never requantised, so equality is exact.
```check d5
build/bin/broadsword.exe test raster > scratch/n21-d5.txt 2>&1
PASS: contains test adjustments_are_non_destructive_round_trip ... ok
```

**d6 A stroke marks only the tiles it crosses.** A straight 500-pixel stroke from (100, 100) to (600, 100) with radius 8 has a bounding box from x 92 to 608 and y 92 to 108. Those cover tile columns 0 to 2 and tile row 0, so the stroke dirties exactly tiles (0,0), (1,0) and (2,0) (computed by hand: 92 / 256 and 608 / 256 round down to 0 and 2; the rows 92 to 108 all lie in row 0). The test lists these three tiles by hand. Reason: exact set equality; a stroke that dirties a whole layer would make every later frame re-composite 4,096 tiles.
```check d6
build/bin/broadsword.exe test raster > scratch/n21-d6.txt 2>&1
PASS: contains test stroke_marks_only_dirty_tiles ... ok
```

**d7 The crate has no dependencies (at first).** Under ADR 0001 (option a) the crate depends on no other repo and on no registry crate until ADR 0003 allows one. The test reads `Cargo.toml` and requires the `[dependencies]`, `[dev-dependencies]` and `[build-dependencies]` tables to be empty or absent. Brief R9 changes this test, with a reason, when ADR 0002 lets the crate depend on the gpu crate; it does not delete the test.
```check d7
build/bin/broadsword.exe test raster > scratch/n21-d7.txt 2>&1
PASS: contains test cargo_toml_has_no_dependencies ... ok
```

**d8 The full-size benchmark (quiet board).** The example builds a 16384 × 16384 canvas with 50 layers, each layer covering a 4096 × 4096 patch (`--layer-coverage 0.0625`, so 1/16 of the canvas; section 8 R3). It runs 600 frames; each frame paints one stroke into one layer, adjusts one layer, and composites a 1920 × 1080 viewport. It prints the frame p99 in milliseconds and the peak resident memory in GiB, and exits 0 only if p99 is at most `--frame-budget-ms` and resident memory is at most `--max-resident-gib`.
- Frame budget 16.7 ms: 1000 ms / 60 = 16.7 ms, one frame at 60 Hz. An estimate of "interactive", not a published benchmark; the first quiet-board run is recorded in `docs/nodes/2.1.md` and the budget revised with a reason, as node 1.1 does for its d3.
- Memory budget 16 GiB: about 14 percent of the 111.6 GB of RAM on this PC (see above). An estimate that leaves room for the build folder and other work; Lazlo may change it.
```check d8
build/bin/broadsword.exe run raster -- cargo run --offline --release --example bench_stack -- --size 16384 --layers 50 --layer-coverage 0.0625 --frames 600 --frame-budget-ms 16.7 --max-resident-gib 16 > scratch/n21-d8.txt 2>&1
PASS: contains bench_stack: ok size=16384 layers=50
```
(quiet board.) The program prints `bench_stack: ok size=16384 layers=50 frames=<n> p99_ms=<x> resident_gib=<x>` on success. On failure it prints `bench_stack: FAIL frame` (p99 over budget) or `bench_stack: FAIL memory` (resident over budget) and exits 1. FAIL: any other output.

**d9 The benchmark can fail (quiet board).** Same example with an impossible frame budget of 0.001 ms.
```check d9
build/bin/broadsword.exe run raster -- cargo run --offline --release --example bench_stack -- --size 16384 --layers 50 --layer-coverage 0.0625 --frames 600 --frame-budget-ms 0.001 --max-resident-gib 16 > scratch/n21-d9.txt 2>&1
PASS: exit != 0
```
(quiet board.) Expected: the run exits non-zero and the saved file contains `bench_stack: FAIL frame` (read it by hand; `node_check.py` judges only the exit code). Reason for 0.001 ms: a frame that paints, adjusts and composites a viewport cannot take a microsecond; if this ever prints `ok`, the timer or the percentile code is wrong. FAIL: `bench_stack: ok` (d8 then proves nothing).

**d10 The GPU composite matches the CPU reference (GPU).** `gpu_composite` builds the same 50-layer, 1024 × 1024 test stack (every layer covers the whole canvas; 50 × 4 MiB at RGBA8 is 200 MiB), composites it on the GPU through the 1.2 layer (`gpu` crate, brief R9), reads it back, and compares every channel with the CPU reference from R5. The program prints `gpu_composite: ok layers=50 size=1024 max_abs_diff=<x> backend=<name>` and exits 1 with `gpu_composite: FAIL diff` if the largest difference is above `--max-abs`. Tolerance 1e-5 absolute: the GPU may use fused multiply-add, which changes the last bits (`docs/nodes/1.2.md` section 5 says the same of its float check), and 1e-5 is the bound d4 uses on the CPU for the same stack.
```check d10
build/bin/broadsword.exe run raster -- cargo run --offline --release --example gpu_composite -- --layers 50 --size 1024 --max-abs 0.00001 > scratch/n21-d10.txt 2>&1
PASS: contains gpu_composite: ok layers=50 size=1024
```
(GPU.) Needs ADR 0002 and node 1.2 merged (section 2). Not runnable before brief R9 merges.

**d11 The GPU check can fail (GPU).** Same example with `--inject-fault`, which adds 0.01 to one channel of one output pixel before comparing.
```check d11
build/bin/broadsword.exe run raster -- cargo run --offline --release --example gpu_composite -- --layers 50 --size 1024 --max-abs 0.00001 --inject-fault > scratch/n21-d11.txt 2>&1
PASS: exit != 0
```
(GPU.) Expected: exit non-zero, and the saved file contains `gpu_composite: FAIL diff`. FAIL: `gpu_composite: ok` (the comparison cannot see one wrong pixel).

**d12 Adjustments run through the node graph and re-evaluate only what changed.** The test builds a graph of one composite node and one adjustment node per layer (50 layers), changes the parameter of one adjustment, and requires the evaluator to re-run exactly two nodes: the changed adjustment and the composite node that reads its layer. It counts evaluations. Reason: exact count equality, from dirty propagation (only the changed node and what reads it downstream are dirty); the expected count 2 is written by hand in the test source. Needs ADR 0002 (the crate depends on `nodegraph`, the 1.7 crate; section 2).
```check d12
build/bin/broadsword.exe test raster > scratch/n21-d12.txt 2>&1
PASS: contains test adjust_graph_reevaluates_only_dirty ... ok
```

**d13 The live window stays interactive while painting and adjusting (human).** Lazlo paints with the mouse for 60 seconds into a 16384 × 16384 image with 50 layers, drags an adjustment slider on one layer, and watches the viewport. The example opens a window through the 1.2 surface (or the 1.1 window, once it exists) and prints one summary line.
```check d13
build/bin/broadsword.exe run raster -- cargo run --offline --release --example bench_stack -- --size 16384 --layers 50 --layer-coverage 0.0625 --interactive --seconds 60 --frame-budget-ms 16.7 --max-resident-gib 16 > scratch/n21-d13.txt 2>&1
PASS: (human) Lazlo confirms the printed bench_stack line shows p99_ms at most 16.7 and resident_gib at most 16, and that the viewport showed no visible stall during the 60 seconds while painting and dragging the slider.
```
(human, GPU, desktop.) Blocked until a window exists (1.1, or the 1.2 surface brief) and ADR 0002 is decided (section 2). Mouse input is enough here; pen input is node 1.1's and 2.2's check. A "visible stall" means a pause the eye can see, estimated at 100 ms (about six frames at 60 Hz); Lazlo judges it by eye and the printed p99 is the record.
