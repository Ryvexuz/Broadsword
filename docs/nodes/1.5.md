Done when: a docked layout saves and restores exactly; the shell holds 60 fps with 20 panels open. Broadsword stage: 1. ROADMAP.md status today: not started.

**Product intent this plan is built around** (Lazlo, 2026-11-20, `state/backlog/t-20261120-013957.md`, "Product intent"): one unified tool. Picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared, live core data model, with no export or import. Modes are switchable plugins over a stable core API, loaded on selection; no mode depends on another mode's internals; the core API stays language-neutral (C ABI or FFI-friendly, serializable data). **The shell is the one place that switches modes**, so its design follows from that:

- **The shell owns no core data.** It holds a `CoreHandle` (an opaque handle to the one shared core) and passes it to every panel. A panel stores *references* into the core (object ids, a selection, a camera), never a copy of core data. Switching modes changes which panels and tools are active; it never copies, exports or reloads core data (check d15).
- **A mode is a registered descriptor, plain data:** `ModeDescriptor { id, name, group, panel_kinds: [PanelKindId], tool_ids }`. The crate group behind a mode is activated the first time the mode is selected (check d16), which is the shell's half of "loaded on selection"; dynamic loading and hot reload are node 0.7's.
- **Each mode has its own perspective:** a dock tree of panels. The layout file holds every mode's perspective plus the active mode, so a layout saves and restores across modes, and switching mode swaps the active perspective only.
- **A panel is data plus a provider.** `Panel { id: PanelId, kind: PanelKindId (a string such as "render.viewport"), state: versioned bytes, view: core references }`. The mode that owns the kind supplies a provider; the shell never knows a mode's types.
- **Panels talk to the shell only in plain messages** (the panel protocol, section 2): input in, a draw list out (rectangles, glyph runs, images, as integers and bytes). The shell does all painting. Because the messages have a byte encoding (check d17), a mode written in another language later needs only that encoding, not a Rust type. That is the language-neutral surface; a C ABI shim over it is not in this node.
- **A panel whose mode is not available is kept, not dropped.** It is restored as a dormant placeholder and saved back byte for byte (check d6), so a layout never loses work because one crate group failed to load.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test shell`; a program goes through `broadsword run shell -- cargo run --offline --release --example <name> -- <flags>`. Programs run with the project folder as their working folder, so a fixture path such as `tests/fixtures/...` is relative to the `shell` repo (or the task worktree of it).
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test therefore looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own. Each program prints one summary line with its fields in a fixed order, so one `contains` string can pin several values at once.
- `python -I scripts/node_check.py 1.5 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only `last line == X` and `contains X`; every other `PASS:` text is "judge by hand".
- A check marked (human) needs Lazlo: never run by an agent and never counted as passed until Lazlo says so. A check marked (quiet board) is timing: run it only while no build, test or review is running (`broadsword status`), and rerun it rather than average over a busy board. A check marked (desktop) needs an interactive, logged-in Windows desktop; with none it fails loudly and is never skipped.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when line 1: a docked layout saves and restores exactly

"Exactly" is defined so it can be checked: (1) the saved file, loaded and saved again, is byte-identical; (2) the restored dock tree is structurally equal to the original (same nodes, same order, same panel ids, kinds and state bytes); (3) for a given window size the restored panels get the same pixel rectangles as before, to the pixel. To make (3) exact and not "close", split ratios are stored as integers (fixed point, 1/65536 of the parent's extent) and rectangles are computed with integer arithmetic only. A float ratio printed and parsed back could differ in the last bit and move a panel edge by a pixel at some window size.

**d1 Dock edits keep the tree valid and the rectangles are exact.** Tests: every edit (split, tab, move, close, resize) keeps the tree valid (no empty split, no duplicate panel id, every ratio inside 1..65535); for known trees at known sizes the rectangles equal hand-worked values and tile the window with no gap and no overlap.
```check d1
build/bin/broadsword.exe test shell > scratch/n15-d1.txt 2>&1
PASS: contains test dock_rects_exact_integer_math ... ok
```
The same run must also print `test dock_edits_keep_tree_valid ... ok`; a reviewer reads both lines in the file.

**d2 The golden layout file round-trips byte for byte.**
```check d2
build/bin/broadsword.exe test shell > scratch/n15-d2.txt 2>&1
PASS: contains test layout_golden_round_trip_byte_identical ... ok
```
The test parses `tests/fixtures/layout_v1.txt` (written by hand: three modes, nested splits, tab stacks, a dormant panel, every field), writes it back and compares bytes; it also requires the parsed tree to equal a tree built in code.

**d3 A bad layout file is a named error, never a partial layout.**
```check d3
build/bin/broadsword.exe test shell > scratch/n15-d3.txt 2>&1
PASS: contains test layout_rejects_bad_input ... ok
```
Cases, each a named error: empty file; unknown `schema=` version; a ratio of 0, 65536, negative or not an integer; a duplicate panel id; a split with fewer than two children; a CR or a lone LF inside a field; a state blob with bad hex; a Windows path or `..` in any field; a nesting depth over the file's stated limit. A layout that fails to load leaves the current layout unchanged.

**d4 1000 random layouts restore exactly (property test as a program).** The program builds 1000 dock trees from a seeded generator (3 modes, up to 20 panels and depth 6 each), applies random edits, saves, loads, saves again, and compares bytes, structure and rectangles at three window sizes (1280x720, 1920x1080, 3840x2160).
```check d4
build/bin/broadsword.exe run shell -- cargo run --offline --release --example layout_roundtrip -- --trees 1000 --seed 1 > scratch/n15-d4.txt 2>&1
PASS: contains layout_roundtrip: ok trees=1000 bytes_identical=1000 trees_equal=1000 rects_equal=1000
```
Threshold reason: exact by definition (1000 of 1000). 1000 trees is enough to reach every edit kind at every depth many times with a run of a few seconds; the three sizes are common monitor resolutions, and 3840 is large enough that a rounding error in the fixed-point maths shows.

**d5 The round-trip check can fail.** `--corrupt` changes one byte of each saved file before it is loaded (within a state blob, so the file still parses).
```check d5
build/bin/broadsword.exe run shell -- cargo run --offline --release --example layout_roundtrip -- --trees 1000 --seed 1 --corrupt > scratch/n15-d5.txt 2>&1
PASS: contains layout_roundtrip: FAIL
```
Expected: `run: FAILED (exit 1)`. FAIL: `layout_roundtrip: ok` (the comparison cannot see a changed byte, so d4 proves nothing).

**d6 A panel from a mode that is not available is kept and saved back unchanged.**
```check d6
build/bin/broadsword.exe test shell > scratch/n15-d6.txt 2>&1
PASS: contains test layout_keeps_dormant_panels ... ok
```
The test loads a layout naming a panel kind no registered mode provides, requires it to appear as a dormant placeholder in its dock slot, saves, and requires the bytes of that panel's entry to be unchanged.

**d7 Layout edits undo back to the start exactly.** 10,000 seeded random dock edits, then undo of all of them, gives a layout file byte-identical to the start; redo of all gives the end file. The count copies node 0.6's own Done-when ("10,000 random edits followed by full undo returns exactly to the start state"), so the shell meets the same bar.

### Done-when line 2: the shell holds 60 fps with 20 panels open

A frame here is: take the frame's input (replayed from a recorded event log), run layout, ask all 20 panels for their draw lists, paint them into a 1920x1080 RGBA framebuffer in software, and present (to an offscreen buffer in the headless bench, to a window in d13). "Holds 60 fps" means the frame's work fits in one 60 Hz frame: **p99 frame time at most 16667 us** (1/60 s, rounded up) and **no single frame over 33333 us** (two frames: a visible hitch). These are budgets, not a published benchmark; after the first quiet-board run the node's brief records the measured p50, p99 and max here and keeps the budget unless Lazlo changes it.

The 20 panels are fixed by the seed so every run paints the same work: 4 viewports (a wireframe of a 1000-edge mesh from the core, software-drawn), 4 property inspectors (200 rows each), 4 outliners (10,000 items, only visible rows drawn), 4 logs (10,000 lines, scrolled one line per frame), 2 toolbars and 2 timeline strips. Reason: one of each heavy kind an editor shows, sized like a real scene, with a scrolling panel so nothing can be cached between frames.

**d8 Every panel is really painted.** A frame with 20 panels calls each provider once, paints 20 non-empty draw lists, and the framebuffer hash differs from a frame with any one panel removed.
```check d8
build/bin/broadsword.exe test shell > scratch/n15-d8.txt 2>&1
PASS: contains test frame_paints_every_panel ... ok
```

**d9 The frame timer sees a known delay.** With a fake clock the measured frame time equals the injected delay exactly; with the real clock a panel that busy-waits 5000 us is measured at 5000 us or more.
```check d9
build/bin/broadsword.exe test shell > scratch/n15-d9.txt 2>&1
PASS: contains test frame_timer_detects_known_delay ... ok
```
Busy-wait, not sleep: a Windows sleep rounds to the timer tick (about 15.6 ms by default).

**d10 The headless bench holds 60 fps with 20 panels.** 600 frames (10 seconds at 60 Hz), after 60 warm-up frames that are not counted.
```check d10
build/bin/broadsword.exe run shell -- cargo run --offline --release --example shell_bench -- --panels 20 --frames 600 --size 1920x1080 --seed 1 --atlas tests/fixtures/atlas_box_8x16_v1.pgm --p99-max-us 16667 --max-frame-us 33333 > scratch/n15-d10.txt 2>&1
PASS: contains shell_bench: ok panels=20 frames=600 panels_painted=12000
```
(quiet board.) The full line is `shell_bench: ok panels=20 frames=600 panels_painted=12000 p50_us=<n> p99_us=<n> max_us=<n> fb_hash=<hex>`; the program exits 0 only if p99 and max are within the flags and every frame painted 20 panels (20 x 600 = 12000). Every threshold flag is required; a missing one is a usage error (exit 2). Text uses the glyph atlas file named by `--atlas` (format in section 5). The fixture is an atlas of solid 8x16 boxes: it has exactly the blit cost of a real 8x16 atlas, so the timing is fair, but it is not real text. Real fonts are node 1.4's and are run with 1.4's atlas file through the same flag when 1.4 exists (section 8, R3).

**d11 The bench can fail.** Same run with an impossible budget.
```check d11
build/bin/broadsword.exe run shell -- cargo run --offline --release --example shell_bench -- --panels 20 --frames 600 --size 1920x1080 --seed 1 --atlas tests/fixtures/atlas_box_8x16_v1.pgm --p99-max-us 1 --max-frame-us 33333 > scratch/n15-d11.txt 2>&1
PASS: contains shell_bench: FAIL p99
```

**d12 The bench holds 60 fps while switching modes, and never copies core data.** Every 10th frame the bench switches to the next of three modes (60 switches in 600 frames); each mode has its own 20-panel perspective.
```check d12
build/bin/broadsword.exe run shell -- cargo run --offline --release --example shell_bench -- --panels 20 --frames 600 --size 1920x1080 --seed 1 --atlas tests/fixtures/atlas_box_8x16_v1.pgm --p99-max-us 16667 --max-frame-us 33333 --mode-cycle 10 > scratch/n15-d12.txt 2>&1
PASS: contains shell_bench: ok panels=20 frames=600 panels_painted=12000 mode_switches=60 core_copies=0
```
(quiet board.) `core_copies` counts every call on the core handle that would copy, snapshot or serialize core data; the product intent says a mode switch makes none.

**d13 The windowed shell holds 60 fps on the desktop.** The same 20 panels in a real window, presented each frame, for 10 seconds.

## 2. Home

**A new repo, `projects/shell`, crate `shell` (library, Rust 2021, std only), created by brief S1.** It is its own Git repo, ignored by the Broadsword repo, like `projects/crash-sim` and `projects/render` (`broadsword.toml`, `projects_dir`), with its own empty `[workspace]` table so it does not join the Broadsword workspace. Creating the repo is a step for Lazlo to approve (a new repo).

Under ADR 0001 (option a, accepted): **no Cargo dependency (path or git) on another repo**; file formats are the contract. The crate's dependency tables are empty (check d19), it never links into `projects/foundation`, `projects/render`, `projects/crash-sim` or any other node's repo, and nothing here needs a new ADR to be built as planned.

**What that costs, and the ADR 0001 triggers this node fires.** The shell is the node where the product intent and ADR 0001 (a) collide, so the collision is named now:

- **Trigger 1** ("a second project must run ... as a library") **fires for every prerequisite.** A live editor needs window input (1.1), text (1.4), property descriptors (1.6) and commands (0.6) in process, and it needs the shared core itself in process to meet "same live data, no export or import". Under (a) this node can only use their *file* contracts: 1.1's event log (replayed input), a glyph atlas file (text), and its own interfaces (section 3). The move that lifts this is ADR 0002 (one workload repo with a Cargo workspace, ADR 0001 option d2), which ADR 0004 (Proposed, not accepted) maps as group `W/shell`. Both are Lazlo's decisions; this plan does not assume them.
- **Trigger 2** ("a third Rust project needs the same ...") **fires with brief S10**: the windowed example needs hand-declared Win32 window and present code (`StretchDIBits`), which render's `src/window.rs` already has and node 1.1's planned `window-input` crate will also have. Under (a) S10 keeps its own copy (option (a) accepts per-repo copies); the third copy is the trigger, and it is recorded, not hidden.

So the plan is split in two on purpose. **Briefs S1 to S9 need no other node's code**: the dock tree, layout format, modes, panel protocol, themes, painting and the headless bench are pure data and std-only software, and they define the shell's interfaces in a form any later home can keep. **Only S10 touches the OS**, and only through its own copy. The step from "shell over interfaces and files" to "shell over the live core and live 1.1/1.4/1.6/0.6" is the ADR 0002 move plus a wiring brief, outside the 10 briefs here (section 8, R1).

**Layers inside the crate** (so a mode never depends on Win32 and a test never needs a window):

1. **Data:** `DockTree`, `Panel`, `PanelId`, `PanelKindId`, `ModeDescriptor`, `Theme`, the layout and theme file formats, the panel protocol encoding. Std only, portable, no `unsafe`.
2. **Shell logic:** mode registry and switching, dock edits and their undo stack, frame loop, draw-list painting into a framebuffer, the frame timer.
3. **Services the shell consumes, as traits** (`src/services.rs`): `CoreAccess` (the shared core: read by id, apply an edit, current revision; every method that would copy is counted, check d15), `TextService` (measure and lay out a glyph run from an atlas), `InputSource` (events per frame, from a replayed log or a window), `PropertySource` (field descriptors for the inspector), `CommandSink` (apply and revert). Each trait takes and returns only protocol-encodable data, so the later real implementations (core 2.4/0.5, 1.4, 1.1, 1.6, 0.6) slot in without changing the shell.
4. **Windows glue:** `src/win32.rs`, `cfg(windows)`, used only by `examples/shell_live.rs`.
