Every program, flag, test and fixture named below is created by a brief in section 7 and is not real until that brief merges. Node (CAPABILITY_ROADMAP.md, Part 5): *UI framework and editor shell.* Build: widgets, docking panels, themes, viewports, editor shell. Needs: 1.1, 1.4, 1.6, 0.6. Done when: a docked layout saves and restores exactly; the shell holds 60 fps with 20 panels open. Broadsword stage: 1. ROADMAP.md status today: not started.

**Product intent this plan is built around** (Lazlo, 2026-11-20, `state/backlog/t-20261120-013957.md`, "Product intent"): one unified tool. Picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared, live core data model, with no export or import. Modes are switchable plugins over a stable core API, loaded on selection; no mode depends on another mode's internals; the core API stays language-neutral (C ABI or FFI-friendly, serializable data). **The shell is the one place that switches modes**, so its design follows from that:

- **The shell owns no core data.** It holds a `CoreHandle` (an opaque handle to the one shared core) and passes it to every panel. A panel stores *references* into the core (object ids, a selection, a camera), never a copy of core data. Switching modes changes which panels and tools are active; it never copies, exports or reloads core data (check d15).
- **A mode is a registered descriptor, plain data:** `ModeDescriptor { id, name, group, panel_kinds: [PanelKindId], tool_ids }`. The crate group behind a mode is activated the first time the mode is selected (check d16), which is the shell's half of "loaded on selection"; dynamic loading and hot reload are node 0.7's.
- **Each mode has its own perspective:** a dock tree of panels. The layout file holds every mode's perspective plus the active mode, so a layout saves and restores across modes, and switching mode swaps the active perspective only.
- **A panel is data plus a provider.** `Panel { id: PanelId, kind: PanelKindId (a string such as "render.viewport"), state: versioned bytes, view: core references }`. The mode that owns the kind supplies a provider; the shell never knows a mode's types.
- **Panels talk to the shell only in plain messages** (the panel protocol, section 2): input in, a draw list out (rectangles, glyph runs, images, as integers and bytes). The shell does all painting. Because the messages have a byte encoding (check d17), a mode written in another language later needs only that encoding, not a Rust type. That is the language-neutral surface; a C ABI shim over it is not in this node.
- **A panel whose mode is not available is kept, not dropped.** It is restored as a dormant placeholder and saved back byte for byte (check d6), so a layout never loses work because one crate group failed to load.

**Second product intent** (Lazlo through the coordinator, 2026-11-20): the tool is "every build tool in one" at its base, UI polish later, and **a base that others can add onto**. So the boundary the shell switches between is also a **public extension API**:

- **Third parties register modes, panels and tools** exactly as first-party crate groups do. There is one registration path: built-in modes register through the same descriptors and messages a plugin sends, so the public API is never a second-class copy (checks d22, d23).
- **A stable, versioned plugin interface with a C ABI** (`include/broadsword_plugin.h`, `docs/PLUGIN_ABI.md`), so plugins can be written in any language that can export C functions. Everything that crosses it is panel-protocol bytes (d17) plus a few C functions; no Rust type crosses. The ABI has a major and minor version and size-prefixed structs; its struct layouts are frozen by a test (d21), and a plugin with the wrong major version is refused before any of its code runs past the entry point.
- **Isolation, so a bad plugin cannot corrupt core data.** (1) A plugin never holds a pointer or a mutable reference into the core: it reads and edits only by sending protocol messages, and every edit goes through the core API's **checked operation** (`CoreAccess::apply_checked`: validate the whole edit, then apply it atomically or not at all, with a named error). (2) **A plugin loaded through the C ABI runs in its own host process** (`plugin_host`), talking to the shell over pipes. A panic in a plugin's `extern "C"` code aborts only that process (Rust aborts on a panic that reaches an `extern "C"` boundary), and a crash such as an access violation does the same, so both are contained: the shell reports the plugin by name and reason, its panels become failed placeholders, other panels keep painting, and the core state stays valid and unchanged. (3) A plugin call that does not answer within a deadline is treated as hung: the host is killed and reported. (4) Malformed bytes, a hijacked id (a plugin claiming a mode or panel kind another owner registered) and invalid edits are refused.
- **A check that deliberately misbehaving plugins are refused or contained** (d24, d25), with a negative control (d26).
- Rust crate groups linked into the shell (first-party, trusted) run in process; the shell wraps every call into them in `catch_unwind` so a Rust panic there is also contained and reported (d23). They still edit the core only through `apply_checked`.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test shell`; a program goes through `broadsword run shell -- cargo run --offline --release --example <name> -- <flags>`. Programs run with the project folder as their working folder, so a fixture path such as `tests/fixtures/...` is relative to the `shell` repo (or the task worktree of it).
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test therefore looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own. Each program prints one summary line with its fields in a fixed order, so one `contains` string can pin several values at once.
- `python -I scripts/node_check.py 1.5 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only `last line == X` and `contains X`; every other `PASS:` text is "judge by hand".
- A check marked (human) needs Lazlo: never run by an agent and never counted as passed until Lazlo says so. A check marked (quiet board) is timing: run it only while no build, test or review is running (`broadsword status`), and rerun it rather than average over a busy board. A check marked (desktop) needs an interactive, logged-in Windows desktop; with none it fails loudly and is never skipped.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when line 1: a docked layout saves and restores exactly

"Exactly" is defined so it can be checked: (1) the saved file, loaded and saved again, is byte-identical; (2) the restored dock tree is structurally equal to the original (same nodes, same order, same panel ids, kinds and state bytes); (3) for a given window size the restored panels get the same pixel rectangles as before, to the pixel. To make (3) exact and not "close", split ratios are stored as integers (fixed point, 1/65536 of the parent's extent) and rectangles are computed with integer arithmetic only. A float ratio printed and parsed back could differ in the last bit and move a panel edge by a pixel at some window size.

**d1 Dock edits keep the tree valid and the rectangles are exact.** Tests: every edit (split, tab, move, close, resize) keeps the tree valid (no empty split, no duplicate panel id, every ratio inside 1..65535); for known trees at known sizes the rectangles equal hand-worked values and tile the window with no gap and no overlap.
```check d1
build/bin/broadsword.exe test shell > scratch/n15-d1.txt 2>&1
PASS: contains test dock_rects_exact_integer_math ... ok
```
The same run must also print `test dock_edits_keep_tree_valid ... ok`; a reviewer reads both lines in the file.

Threshold reason: exact by definition (1000 of 1000). 1000 trees is enough to reach every edit kind at every depth many times with a run of a few seconds; the three sizes are common monitor resolutions, and 3840 is large enough that a rounding error in the fixed-point maths shows.

### Done-when line 2: the shell holds 60 fps with 20 panels open

A frame here is: take the frame's input (in the headless bench, a mouse move and a scroll per frame generated from the seed; in d13, the window's own events), run layout, ask all 20 panels for their draw lists, paint them into a 1920x1080 RGBA framebuffer in software, and present (to an offscreen buffer in the headless bench, to a window in d13). "Holds 60 fps" means the frame's work fits in one 60 Hz frame: **p99 frame time at most 16667 us** (1/60 s, rounded up) and **no single frame over 33333 us** (two frames: a visible hitch). These are budgets, not a published benchmark; after the first quiet-board run the node's brief records the measured p50, p99 and max here and keeps the budget unless Lazlo changes it.

The 20 panels are fixed by the seed so every run paints the same work: 4 viewports (a wireframe of a 1000-edge mesh from the core, software-drawn), 4 property inspectors (200 rows each), 4 outliners (10,000 items, only visible rows drawn), 4 logs (10,000 lines, scrolled one line per frame), 2 toolbars and 2 timeline strips. Reason: one of each heavy kind an editor shows, sized like a real scene, with a scrolling panel so nothing can be cached between frames.

**d8 Every panel is really painted.** A frame with 20 panels calls each provider once, paints 20 non-empty draw lists, and the framebuffer hash differs from a frame with any one panel removed.
```check d8

PASS: contains test frame_paints_every_panel ... ok
```

PASS: contains test frame_timer_detects_known_delay ... ok

The full line is `shell_bench: ok panels=20 frames=600 panels_painted=12000 p50_us=<n> p99_us=<n> max_us=<n> fb_hash=<hex>`; the program exits 0 only if p99 and max are within the flags and every frame painted 20 panels (20 x 600 = 12000). Every threshold flag is required; a missing one is a usage error (exit 2). Text uses the glyph atlas file named by `--atlas` (format in section 5). The fixture is an atlas of solid 8x16 boxes: it has exactly the blit cost of a real 8x16 atlas, so the timing is fair, but it is not real text. Real fonts are node 1.4's and are run with 1.4's atlas file through the same flag when 1.4 exists (section 8, R3).

| `bad_edit.rs` | sends edits: unknown id, NaN value, wrong type, and a batch of 9 valid edits plus 1 invalid | every edit refused with its named error; the batch applies none of its 10 (atomic) |

## 2. Home

**A new repo, `projects/shell`, crate `shell` (library, Rust 2021, std only), created by brief S1.** It is its own Git repo, ignored by the Broadsword repo, like `projects/crash-sim` and `projects/render` (`broadsword.toml`, `projects_dir`), with its own empty `[workspace]` table so it does not join the Broadsword workspace. Creating the repo is a step for Lazlo to approve (a new repo).

Under ADR 0001 (option a, accepted): **no Cargo dependency (path or git) on another repo**; file formats are the contract. The crate's dependency tables are empty (check d19), it never links into `projects/foundation`, `projects/render`, `projects/crash-sim` or any other node's repo, and nothing here needs a new ADR to be built as planned.

**What that costs, and the ADR 0001 triggers this node fires.** The shell is the node where the product intent and ADR 0001 (a) collide, so the collision is named now:

- **Trigger 1** ("a second project must run ... as a library") **fires for every prerequisite.** A live editor needs window input (1.1), text (1.4), property descriptors (1.6) and commands (0.6) in process, and it needs the shared core itself in process to meet "same live data, no export or import". Under (a) this node can only use their *file* contracts: 1.1's event log (replayed input), a glyph atlas file (text), and its own interfaces (section 3). The move that lifts this is ADR 0002 (one workload repo with a Cargo workspace, ADR 0001 option d2), which ADR 0004 (Proposed, not accepted) maps as group `W/shell`. Both are Lazlo's decisions; this plan does not assume them.
- **Trigger 2** ("a third Rust project needs the same ...") **fires with brief S10**: the windowed example needs hand-declared Win32 window and present code (`StretchDIBits`), which render's `src/window.rs` already has and node 1.1's planned `window-input` crate will also have. Under (a) S10 keeps its own copy (option (a) accepts per-repo copies); the third copy is the trigger, and it is recorded, not hidden.

So the plan is split in two on purpose. **No brief here needs another node's code**: the dock tree, layout format, modes, panel protocol, themes, painting, the headless bench and the plugin ABI are pure data and std-only software, and they define the shell's interfaces in a form any later home can keep. **Only S10 (window) and P2 (DLL loading in the host process) touch the OS**, each through its own hand-declared functions. The step from "shell over interfaces and files" to "shell over the live core and live 1.1/1.4/1.6/0.6" is the ADR 0002 move plus a wiring brief, outside the 10 briefs here (section 8, R1).

**Layers inside the crate** (so a mode never depends on Win32 and a test never needs a window):

1. **Data:** `DockTree`, `Panel`, `PanelId`, `PanelKindId`, `ModeDescriptor`, `Theme`, the layout and theme file formats, the panel protocol encoding. Std only, portable, no `unsafe`.
2. **Shell logic:** mode registry and switching, dock edits and their undo stack, frame loop, draw-list painting into a framebuffer, the frame timer.
3. **Services the shell consumes, as traits** (`src/services.rs`): `CoreAccess` (the shared core: read by id, apply an edit, current revision; every method that would copy is counted, check d15), `TextService` (measure and lay out a glyph run from an atlas), `InputSource` (events per frame, from a replayed log or a window), `PropertySource` (field descriptors for the inspector), `CommandSink` (apply and revert). Each trait takes and returns only protocol-encodable data, so the later real implementations (core 2.4/0.5, 1.4, 1.1, 1.6, 0.6) slot in without changing the shell.
4. **Extension API:** `src/plugin_abi.rs` (the `#[repr(C)]` ABI structs and version rule, no `unsafe`), `src/plugin.rs` (the shell side: spawn a `plugin_host` per plugin with `std::process`, a proxy panel provider over its pipes, deadlines, failed placeholders, reports), `src/bin/plugin_host.rs` (the child: loads one plugin DLL and relays protocol bytes on stdin and stdout), `src/plugin_dll.rs` (`LoadLibraryW`, `GetProcAddress`, `FreeLibrary`; `cfg(windows)`, `unsafe`, used only by the host). The C header and `docs/PLUGIN_ABI.md` are the contract a plugin author reads.
5. **Windows glue:** `src/win32.rs`, `cfg(windows)`, used only by `examples/shell_live.rs`.

**The plugin ABI fits ADR 0001 as it stands.** A plugin is a DLL file plus a header file: it is a file contract, not a Cargo dependency, so loading a third-party plugin built anywhere fires no ADR 0001 trigger and needs no new ADR. The shell repo's own test plugins are `cdylib` examples of the shell crate, not separate repos. ADR 0004 (Proposed) puts the plugin *mechanism* in node 0.7 (`W/core`); section 3 names that overlap.

**Draft formats (each brief writes the real one down):**

- Layout (`docs/LAYOUT_FORMAT.md`, S3): first line `schema=1`, then `active=<mode id>`, then one `perspective <mode id>` block per mode, each an indented tree of `split h|v <ratio>...`, `tabs <active index>` and `panel <id> <kind> <state hex>` lines. Ratios are integers in 1/65536 of the parent (the remainder pixel of a split goes to the last child, by rule). Line ending LF only; a stated maximum depth and size.
- Panel protocol (`docs/PANEL_PROTOCOL.md`, S5): a version byte, then tagged messages, each `tag u8, length u32 LE, payload`; integers little-endian, strings UTF-8 with a length, no floats in layout-critical fields. Draw list items: `rect x y w h rgba`, `glyphs x y atlas_cell...`, `line x0 y0 x1 y1 rgba`, `image w h bytes`, `clip push/pop`.
- Atlas (`docs/ATLAS_FORMAT.md`, S8): as the fixture above; a proposal for node 1.4.
- Theme (`docs/THEME_FORMAT.md`, S7): `schema=1` then `key=value` lines in a fixed order.
- Plugin ABI (`docs/PLUGIN_ABI.md` and `include/broadsword_plugin.h`, P1): one exported entry `bs_plugin_entry(const BsHostV1 *host, BsPluginV1 *out) -> int32_t`. Every struct starts with `uint32_t abi_major, abi_minor, struct_size`. `BsHostV1` gives the plugin `send(ctx, const uint8_t *bytes, size_t len)` (its only way to reach the shell or core: protocol bytes, answered asynchronously) and `log`. `BsPluginV1` gives the shell `describe` (the plugin's `Registration`: modes, panel kinds, tools), `call(ctx, bytes, len, BsBuf *out)` and `free_buf`. Only fixed-width integers, pointers to bytes and function pointers; no Rust or C++ types. Rule: same major required; minor features negotiated; structs only grow at the end. Ids are namespaced `<vendor>.<plugin>.<name>` and the first owner of an id keeps it.
- The test core (`tests/support/test_core.rs`) carries the checked-operation contract: `apply_checked(batch)` validates every edit (id exists, type matches, value finite and in range) before applying any, and `validate()` checks the core's invariants (no dangling id, no non-finite value, revision monotonic).

**Every test must be shown able to fail** (playbook lesson 10): each brief's done check includes one mutation (named per brief in section 7), run once, shown failing, then restored. A test that fails only to compile does not count.

## 8. Risks and size

- **R1 Prerequisites not started.** 1.1, 1.4, 1.6 and 0.6 are all `not started`, and the node prompt says to stop when one is missing. Ask Lazlo before S1 whether they are waived for S1 to S10 (section 3). Cost of asking: one message. Cost of not asking: a coder that stops on its first step.
- **R2 The unified tool needs ADR 0002 before it is real.** Under ADR 0001 (a) the shell cannot hold the live core or live 1.1/1.4/1.6/0.6 in process (trigger 1, section 2). Checks d15 and d16 prove the shell's half of "same live data, no export or import" against a counting test core, which is honest and necessary but not the whole claim; the node record must say exactly that and must not claim the unified tool works. Wiring the real core and the four prerequisites in is about 4 to 6 more briefs after ADR 0002, not planned here.
- **R3 Box glyphs are not text.** d10 to d13 use a solid-box atlas with the same blit cost as a real 8x16 atlas. Real fonts at other sizes, shaping and ligatures (1.4) cost more per frame. When 1.4 exists, the same checks are rerun with `--atlas` pointing at 1.4's atlas file, and a check line for that is added here then. If shaping per frame breaks the budget, the shell caches shaped runs per panel.
- **R4 Software painting may not hold 60 fps.** 1920x1080 is about 2.1 million pixels per frame. A full clear plus 20 panels of fills and blits should fit well inside 16.7 ms on one core, but that is an estimate, not a measurement; high-DPI or 4K monitors would quadruple it. If the first quiet-board run of d10 misses, options are (in order): paint only damaged rectangles, split painting across threads (std threads; 0.4 is not needed for this), then paint through node 1.2 (GPU, `wgpu`, ADR 0003, graphics-heavy). The last one is Lazlo's call.
- **R5 Budgets are placeholders and timing is noisy.** 16667 us and 33333 us come from the 60 Hz definition, not from a measurement of this shell. d10 to d13 run only on a quiet board; if they flap there, the first step is to find the noise source (timer resolution, power plan), not to loosen the budget silently.
- **R6 GDI present has no vsync.** `StretchDIBits` can tear and gives no flip timing, so d13 measures frame work time and pacing, not photon-to-eye latency. Every output line and the node record say what is measured.
- **R7 Exactness edge cases.** A window resized below the minimum panel size, ratios at the 1/65536 limit, and the remainder rule are where "restores exactly" can break. They are named in S2's tests; restoring at a different window size gives the same ratios and therefore the same rectangles as a fresh layout at that size, which is the defined meaning of "exactly" there.
- **R8 Panel state blobs belong to modes.** The shell stores them as opaque bytes and promises only to give them back unchanged. Versioning and migrating a mode's state is that mode's job and, for layout schema changes, node 0.5's. A layout `schema=2` needs a migration from 1, written when it happens.
- **R9 A third Win32 copy (trigger 2).** S10 adds the third hand-declared Win32 window layer (render, the planned `window-input`, the shell). That fires ADR 0001 trigger 2 and is a reason for Lazlo to decide ADR 0002 before or with this node.
- **R10 The dependency rule is only partly enforced here.** `no_use_outside_crate` stops the shell from importing a mode, but "no mode depends on another mode" across crate groups is a harness check (`cargo metadata` walk) that ADR 0004 assigns to `docs/SCALING.md`. Until that exists the rule is **not yet in force** for modes.
- **R11 Brief size.** S8, S10 and P2 are the largest; S8 has a planned split (section 7). The first review of S2, S8, S10 and P2 is the most likely to fail.
- **R12 The ABI freezes early.** Once a third party builds against ABI v1, changing it costs them. The freeze test (d21) makes every change visible, but the v1 design is made before any real plugin exists. Mitigation: call v1 "preview" in `docs/PLUGIN_ABI.md` until node 0.7 and the first real external plugin have used it, and allow a v2 major with both supported for a stated period.
- **R13 Process isolation is not a security sandbox.** The host process keeps a bad plugin from corrupting core data or killing the shell; it does not stop a malicious plugin from reading Lazlo's files or using the network. Loading plugins from anyone but Lazlo needs a real sandbox (job object limits, restricted token, AppContainer) and a policy for where plugins come from. Both are Lazlo's decisions, not planned here. Until then the shell loads only plugins from a folder named by its caller, and never fetches one.
- **R14 Out-of-process panels cost frame time.** A plugin panel's draw list crosses a pipe every frame. A draw list of tens of KB per panel is small next to the 16.7 ms budget, but that is an estimate; the bench (d10) uses in-process demo panels, so no check measures plugin panels at 60 fps yet. A later check adds `plugin` panels to the bench when P2 has merged. In-process loading of C ABI plugins (faster, no crash containment) is a later opt-in for trusted plugins only.
- **R15 Overlap with node 0.7.** The plugin mechanism here may become 0.7's first part or be replaced by it (section 3). Decide before P1 so the work is not done twice.
- **R16 d22's build assumption.** If `cargo test` does not build the `cdylib` examples first, d22 and d24 need a separate build step through `broadsword run shell -- cargo build --offline --examples`, which P2's spike settles before any plugin code is written.

**Size:** 13 briefs (S1 to S10 and P1 to P3), roughly 250 lines each, about 3,200 changed lines in a new repo, plus about 3 fix rounds (the playbook expects first reviews of the trickier briefs, and of P2's process handling, to fail), so about 16 merged tasks to reach the Done-when and the extension-API checks in section 1, plus one human check (d14). On the harness's own measure (about 20 merged tasks per delivered stage) that is about 0.8 of a stage. Making the shell host the real live core and the real prerequisites is a further 4 to 6 briefs after ADR 0002 (R2); a real plugin sandbox (R13) and plugin panels in the bench (R14) are 1 to 3 more; none of these are counted here.
