## 1. Done checks as commands

### Execution contract and meaning of "matches"

Run from the Broadsword root. `broadsword` below denotes the installed
`build/bin/broadsword.exe`, not an independently built executable. Inside a task,
the orchestrator adds `--task <id>` after the project name. Never invoke cargo
outside Broadsword. Sections 7/B1-B10 create the projects, tests, examples,
subcommands, flags, configuration keys and fixtures used below.

These are prospective checks, not runnable evidence for this docs-only task.
Use the existing `scripts/node_check.py` runner outside a Broadsword job: it
understands `check <id>` fences and `contains` rules, requires exit zero, captures
output in `scratch/node-checks/1.11/`, and kills the process tree on timeout.
Supply its `--timeout` from the required `done_check_timeout_seconds` setting in
`broadsword.toml`; do not invent another duration. The redirects below give
distinct scratch names for direct runs; direct runs must receive the same
orchestrator timeout. No shell pipelines, directory changes or background jobs.
The runner's capture location takes precedence over a trailing redirect.

Each test command runs the entire suite, not a filtered test. A PASS needs its
named `test ... ok` line and exit zero; missing tests, empty output, refusals,
truncation, missing native libraries and timeouts fail. Program success markers
are emitted only after all validation and comparisons finish, never copied from
an input. Also retain labelled measurements and hashes, not only a PASS marker.

The acceptance boundary is the app's final display-referred pixel buffer,
**after** its color processing and **before** OS compositor/monitor conversion.
Reference and capture must share input bytes, dimensions, channel order, alpha
association, input ICC profile, working space, OCIO config, view/display/look,
exposure and rendering intent. Compare each app independently to the frozen
reference, not merely to each other. Physical monitor agreement is a separate
human check, not something a screenshot or identical wrong apps proves.

Threshold decisions (B2 stores them as required settings; B5 records their
independent justification):

| Setting | Proposed value and reason, not an already measured result |
| --- | --- |
| `color111_linear_abs_tol` | `0.000002`, provisional f32 arithmetic allowance against independently calculated f64 values; not a perceptual threshold. |
| `color111_reference_abs_tol` | `0.00002`, provisional allowance for the bounded SDR reference suite's ICC/OCIO float implementation differences. Must be approved against independent reference precision before acceptance. |
| `color111_display_code_tol` | `1`, maximum per-channel difference in final unsigned 8-bit RGB codes; a proposed quantization allowance, not a claim that one code is always invisible. |

Every sample must meet its bound; **zero** pixels beyond the bound is the rule,
not a mean, percentile or allowed bad fraction. The reference suite initially
covers SDR RGB matrix/TRC ICC profiles and a pinned SDR OCIO view. HDR, arbitrary
printer/CMYK profiles, proofing and arbitrary OCIO configs are not implicitly
certified by it. Report unsupported cases explicitly; expanding support requires
new reference cases and the same all-app acceptance. Lazlo approves this band;
do not silently reinterpret the roadmap as supporting every possible profile.
No timing threshold is implied by the Done-when; none of these checks requires
a quiet board. Future timing checks must be marked **quiet board**.

### 1. Linear workflow and alpha

```check cm1
broadsword test color > scratch/n111-cm1.txt 2>&1
PASS: contains test linear_workflow_matches_independent_values ... ok
```

B6 proves decode to scene-linear, linear-light compositing, and encode exactly
once against B5 values. Include transfer-function breakpoints and adjacent
representable values, primaries, neutral ramp, transparent and opaque pixels,
and premultiplied-alpha handling. Alpha is not gamma-corrected. Removing the
decode must make the encoded-midpoint case fail, not merely fail compilation.

### 2. ICC interpretation is real, not metadata-only

```check cm2
broadsword test color > scratch/n111-cm2.txt 2>&1
PASS: contains test icc_transform_matches_independent_reference ... ok
```

B7 transforms the same nonempty image under distinct B5 profiles and intent,
compares all channels to independent results within the reference tolerance,
and verifies that choosing the wrong profile fails. Profiles are applied once;
the view transform never accidentally substitutes for ICC input conversion.

### 3. OCIO view transforms and reproducibility

```check cm3
broadsword test color > scratch/n111-cm3.txt 2>&1
PASS: contains test ocio_view_matches_frozen_reference ... ok
```

B8 compares against a frozen upstream-OCIO CPU rendering with recorded release,
config and dependency hashes, view, display, look, exposure and interpolation.
An identity view is not the only fixture. Changing the look or applying the
view twice must violate the reference tolerance. Round trips supplement this
test only for invertible transforms; clipped views need not be invertible.

### 4. Hostile inputs and numerical boundaries fail closed

```check cm4
broadsword test color > scratch/n111-cm4.txt 2>&1
PASS: contains test color_boundary_rejects_invalid_without_partial_output ... ok
```

B9's direct lower-level tests cover empty/truncated/oversized images and profiles,
overflowing dimensions, duplicate/unknown fields, invalid UTF-8, CR and other
line separators in identifiers, NaN/infinity, missing config/view/intent, hostile
LUT references, Windows separators/drive paths, traversal and replaced links.
Reject before allocation or processing and before any result is published.
No fallback to identity, sRGB, a different profile or a missing library is allowed.
The accepted numeric band and its near-boundary cases are specified in section 5.

### 5. The judge itself detects a wrong or incomplete result

```check cm5
broadsword test color > scratch/n111-cm5.txt 2>&1
PASS: contains test acceptance_judge_detects_corruption_and_missing_apps ... ok
```

B4 tests the comparator directly: corrupt one pixel beyond tolerance, delete a
required app capture, duplicate an app ID, supply empty images, a NaN sample,
a stale source hash or a mismatched view. Each must return a named failure.
The ordinary test succeeds only when every injected defect is rejected. It
does not use an arbitrary nonzero process exit as evidence of correct rejection.

### 6. Capture the first real consuming app

```check cm6
broadsword run render -- cargo run --offline --release --example color_capture -- --case node111 > scratch/n111-cm6.txt 2>&1
PASS: contains color_capture: PASS app=render
```

B10 drives render's actual color-enabled output path, not a harness that calls
the color library and labels itself "render". It uses B9's file-protocol service.
It writes its capture and provenance atomically to the configured scratch
capture directory. It prints input, profile, config, service and render source
hashes, dimensions, sample count and output hash. The final marker requires a
nonempty capture and successful service exit. This is capture, not a reference
comparison; cm7 must still pass.

### 7. Every registered consuming app matches the reference

```check cm7
broadsword run color -- cargo run --offline --release --example acceptance -- --suite all-apps > scratch/n111-cm7.txt 2>&1
PASS: contains color_acceptance: PASS suite=all-apps
```

B4 creates the verifier and its `--suite all-apps` interface; B10 supplies the
first real consumer capture. Required setup: build the service and every
consumer through Broadsword on the source revisions being judged, pin their
executable hashes in the run manifest, run each real app's capture adapter, and
only then run cm7. cm6 is the first adapter command. New apps need their own
adapter briefs and commands added here before they can claim node acceptance.

The configured consumer roster must be nonempty and contain render. The
verifier requires exact set equality between the roster and current captures,
all required fixture cases per app, matching source/executable/fixture hashes,
and both float and final-code comparisons. It prints `app=<id> case=<id>
samples=<n> max_abs=<x> max_code=<n> over_limit=<n>` for every pair. Empty/missing,
extra, duplicate, stale or unsupported entries fail, including an unavailable
app: never skip it. A prior run, a different commit or the reference renderer
itself cannot stand in for a consuming app.

### 8. Coverage audit and visual review **(human: Lazlo)**

```check cm8
broadsword run color -- cargo run --offline --release --example acceptance -- --suite review > scratch/n111-cm8.txt 2>&1
PASS: (human) Lazlo confirms the audited consumer roster is complete and the reference and per-app review images agree, after cm1-cm7 pass.
```

## 2. Home

Proposed independent repo **`projects/color`**, library crate **`color`**, binary
**`color_service`**, and examples **`acceptance`** and **`make_references`**.
Its own `[workspace]` keeps it out of the Broadsword tooling workspace.
Creating/registering it is a later orchestrator action with Lazlo's approval,
not part of this file.

Accepted `docs/adr/0001-shared-core.md` option (a) governs: separate repos;
**file formats are the contract; no Cargo dependency, path or git, on another
repo without a new ADR, which is Lazlo's call. Never plan a link into
`projects/foundation`.** No scene, renderer or GPU crate is imported here.
Local scalar arrays and file buffers suffice; do not copy another repo's math
or parser implementation. The consumer invokes the pinned color service over
versioned request/result files; it does not depend on its Rust types.

The contract specifies pixels, encoding, primaries/white point, alpha association,
ICC bytes, OCIO config identity and named view selection. Node 1.9's codecs are
not needed: the harness uses a small documented float-buffer container and PPM
review images, not a cross-repo media crate. Processing occurs on linear pixels;
format decoding is outside this node.

This CPU/file service is the isolated first proof, not a promise of interactive
in-process rendering. If GPU integration needs **code** from node 1.2's repo,
or an app needs `color` as an in-process Rust dependency, stop for a new ADR.
ADR 0001 trigger 1 specifically concerns a second project's in-process sim/BSN
use; do not pretend it already authorizes arbitrary color-library sharing.
Trigger 2 applies if a third Rust project would need the same math/parser, and
trigger 3 if copied math/parser bugs must be repaired in multiple repos.
For live shared services the proposed ADR 0004 T6/product-intent migration is
also relevant; neither that proposal nor a registry wrapper grants permission
to import a workload repo. Lazlo must approve the applicable new ADR/migration
before changing this file-based boundary.

`docs/adr/0004-roadmap-repo-map.md` is **Proposed**, not Accepted. Its proposed
future home is `W/media-io` (or a shared service when multiple groups need it); do not
create W or move existing history on this plan's authority.

### Conditional native exception

OpenColorIO: mature film/VFX color-management engine, expected BSD-3-Clause,
C++ (all verify against the pinned release). It handles config-defined scene/
display/view transforms; it does **not** replace a general ICC engine.
Request its CPU processor first; no Python runtime hidden in the shipped app.
The Rust std-only alternative is a narrow hand-written matrix/transfer/LUT
subset, costing separate parser, interpolation and conformance briefs and
**not** meeting general OCIO compatibility. `palette` plus `moxcms` covers math
and ICC but does not by itself execute OCIO configs. Lazlo chooses rather than
calling that subset an OCIO wrapper.

If approved, a dedicated `ra-adr-deps` native-build task pins source checksums,
licences, toolchain, CMake options and transitive native libraries, builds OCIO
**once on this PC** using the approved Windows C++ toolchain, and records a
rebuild recipe and artifact manifest. Disable unneeded apps/Python/GPU components
where supported. Headers and binaries live in one read-only shared directory,
selected by required `native_ocio_dir`; a thin reviewed C ABI shields Rust from
C++ exceptions. Never build OCIO per worktree or search arbitrary system DLLs.
Approve DLL/static distribution and licence notices explicitly. If Little CMS
is necessary, repeat that decision/build manifest for `native_lcms2_dir`.
Missing artifacts cause a named failure, never a skipped test.

Other proposed non-std crates: `toml` for real settings/manifest parsing,
`sha2` for provenance hashes, and on Windows `windows-sys` for bounded job-object
child supervision. Expected MIT/Apache-2.0 licensing and established maintenance
must be verified for each pinned version and its closure. Registry crates get
exact pins, a committed lockfile, supply-chain/licence review and one approved
vendored shared copy with a reproducible manifest; offline builds must work in
both main checkout and a task worktree. No Cargo dependency on another repo.
Avoid adding `image`, a YAML parser or a GPU crate just for review files: std
PPM output suffices and approved OCIO parses its own configs.

**Graphics-heavy:** the initial CPU reference/service harness is not GPU-heavy.
Future GPU view/shader/LUT integration is graphics-heavy: this PC shares system
RAM and GPU memory, so **Lazlo moves it first**, before that work starts. GPU
access is not needed for the initial CPU buffer acceptance; it cannot certify
a later GPU path, which must get its own CPU-reference and two-backend checks.
No tablet, gamepad, audio interface or second PC is required. A calibrated
monitor/colorimeter would strengthen physical-display review but is a separate
hardware decision, not a requirement secretly assumed by cm8.

Network: only approved upstream source/crate/config/profile acquisition by the
orchestrator. Tests run offline and never fetch missing references. No paid
services or credentials. ICC profile and OCIO-config data licences are separate
from engine licences; B5 records redistribution permission or generates owned
fixtures instead. Nothing is downloaded by this task.

## 5. Test harness

B4 owns a strict manifest and comparison engine, B5 owns immutable independent
references, and B9 owns the single validated processing boundary. Test both that
boundary directly and every exposed service route; a main-program-only guard
is insufficient. Reference generation is separate from comparison and never
runs during acceptance. Never update a golden to the implementation's output.

| Checks | Proof and fixtures |
| --- | --- |
| cm1 | B5 decimal/f64 reference table derived independently from published sRGB equations, with derivation and precision; generated RGBA ramp/patch/alpha-edge image. Compare B6 operations, not just encode/decode round trips. |
| cm2 | Distinct owned RGB matrix/TRC ICC profiles plus frozen output from a separately pinned Little CMS reference tool, independently of the chosen production ICC engine. If production is Little CMS too, include published-equation matrix/TRC expected values so the shared engine is not the only oracle. |
| cm3 | Minimal owned OCIO config with nonidentity view and look, owned LUT, frozen upstream OCIO CPU output and final-code image. Record all processor selections. Same-engine agreement alone is insufficient: B5 also supplies analytically known matrix/transfer/LUT samples. |
| cm4 | Valid/invalid table-driven and deterministic property-style tests. Fixture parser gets huge declarations, tiny payloads, overlapping/out-of-range ICC tags, truncated LUTs, duplicate TOML keys, comments/strings resembling keys, cycle/path escape cases and half-written results. No success file survives failure. |
| cm5 | Direct comparator tests with deliberately bad nonempty buffers and malformed manifests. Disabling the per-channel comparison must cause the corruption-rejection assertion to fail; disabling roster equality must cause the missing-app assertion to fail. Mutations are not committed. |
| cm6-cm8 | Real app capture, independent golden comparison, source/fixture/executable hash checks and human roster audit. Fixtures are identical across apps; adapters capture after their own final color stage. Save float buffers plus quantized PPM review images, not screenshots containing UI. |

Accepted numeric band: finite SDR encoded RGB and alpha in `[0,1]`, RGB
matrix/TRC ICC input, the pinned view/config, and finite scene-linear values
within the approved `color111_linear_min`/`color111_linear_max` settings.
Those bounds must be chosen and justified in B5 against the fixture profile/
view matrices before B6; no unsupported HDR magnitude is accepted by accident.
Reject invalid bounds, NaN/inf, negative tolerances, empty identifiers, unknown
intent and integer multiplication overflow with named errors. Do not clamp
invalid inputs to make them valid. Permit only the documented view's final
display-range clipping; keep it separate from validation.

For accepted floats, test zero, smallest subnormal, smallest normal, largest
allowed values, transfer breakpoints and adjacent values, and near-cancelling
matrix terms against independently derived higher-precision values. Alpha zero
must not divide by zero or leak hidden RGB; alpha-one and subnormal alpha cases
need explicit expected values. Validate once at construction, then check
finiteness of all values about to be published before any output/state change.
RGB may become negative in a documented scene-linear stage; do not confuse
that with encoded-input range validation. Round-trip tests apply only within
the reversible band and never replace references.

Settings live only in Broadsword's `broadsword.toml`. B2 adds required keys,
B4/B9/B10 consume and validate them, with no defaults or hard-coded operational
paths/limits. Required keys, in addition to the tolerances and numeric bounds:

- `color111_fixture_manifest`, `color111_consumer_manifest`,
  `color111_capture_dir`, `color111_review_dir`, `color111_service_exe`;
- `color111_max_pixels`, `color111_max_profile_bytes`,
  `color111_max_config_bytes`, `color111_max_lut_bytes`,
  `color111_max_manifest_bytes`, `color111_max_output_bytes`;
- `color111_process_timeout_seconds`, `color111_pipe_wait_seconds`;
- conditional `native_ocio_dir` and `native_lcms2_dir` as approved above.

The fixture manifest names all source/reference/profile/config files and hashes;
the consumer manifest names pinned app sources/executables and expected captures.
All configured paths are root-relative and confined to their intended roots,
including Windows separators/drive letters, traversal, links and replacement
races. Resolve the root from the enclosing Broadsword configuration in both
checkout depths, not a committed `../../` assumption. Open validated files
without following replacements; deny external OCIO resource/search paths.
Byte/pixel limits apply before allocation, parse or processing.

The service protocol includes version, length, case identity and provenance.
B10 supervises children with a process-tree lifetime guard and bounded pipe
draining; tests include a child/grandchild holding pipes after its parent exits,
an oversized reply and a mid-write failure. Keep the first error visible and
refuse truncated/partial replies. Hash verification ties captures to the exact
tree being judged, not a different checkout's executable in the shared build
folder. Rebuild via Broadsword before pinning hashes. Scratch artifacts are
disposable; the orchestrator saves final evidence outside scratch after review.
Use an exclusively created per-run capture directory and unique per-app result
names; never overwrite another run's capture. Concurrent creation of the same
resolved destination must fail, not reuse stale data. B4 tests that collision
at the file-publication boundary; identity is the destination path, not a
package-name label.

## 6. Reference data

List only; no download or licence verification has occurred.

- **sRGB transfer and colorimetric equations:** ICC's sRGB interpretation,
  https://www.color.org/chardata/rgb/srgb.xalter . ICC copyright/document terms;
  verify before redistributing text. Use the equations as a cited specification,
  not copied third-party test images.
- **ICC specification and profile structure:**
  https://www.color.org/icc_specs2.xalter . ICC specification copyright/terms,
  not an assumed permissive dataset licence. B5 generates owned matrix/TRC
  profile fixtures; do not bundle arbitrary monitor/vendor profiles.
- **Little CMS independent ICC oracle:**
  https://github.com/mm2/Little-CMS . Expected MIT, verify pinned source and
  reference-tool licence. Record executable/source version, profile hashes,
  intent, flags, sample precision and command used to generate each reference.
- **OpenColorIO reference processor and configuration format:**
  https://github.com/AcademySoftwareFoundation/OpenColorIO and
  https://opencolorio.readthedocs.io/ . Expected BSD-3-Clause for source; verify
  documentation and any bundled data separately. Freeze references using a
  pinned upstream CPU tool, not this node's wrapper.
- **Optional realistic OCIO configs, not required fixtures:**
  https://github.com/AcademySoftwareFoundation/OpenColorIO-Config-ACES .
  Expected BSD-3-Clause, verify each config/LUT and ACES-derived notice before
  approval. Do not assume an ACES config's identity or licence from its filename.
- **Owned primary fixture set:** generated ramp, saturated patches, alpha edges,
  matrix/TRC profiles, minimal OCIO config/LUT and analytic value tables from
  B5. Licence: proposed MIT under this repo, subject to Lazlo's approval.
  B5's manifest records generator/tool versions, hashes, precision, licence and
  per-file provenance. This is synthetic reference data, not a published
  performance benchmark. No speed or perceptual-quality benchmark is claimed.

## 8. Risks and size

- **Rust coverage may change the architecture.** Candidate maturity/licences
  were not checked online. The Rust survey can remove the native exception;
  absence of an approved mature ICC route or OCIO exception blocks code rather
  than authorizing an inaccurate subset.
- **Proposed ADRs are not permissions.** Native/offline shared infrastructure
  and future live GPU integration may require more tasks and a new ADR. The
  isolated CPU service cannot promise interactive GPU performance or a single
  live shared core; a workspace migration remains Lazlo's decision.
- **Reference independence is incomplete without analytic cases.** OCIO versus
  OCIO mainly proves correct selection/integration; Little CMS versus itself
  has the same weakness. Keep B5's independent matrix/transfer/LUT expectations
  and deliberate wrong-profile/view/roster cases.
- **Tentative tolerances and scope need approval.** Do not tune bounds from the
  code's own output, loosen a bound on failure, average away a bad pixel, or
  call SDR buffer parity HDR/print/monitor correctness. Report measured maxima
  and the first failing case. Expanding the numeric/profile band needs new
  independent evidence.
- **"Every app" is open-ended.** Source/hash checks prevent stale captures, but
  only a current consumer inventory plus cm8 can expose an undeclared app.
  Each new app and each CPU/GPU output path adds acceptance obligations.
- **Parser/native/process surface.** ICC and OCIO inputs, transitive DLLs,
  hostile search paths, replaced links, inherited pipes and partial writes
  require central bounded validation and lifecycle tests. If this exceeds a
  small brief, split it; never defer the fail-closed cases until after shipping.
- **Size estimate:** the initial sequence has **10 brief outlines** (planning
  enumeration command output: `initial_brief_count=10`). This is a rough first
  implementation sequence, not a measured effort. Reaching Done also requires
  the prerequisite node, approval/dependency infrastructure, any size-driven
  splits and one adapter brief per additional consumer. GPU display support,
  broader ICC/HDR support and an in-process workspace migration are additional
  work, not delivered by these CPU checks. No duration, throughput or line-total
  estimate is asserted.
