Product intent this plan respects (Lazlo, 2026-11-20): one unified tool, where every mode reads and writes one shared core data model. So this node is a **platform layer under the modes**, not a mode. It holds plain data (keyframes, clips, poses, the skeleton) and pure evaluation (curves, forward kinematics, skinning, blending, IK). That is why the clip file (section 5, check a10) is versioned from its first commit.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test animation-core`; a program goes through `broadsword run animation-core -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. The programs print their results to stdout.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that lacks the named test fails.
- `broadsword run` prints its job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains".
- `python -I scripts/node_check.py 2.6 --list` lists these blocks and `--run <id>` runs one. It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text, including every `(human)` rule, is printed as "judge by hand". A negative control (a check that must fail on purpose, a12) is written `PASS: exit != 0`; its expected output line is read by hand from the saved file, and it counts only when its positive twin (a11, same example, same flags minus the fault) has passed.
- A rule starting `(human)` needs Lazlo. It is never run by an agent and never counts as passed until Lazlo says so. Checks a13 and a14 are marked for a quiet board or Lazlo's reading. For a quiet-board check, run it only while no build, test or review is running (`broadsword status`), and rerun it rather than averaging over a busy board.
- Checks a11 to a14 need the rigged sample file. That file is a step for Lazlo (section 4, decision D2), not a file any brief creates. Until it exists, those four checks report FAIL, which is the correct result for a missing input.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when line 2: walk and run blend smoothly

**a1 Keyframes hit their keys exactly.** At every key time the curve returns the key's value, with no tolerance.
```check a1
build/bin/broadsword.exe test animation-core > scratch/n26-a1.txt 2>&1
PASS: contains test keyframes_hit_keys_exactly ... ok
```
Reason: the keys are the input, so the output at a key is the input value; exact equality is the correct test.

**a2 Curve easing matches reference values.** Cubic Hermite and Bezier easing at t = 0, 0.5 and 1 must match values worked out by hand from the Hermite basis functions (the test comment shows the arithmetic).
```check a2
build/bin/broadsword.exe test animation-core > scratch/n26-a2.txt 2>&1
PASS: contains test curve_matches_reference_values ... ok
```
Tolerance: 1e-9 on f64 (estimate; the arithmetic at those t values is exact to far better, so 1e-9 only absorbs rounding in the test's own constants).

**a3 Quaternion slerp is unit length and takes the short way round.** Checked on a seeded grid of pairs of rotations, including pairs more than 180 degrees apart.
```check a3
build/bin/broadsword.exe test animation-core > scratch/n26-a3.txt 2>&1
PASS: contains test slerp_is_unit_and_shortest_path ... ok
```
Tolerance: 1e-6 on unit length (estimate, f32 rounding over one normalisation). The grid is seeded, so it is exhaustive over the chosen grid, not random.

**a4 Skinning matches a hand-computed three-bone chain.** Forward kinematics and linear blend skinning on a three-bone chain at one pose must match numbers worked out on paper (the test comment has them).
```check a4
build/bin/broadsword.exe test animation-core > scratch/n26-a4.txt 2>&1
PASS: contains test skinning_matches_reference_chain ... ok
```
Tolerance: 1e-6 metres (estimate, f32 rounding over three multiplications of joint transforms).

**a5 Blend weight 0 is the walk and weight 1 is the run.** The test blends two synthetic clips and requires the output pose to equal each clip's own pose at the two ends.
```check a5
build/bin/broadsword.exe test animation-core > scratch/n26-a5.txt 2>&1
PASS: contains test blend_weight_zero_is_walk_one_is_run ... ok
```
Reason: the endpoints are definitional; a failure here means the blend is wired wrong, not that a threshold is off.

**a6 The blend is continuous.** The test sweeps the weight from 0 to 1 in 1000 steps and requires the largest change in any joint's angle between two steps to stay under the budget.
```check a6
build/bin/broadsword.exe test animation-core > scratch/n26-a6.txt 2>&1
PASS: contains test blend_is_continuous ... ok
```
Budget: 5 degrees per step (estimate). A sweep of 1000 steps over a unit weight spreads a full walk-to-run change over 1000 steps, so any single step above 5 degrees is a jump, not a blend. The budget is replaced with a measured value after the first run on the real sample clips (risk R4).

**a7 Two-bone IK reaches its target.** The analytic two-bone solver must put the end joint within 1e-5 metres of every reachable target on a 21 by 21 grid (seeded, exhaustive over the grid).
```check a7
build/bin/broadsword.exe test animation-core > scratch/n26-a7.txt 2>&1
PASS: contains test ik_two_bone_reaches_target ... ok
```
Reason: the two-bone solution is closed form (law of cosines), so the error is rounding only; 1e-5 m is 10 micrometres, far below anything a viewer shows (estimate).

**a8 Foot IK plants the feet on slopes.** On a synthetic heightfield with slopes of 0, 10, 20 and 30 degrees, the foot joint's height above the ground after foot IK must be within 0.005 m of the ground at each step of a walk.
```check a8
build/bin/broadsword.exe test animation-core > scratch/n26-a8.txt 2>&1
PASS: contains test foot_ik_plants_on_slope ... ok
```
Budget: 5 mm (estimate). Reason: a foot 5 mm off the ground is at the edge of what a viewer reads as floating or sinking at character scale. Slope angles 0 to 30 degrees are the range of the walk the node must handle (estimate; Lazlo may widen it). The heightfield is synthetic, so no scene (2.4) is needed for this check.

**a11 The example blends walk and run on the rigged sample.** `character_blend` loads the sample, blends walk and run for 10 seconds, applies foot IK on a slope, and prints a summary line. This check needs the sample (section 4, D2).
```check a11
build/bin/broadsword.exe run animation-core -- cargo run --offline --release --example character_blend -- --character shared/samples/rigged-sample.gltf --seconds 10 > scratch/n26-a11.txt 2>&1
PASS: contains character_blend: ok
```
`shared/samples/rigged-sample.gltf` is a placeholder for the sample Lazlo picks; the real path is written into this file when the sample is chosen. The program prints `character_blend: ok blend_max_step_deg=<n> foot_max_err_m=<n> clips=2` and exits 0 only if the a5 and a6 budgets and the a8 budget hold on the real clips, and the sample has both a walk and a run clip. Otherwise it prints `character_blend: FAIL <reason>` and exits 1.

**a12 The blend check can fail.** The same run with `--corrupt-blend`, which doubles every blend weight before evaluation.
```check a12
build/bin/broadsword.exe run animation-core -- cargo run --offline --release --example character_blend -- --character shared/samples/rigged-sample.gltf --seconds 10 --corrupt-blend > scratch/n26-a12.txt 2>&1
PASS: exit != 0
```
Expected: the run exits non-zero and the saved file contains `character_blend: FAIL blend` (read by hand). FAIL: `character_blend: ok` (the summary cannot see a wrong blend). Valid only while a11 passes with the same example and sample.

**a13 Per-frame cost fits half a 60 Hz frame (quiet board).** `character_blend --bench` evaluates 100 characters per frame for 600 frames and reports the 99th-percentile frame time.
```check a13
build/bin/broadsword.exe run animation-core -- cargo run --offline --release --example character_blend -- --character shared/samples/rigged-sample.gltf --bench --characters 100 > scratch/n26-a13.txt 2>&1

It is a budget, not a published benchmark, and it is replaced after the first quiet-board run (risk R5).

## 2. Home

**A new repo, `projects/animation-core`, crate `animation-core` (library, Rust 2021, std only), created by brief A1.** Like `projects/window-input` in `docs/nodes/1.1.md`, it is its own Git repo, ignored by the Broadsword repo (`broadsword.toml`, `projects_dir = "projects"`, line 16). It is registered as a project by its own `Cargo.toml` with an empty `[workspace]` table, so it does not join the Broadsword workspace.

Under ADR 0001 (option a, accepted, `docs/adr/0001-shared-core.md`):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` stays empty (check a15). The crate does not depend on `projects/render`, `projects/crash-sim` or `projects/foundation`, and the plan never links into `projects/foundation`, even though `projects/foundation/docs/quat.md` and `transform.md` exist for node 0.2 (ROADMAP.md row 0.2).
- **Math is a fresh copy, written by brief A2 with its own reference tests.** ADR 0001 measured the duplication (crash-sim `Vec3` in `f64`, render `Vec3` and `Mat4` in `f32`). This crate needs a `Quat`, a `Vec3` and a `Mat4`, so option (a) accepts a third copy here. Option (a) also has a trigger, see below.
- **The contract between repos is a file.** `docs/FORMAT.md` (brief A3) describes the clip file. A timeline (1.8) or a rigging mode (3.9) reads and writes clips through that file, not through a link.

**ADR 0001 triggers this node will fire, named now:**

- **Trigger 2** ("a third Rust project needs the same ...", as quoted in `docs/nodes/1.1.md` section 2) fires when brief A2 writes the math. This crate becomes the third project with its own `Vec3`. The plan proceeds with option (a) only if Lazlo accepts that the copy is the decision for now (decision D3, section 4). If he wants the shared math first, the move is ADR 0002 (option d2, Lazlo's decision), and A2 waits.
- **Trigger 1** ("a second project must run ... as a library") fires when node 2.4 (the scene) or node 1.8 (the timeline) must call this crate's evaluation in-process, for example to evaluate a live pose inside a viewport. Both are planned in other repos, and a live pose cannot go through a file at 60 Hz. The move is ADR 0002, not planned here. Until Lazlo decides, the other modes can only use recorded clips and poses from files.

**Scene dependency.** Node 2.4 owns the scene's transforms and node hierarchy, and it owns glTF import for scenes (CAPABILITY_ROADMAP.md line 152). This node needs a joint hierarchy and a skin, so brief A8 reads the skin and the animation channels from glTF itself. That duplicates part of 2.4's job, on purpose, to avoid a cross-repo link. If 2.4 later exposes its importer as a file format only, A8 can be replaced without changing the evaluation code. ADR 0001 trigger 1 would fire if the two must share one in-process type. Decision D4 (section 4) asks Lazlo to confirm this split.

**Fit with the product intent.** The crate has three layers, so no mode depends on another and no test needs a window or a GPU:

1. **Data:** `Vec3`, `Quat`, `Mat4` (`src/math.rs`), `Curve` and `Key` (`src/curve.rs`), `Clip` (`src/clip.rs`), the clip file (`src/clipfile.rs`), the skeleton (`src/skeleton.rs`). Std only.
2. **Evaluation:** pure functions from data to poses: curve sampling, forward kinematics and skinning (`src/skin.rs`), blending (`src/blend.rs`), two-bone IK (`src/ik.rs`), foot IK on a heightfield (`src/foot_ik.rs`).
3. **Import:** `src/gltf_import.rs` reads a file into layer 1. Nothing in layers 1 and 2 knows where a file came from.

## 5. Test harness

| Check | Kind of test | What it compares against |
|---|---|---|
| a1, a2 | exact key-time tests; hand-worked Hermite values | the key values themselves; the basis functions at t = 0, 0.5, 1 |
| a3 | seeded grid over pairs of rotations, including pairs more than 180 degrees apart | unit length; the shorter of the two arcs |
| a4 | a three-bone chain with joint angles chosen so the answer is easy on paper | the paper values in the test comment |
| a5, a6 | two synthetic clips (one walk-like, one run-like) blended over 1000 weight steps | each clip's own pose at weight 0 and 1; the 5 degree step budget |
| a7 | seeded 21 by 21 grid of targets, every reachable one | the target position, to 1e-5 m |
| a8 | synthetic heightfield with slopes 0, 10, 20, 30 degrees, a walk of fixed steps | the ground height under each foot, to 5 mm |
| a9 | hand-written glTF fixture (three joints, one skin, two animations) | the counts in `rigged_min.expected.txt` |
| a10 | write, parse, compare; a second file with a version this crate does not know | byte identity with `tests/fixtures/clip_v1.txt`; a named error |
| a11, a12 | the sample (D2): a real run, and the same run with a fault injected | the budgets of a6 and a8 on real clips; the negative control must exit non-zero |
| a13 | the sample, 100 characters, 600 frames, quiet board | the 8333 us frame budget (estimate, section 1) |
| a14 | the sample, one 30-second run written to CSV | Lazlo's reading (human) |
| a15 | structure test reading `Cargo.toml` | an empty dependency list |

**Why these kinds of test.** Curves, Hermite values and the two-bone IK are closed-form, so exhaustive or seeded-grid tests beat random fuzzing: the input spaces are small and every value can be checked. The blend and the foot IK are judged on the real sample (a11 to a13) because a synthetic clip cannot show a real hip or knee jump. Timing (a13) and the human judgement (a14) are kept apart from the automated checks, as in 1.1.

**Fixtures to make (all text, small, committed in the new repo).**

- `tests/fixtures/clip_v1.txt`: one clip with two curves and a few keys of each kind, written by hand once (brief A3). Its header line carries the version.
- `tests/fixtures/rigged_min.gltf` and `rigged_min.expected.txt`: three joints, one skin, two animations named `walk` and `run`, a few keys each, written by hand (brief A8). The expected file lists the counts a correct import must report.
- No binary fixture is committed. The rigged sample is read from `shared/samples/` and is never copied into the repo.

**Mutation steps.** Each brief whose check can pass by compiling alone includes a mutation step: change one line, show the named test fail, then restore it. A3 (the curve divides by 2 instead of the interval, and the Hermite test must fail), A4 (the skinning applies the parent after the child, and the chain test must fail), A5 (the blend returns weight 1 for every input, and the endpoint test must fail), A7 (the foot target uses the wrong sign, and the slope test must fail).

**Format of the clip file.** Draft, to be written in `docs/FORMAT.md` by A3: a first line `schema=1`, then one row per key: `clip,curve,joint,time_s,value,kind`. Times and values are fixed decimal so a round trip is byte identical. Unknown `schema` values are a named error.
