Node (CAPABILITY_ROADMAP.md line 157, Part 5): *2D constraint solver and sketcher.* Build: geometric constraints (coincident, tangent, parallel, distance, angle) with degrees-of-freedom (DOF) reporting, and a sketch UI. Needs: 2.8, 1.3. Done when: a 30-constraint sketch solves instantly and correctly reports over- and under-constrained states. Broadsword stage: 8 (ROADMAP.md line 39). ROADMAP.md status today: not started.

**Decision for Lazlo (section 8, R2):** the Build line names five constraint kinds. This plan adds a sixth, `Fix` (one point pinned to an absolute x and y). Reason: a 2D sketch has three rigid motions (two translations and one rotation) that none of the five kinds removes. Without an absolute anchor a 30-constraint sketch can never reach DOF 0, so "fully constrained" and the under-constrained count would be wrong. Cost: one enum variant and its residual, about 20 lines (estimate).

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `build/bin/broadsword.exe` is `broadsword`. Inside a task, add `--task <id>` after the project name.
- Tests go through `build/bin/broadsword.exe test constraint-sketch`. Programs go through `build/bin/broadsword.exe run constraint-sketch -- cargo run --offline --release --example <name> -- <flags>`. Never call cargo directly.
- Every command writes its output to `scratch/n29-<id>.txt` (`> scratch/... 2>&1`). Read the file. The suite-wide `broadsword test` has no name filter, so a check looks for its own test's `test <name> ... ok` line. A test that is missing fails the check.
- `python -I scripts/node_check.py 2.9 --list` lists these blocks. `--run <id>` runs one. It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Any rule starting `(human)` is printed as "judge by hand". Use `--run` one id at a time; never `--run --all`, because it would run the human checks.
- A rule that is a negative control is written `PASS: exit != 0`. Its positive twin (s11 for s12) must pass with the same example before the negative control means anything.
- A line after a block marked `(human)`, `(quiet board)` or `(desktop)` is a condition, not part of the rule. `(human)` checks need Lazlo and are never run by an agent. `(quiet board)` checks are timing: run them only while `broadsword status` shows no build, test or review running, and rerun them rather than average over a busy board. `(desktop)` checks need a logged-in interactive Windows desktop.
- Anything that is not PASS is FAIL, including a check that cannot run because a file, flag or test is missing.

**s12 The instant check can fail.** Same example with an impossible budget.
```check s12
build/bin/broadsword.exe run constraint-sketch -- cargo run --offline --release --example solve30 -- --constraints 30 --budget-us 1 > scratch/n29-s12.txt 2>&1
PASS: exit != 0
```
(quiet board.) Expected: `run: FAILED (exit 1)` and the saved file contains `solve30: FAIL budget` (read it by hand; `node_check.py` judges only the exit code). Reason for 1 us: a 30-constraint dense solve cannot finish in under a microsecond. If this prints `ok`, the timer or the budget comparison is wrong. FAIL: `solve30: ok` (the check cannot fail, so s11 proves nothing).

## 2. Home

**A new repo, `projects/constraint-sketch`, crate `constraint-sketch` (library, Rust 2021, std only), created by brief S1.** Like `projects/window-input` (node 1.1, section 2), it is its own Git repo, git-ignored by Broadsword (`projects_dir = "projects"`, `broadsword.toml`). It has its own empty `[workspace]` table so it does not join the Broadsword workspace. The name is a proposal (estimate of the convention, not a decision): the existing project folders are `projects/crash-sim`, `projects/render`, `projects/foundation`, and node 1.1's plan already uses `projects/window-input`.

Under ADR 0001 (option a, Accepted):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (check s1). The crate does not depend on `projects/foundation`, and this plan never links into it. The math it needs is a two-field point and a dense solve written in the crate (S2, S3).
- **Node 2.8's code is not used.** Node 2.8 (numerics core: dense linear algebra, optimisers) is planned for another repo. The solver needs a dense linear solve and a rank test on a matrix of at most about 60 by 60 (estimate: 30 constraints and 30 unknowns, plus the `Fix` rows). A small hand-written QR with a documented pivot tolerance is enough for that size (estimate). If Lazlo wants 2.8's routines instead, that is a cross-repo Cargo dependency: it needs a new ADR, which is Lazlo's call, and ADR 0001's trigger 2 (below) is the route to it.
- **The contract between repos is a file.** The sketch file (`docs/FORMAT.md`, brief S5) is how another repo's tests can load a sketch with no link to this crate. Node 3.11 (feature tree) and node 3.9 (rigging) can read sketches that way.
- **Node 1.3 (2D renderer) is not imported.** The sketch UI (S9) draws with 1.3 only after 1.3 exists, and only through an ADR 0001 decision. Until then the UI draws its own lines and points, with no link to any other repo.

**ADR 0001 triggers this node fires, named now:**

- **Trigger 1** ("A second project must run the sim or parse `.bsn` as a library", `docs/adr/0001-shared-core.md`, line 206, in the shape of that trigger). It fires when node 3.11 (parametric feature tree, which needs 2.9 and 3.10), node 3.12 (assemblies, mates) or node 3.14 (EDA) must call the live solver from their own repos. Each of those would then need `constraint-sketch` as a library, and a live sketch cannot go through a file on every drag. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2), which is Lazlo's decision and is not planned here. Until then those nodes can only use saved sketch files.
- **Trigger 2** ("A third Rust project needs the same `Vec3` or the same parser", line 208, in the shape of that trigger). It fires if node 2.8 and this crate end up sharing the dense solve. Not planned.

ADR 0004 (`docs/adr/0004-roadmap-repo-map.md`, Proposed) should list node 2.9 as `constraint-sketch`, with triggers 1 and 2 above. ADR 0004 is Proposed, so this is a request, not a fact in force.

**Fit with the product intent.** The crate has three layers, so the solver is testable with no UI, and a mode never depends on the sketch UI: (1) data: `Point`, `Constraint`, `Sketch`, the file format; (2) solving and analysis: residuals, Jacobian, solve, DOF, over- and under-constrained reporting, all pure std Rust; (3) the UI: `examples/sketch_ui.rs` (S9) and `src/ui.rs`, the only part that touches a window. Layers 1 and 2 are the surface a core API can wrap. Under the one-unified-tool intent (Lazlo, 2026-11-20, as recorded in `docs/adr/0004-roadmap-repo-map.md`), a sketch is a piece of the shared data model, and the file format is what makes that possible without a cross-repo link.
