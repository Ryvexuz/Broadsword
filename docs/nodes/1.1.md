# Node 1.1 Window and input: infrastructure plan and done checks

**Status: draft: rewrite when the node starts.** Written 2026-11-19 from Broadsword `fefe8b1`, before any code. Nothing in this file has been run: every number and Windows API fact below is a plan to be confirmed by the briefs in section 7, and the first brief that touches a fact it names must correct this file if the fact is wrong.

Node (CAPABILITY_ROADMAP.md, Part 5): *Window and input.* Build: multi-window support; keyboard, mouse, gamepad and pen input with pressure and tilt; input-latency measurement. Needs: 0.1-0.4. Done when: input latency is measured and logged; tablet pressure and tilt values are correct across the full range; two windows run at once. Broadsword stage: 1. ROADMAP.md status today: not started.

Product intent this plan respects (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared core data model. So this node is a **platform layer under all modes**, not a mode. It turns the OS's window and device messages into plain, versioned data (`InputEvent`) and never imports a mode, a scene or any core type. Routing an event to the active mode, and deciding what a window shows, is the editor shell's job (node 1.5). Because many modes will read the event type, any later change to it is a cross-shard change; that is why the file form of the events (section 5, check d14) is versioned from the first commit.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test window-input`; a program goes through `broadsword run window-input -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program. The programs write their results to stdout, not to files of their own, so a program's folder (which differs between `projects/window-input` and a task worktree) never matters.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test therefore looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 1.1 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text (including every `(human)` rule) it prints as "judge by hand". A command that exits non-zero is always a FAIL unless its rule is `exit != 0`, so a negative control (a check that must fail on purpose, d4 and d9) is written as `PASS: exit != 0`, and its expected output line is then read by hand from the saved file. That form alone would also pass if the example failed to build, so a negative control is only meaningful when its positive twin (d3 for d4, d8 for d9) has passed with the same example. A `(human)` block is marked by its rule starting `(human)`; `node_check.py` does not skip it, it would run the command, so never use `--run --all` on this node: run one id at a time and leave the `(human)` ids (d10, d13, d16) to Lazlo.
- A rule starting `(human)`, or a check marked (human), needs Lazlo and his hardware: it is never run by an agent and never counts as passed until Lazlo says so. A rule ending `(quiet board)` is timing: run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board. A rule ending `(desktop)` needs an interactive logged-in Windows desktop (windows and input injection do not work from a service, a locked screen or session 0). If there is no desktop the check fails loudly; it is never skipped.
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.

### Done-when line 1: input latency is measured and logged

Latency here means: from the moment the harness hands an event to the OS (its timestamp T0, read from the same clock as T1) to the moment the window's message handler turns it into an `InputEvent` (T1). It is not photon latency (finger to light on the screen), which needs a camera and is out of scope for 1.1 (section 8).

**d1 The latency log round-trips.** Tests prove the log format (header, one row per event, versioned) writes and parses back with identical values, and a malformed log is a named error.
```check d1
build/bin/broadsword.exe test window-input > scratch/n11-d1.txt 2>&1
PASS: contains test latency_log_round_trip ... ok
```
Threshold reason: none needed; it is an exact round trip. FAIL: the line is missing (no such test) or says FAILED.

**d2 The measurement can see a known delay.** With a fake clock the recorder must report exactly the delay put in; with the real clock a handler that busy-waits 5000 us must be measured at 5000 us or more. A recorder that always printed 0 would fail it.
```check d2
build/bin/broadsword.exe test window-input > scratch/n11-d2.txt 2>&1
PASS: contains test latency_detects_known_delay ... ok
```
Why busy-wait: `Sleep` on Windows rounds to the timer tick (about 15.6 ms unless the program raises the timer resolution), so a sleep cannot give a known 5 ms. The upper bound of the real-clock leg is not asserted here (a loaded board would make it flaky); the quiet-board run d4 covers it.

**d3 End-to-end latency is measured and logged for 2000 events.** The example injects 2000 mouse-move events at 1000 per second (1 ms apart: the polling rate of a high-end gaming mouse, so the queue sees a realistic worst case), records T0 and T1 for each, writes one `log,` row per event to its output, and prints percentiles.
```check d3
build/bin/broadsword.exe run window-input -- cargo run --offline --release --example latency -- --events 2000 --p99-max-us 8333 > scratch/n11-d3.txt 2>&1
PASS: contains latency: ok events=2000 received=2000
```
(desktop, quiet board.) The program prints `latency: ok events=2000 received=2000 p50_us=<n> p99_us=<n> max_us=<n>` and exits 0 only if every event arrived, the log has 2000 `log,` rows, and p99 is at most `--p99-max-us`. Otherwise it prints `latency: FAIL <reason> events=<n> received=<n> p99_us=<n> budget_us=<n>`, where `<reason>` is `p99` (budget exceeded), `lost` (an event did not arrive) or `rows` (log row count wrong), and exits 1. Threshold reason: 8333 us is one frame at 120 Hz, the highest common refresh rate; an input path that takes longer than a frame is visibly late. It is a **budget, not a published benchmark**, and is a placeholder: after the first quiet-board run, the node's brief replaces it with the measured p99 times 2 and records the measured value in `docs/nodes/1.1.md`.

**d4 The latency check can fail.** Same example with an impossible budget.
```check d4
build/bin/broadsword.exe run window-input -- cargo run --offline --release --example latency -- --events 2000 --p99-max-us 1 > scratch/n11-d4.txt 2>&1
PASS: exit != 0
```
(desktop, quiet board.) Expected: the run exits non-zero (`run: FAILED (exit 1)`) and the saved file contains `latency: FAIL p99` (read it by hand; `node_check.py` judges only the exit code). Reason for 1 us: a message crossing the OS queue and a window procedure cannot take under a microsecond; if this ever prints `ok`, the clock or the percentile code is wrong. FAIL: `latency: ok` (the check cannot fail, so d3 proves nothing).

### Done-when line 2: pen pressure and tilt are correct across the full range

The OS reports a pen through `WM_POINTER*` messages and `POINTER_PEN_INFO`: pressure 0 to 1024, tilt X and Y -90 to 90 degrees, rotation 0 to 359 degrees (Microsoft Learn, `POINTER_PEN_INFO`; section 6). "Full range" means every one of those integer values, not a few samples. The OS normalises every tablet to these ranges, so this checks 1.1's decoding, not the tablet's raw resolution.

**d5 Pressure decodes exactly for all 1025 values.**
```check d5
build/bin/broadsword.exe test window-input > scratch/n11-d5.txt 2>&1
PASS: contains test decode_pen_pressure_all_1025_values ... ok
```
The test loops raw 0..=1024 and requires the decoded value to equal raw / 1024 exactly (0.0, 0.5 at 512, 1.0 at 1024; 1/1024 is a power of two, so the f32 result is exact) and the sequence to be strictly increasing.

**d6 Tilt and rotation decode exactly for every value.**
```check d6
build/bin/broadsword.exe test window-input > scratch/n11-d6.txt 2>&1
PASS: contains test decode_pen_tilt_and_rotation_full_range ... ok
```
181 tilt values (-90..=90) for each of X and Y decode to the same degrees and the two axes are not swapped; 360 rotation values (0..=359) decode to the same degrees.

**d7 Out-of-range raw values are an error, not a clamp.**
```check d7
build/bin/broadsword.exe test window-input > scratch/n11-d7.txt 2>&1
PASS: contains test decode_pen_rejects_out_of_range ... ok
```
Pressure 1025 and -1, tilt -91 and 91, rotation 360 and -1 each give a named error. (A driver that sends 2048 must not silently become 1.0.)

**d8 Through the OS, a synthetic pen sweep arrives unchanged.** The example creates a window, creates a synthetic pen device, injects a pressure sweep (raw 0..=1024 at tilt 0,0: 1025 events), a tilt-X sweep (-90..=90 at pressure 512: 181 events) and a tilt-Y sweep (181 events), reads the events back from the window, and compares every one with what was injected.
```check d8
build/bin/broadsword.exe run window-input -- cargo run --offline --release --example pen_sweep > scratch/n11-d8.txt 2>&1
PASS: contains pen_sweep: ok injected=1387 received=1387
```
(desktop.) 1387 = 1025 + 181 + 181. The program prints that line only if every received value equals the injected one and no event was dropped. The OS's own integer values are compared exactly, so there is no tolerance. This is the plan's biggest unverified fact: that Windows lets a normal process inject pen input that a window receives with pressure and tilt (`CreateSyntheticPointerDevice` and `InjectSyntheticPointerInput`, Windows 10 1809 or later). Brief W8 is a spike for it first; if it does not work, d8 is replaced by d9 alone and d10 becomes the gating check.

**d9 The sweep check can fail.** The `--corrupt-pressure` flag adds 1 to every received pressure before comparing.
```check d9
build/bin/broadsword.exe run window-input -- cargo run --offline --release --example pen_sweep -- --corrupt-pressure > scratch/n11-d9.txt 2>&1
PASS: exit != 0
```
(desktop.) Expected: the run exits non-zero and the saved file contains `pen_sweep: FAIL pressure` (read by hand). FAIL: `pen_sweep: ok` (the comparison cannot see a wrong value).

**d10 A real tablet reaches the ends of its range.** Lazlo draws for 30 seconds, from the lightest touch to the hardest press, with the pen vertical and then tilted as far as it goes in each direction.
```check d10
build/bin/broadsword.exe run window-input -- cargo run --offline --release --example pen_live -- --seconds 30 > scratch/n11-d10.txt 2>&1
PASS: (human) Lazlo confirms the printed pen_live line shows contact_rows of at least 500, pressure_min at most 0.01, pressure_max at least 0.95, and tilt_x and tilt_y each spanning at least 60 degrees, and that no event carried a value outside 0..1 or -90..90.
```
(human, desktop.) The thresholds are loose on purpose: a real pen's hardware may top out a few percent below 1.0, and a person cannot reach exactly 90 degrees. They separate "the range is wired up" from "pressure stuck at one value or an axis swapped". If Lazlo's tablet fails, the first suspect is the driver (Windows Ink off), not 1.1.

## 2. Home

**A new repo, `projects/window-input`, crate `window-input` (library, Rust 2021, std only), created by brief W1.** `projects/window-input` is its own Git repo, ignored by the Broadsword repo, like `projects/crash-sim` and `projects/render` (`broadsword.toml`, `projects_dir`). It is registered as a Broadsword project by having a `Cargo.toml` with its own empty `[workspace]` table, as render does, so it does not join the Broadsword workspace.

Under ADR 0001 (option a, accepted):

- **No Cargo dependency (path or git) on another repo.** The crate's `[dependencies]` is empty (check d17). It does not depend on `projects/render`, `projects/crash-sim` or `projects/foundation`, and the plan never links into `projects/foundation`.
- **Render's `window.rs` is not reused.** `projects/render/src/window.rs` already declares Win32 by hand (about 190 lines, one window, std only). This crate declares its own Win32 functions: copying a few dozen declarations is what option (a) accepts ("keep the copies per repo"), and a path dependency would not build in task worktrees (ADR 0001, "The fact that decides most of this"). Nothing is imported from render and render is not edited.
- **The contract between repos is a file.** The event log (`docs/FORMAT.md` in the new repo, brief W3) is how another repo's tests replay recorded input; for example node 2.2's brush-engine tests can replay a recorded stroke with no link to this crate.

**ADR 0001 triggers this node will fire, so they are named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires when node 1.5 (the editor shell) or node 2.2 (the brush engine, which needs 1.1 and 2.1) must receive live `InputEvent` values in-process. Both are planned to be in other repos, and a live pen stroke cannot go through a file. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2, Lazlo's decision), which is not planned here. Until Lazlo decides, they can only use recorded event logs.
- **Trigger 2** ("a third Rust project needs the same ...") fires if render later wants to replace its `window.rs` with this crate: render and this crate would then share code, and the Win32 declarations would be the shared part. Not planned.

ADR 0004 (ra-adr-repo-map) should list node 1.1 -> `window-input` with triggers 1 and 2 above.

**Fit with the product intent.** The crate has three layers, so a mode never depends on Win32 and a test never needs a window: (1) data: `InputEvent`, `WindowId`, `Timestamp`, the event log and the latency log, all portable and std only; (2) decoding: pure functions from raw OS integers to events, with no window; (3) Windows glue: `win32.rs`, `window.rs`, `pointer.rs`, `gamepad.rs`, `inject.rs`, behind `cfg(windows)`. Layers 1 and 2 are the stable surface a core API can wrap. Modes receive events from the shell; they never open windows themselves, which keeps "no mode depends on another mode" true for input as well. Multi-window serves the "same live data, several views" idea: two windows are two views the shell can point at different modes, and an event carries only its `WindowId`.

Planned layout:

```
projects/window-input/
  Cargo.toml  README.md  .gitignore
  docs/FORMAT.md                      the event log and latency log formats
  src/lib.rs  event.rs  clock.rs      data and clock
  src/decode.rs  eventlog.rs  latency.rs
  src/win32.rs  window.rs  pointer.rs  gamepad.rs  inject.rs   (cfg windows)
  tests/structure.rs  decode.rs  eventlog.rs  latency.rs  windows.rs
  tests/fixtures/event_log_v1.csv
  examples/latency.rs  pen_sweep.rs  pen_live.rs  two_windows.rs  gamepad_dump.rs
```

Fixtures to make (all text, small, committed in the new repo): `tests/fixtures/event_log_v1.csv` (about 20 events covering every device and every field, including a pen event at pressure 0, 512 and 1024) in brief W3. No binary fixture, no recorded pen data and no download is needed.

Each test that can fail only by compilation (a missing function) is not enough: W2, W3, W4 and W8 each include a mutation step in their done check. That step changes one line (for example, divides pressure by 1023) and shows the named test failing, then restores it.

Event log format (for W3 to write down in `docs/FORMAT.md`; draft): a first line `schema=1`, a header line `seq,t_ns,window,device,kind,a,b,c,d,e` and one row per event; `t_ns` is nanoseconds since the first event, from the QueryPerformanceCounter clock; `a..e` mean different things per device and are named per kind in the document. Numbers are written with fixed decimals so a round trip is byte identical. The latency log is a separate table: `schema=1` then `seq,device,t0_ns,t1_ns,latency_ns`.

## 8. Risks and size

**Risks, with what to do:**

- **R1 Prerequisites.** 0.3 and 0.4 are not started and the node prompt says to stop if a prerequisite is missing. Ask Lazlo before starting W1 whether 0.2-0.4 are waived for 1.1 (section 3). Cost of asking: one message. Cost of not asking: a stopped coder.
- **R2 Injection may not work as planned.** Whether a normal process can inject a pen that a window receives with pressure and tilt is unverified. W8's first hour proves or disproves it. d3 and d4 do not depend on pen injection: they inject mouse-move events with `PostMessage` (W8's mouse path, which the pen spike does not test), so they still run if the pen spike fails, and W9 still follows W8 for that mouse path. If the pen spike fails, d8 and d9 go; d5 to d7 (exhaustive decode) still prove decoding, and d10 (Lazlo's real pen) becomes the only end-to-end pen proof. That is weaker, and the node must say so rather than claim d8.
- **R3 Pen history.** At high report rates, Windows can deliver several samples in one message (`GetPointerPenInfoHistory`). If W6 reads only the latest, d8's `received` count will be below `injected`. W6 must read the history. If the OS coalesces even so, the count rule in d8 is wrong, not the code: change it with a reason and a measurement, not by loosening the check silently.
- **R4 Mouse-move coalescing.** Windows merges mouse moves, so d3's `received=2000` could fail on a busy machine. W9 injects paced messages (with a clock-spin, 1 ms apart) rather than relying on cursor movement, and the check is a quiet-board check; if coalescing still happens on a quiet board, the count rule is revisited.
- **R5 Latency budget is a guess.** The 8333 us budget is a frame time, not a measurement. The first quiet-board run replaces it (section 1, d3). Until then, d3 can pass or fail for a reason unrelated to correctness.
- **R6 Measurement bias.** T0 and T1 are in the same process and the same clock, so d3 measures the OS queue plus our handler, not the pen hardware or the display. A reader could mistake it for photon latency. Every output line and `docs/FORMAT.md` says what it measures; node 2.2's "stroke lag no worse than Krita" needs a separate, camera-based method, which is outside this node.
- **R7 Desktop session.** Window and injection checks fail on a locked or headless session. The plan says "fail loudly, never skip"; the orchestrator should run them from the logged-in desktop and know this before a reviewer wonders why they fail.
- **R8 Windows-only.** Layers 1 and 2 (section 2) are portable; the rest is `cfg(windows)`. That fits "run from any drive or folder" (a Windows PC), but a Linux or macOS port is not planned and would need an ADR.
- **R9 `unsafe` growth.** About 20 to 30 hand-declared Win32 functions across W5, W6, W8 and W10, each with its invariant commented. A wrong declaration is memory-unsafe. Each brief's reviewer should read the signatures against the Microsoft page, not only the tests. The risk is accepted by precedent (render); a crate such as `windows-sys` would reduce it, and that is ADR 0003's question for Lazlo.
- **R10 ADR 0001 triggers 1 and 2** (section 2) will fire when 1.5 or 2.2 start. The plan lets them start by replaying event logs, but a live editor cannot; ADR 0002 must be decided before 1.5 can use live input.

**Size:** 10 briefs (W1-W10), roughly 250 lines each, about 2,500 changed lines in all (code, tests and the format document) in a new repo. Allow about 2 extra fix-round tasks, since the playbook expects the first review of risky work to fail (W5, W6, W8 are the likely ones). So about 10 merged tasks plus 2 fix rounds to reach the Done-when, plus 3 human checks (d10, d13, d16) that only Lazlo can run. On the harness's own measure (about 20 merged tasks per delivered stage) that is about half a stage's worth of work. The critical path is W1, then W2, then W5, then W6, then W8, then W9: six rounds, with W3, W4, W7 and W10 running beside them.
