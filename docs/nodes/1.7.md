# Node 1.7 Node graph framework: infrastructure plan and done checks

**Status: draft: rewrite when the node starts.** Written 2026-11-20 from Broadsword `fefe8b1`, before any code. Nothing in this file has been run. Every test, example, flag and number below is a plan: the program names, flags and test names in section 1 are the ones the briefs in section 7 create, and none of them exists until those briefs merge. A brief that finds a plan fact wrong must correct this file.

Node (CAPABILITY_ROADMAP.md, Part 5): *Node graph framework.* Build: typed ports, lazy cached evaluation, dirty propagation, subgraphs, and a graph editor UI, generic enough to serve shaders, procedural geometry, compositing, audio and block simulation later. Needs: 1.5, 1.6, 0.6. Done when: a 500-node graph re-evaluates only dirty nodes; a subgraph saves as a reusable asset; two different graph types (math and image) share one editor. Broadsword stage: none. ROADMAP.md status today: not started.

**Product intent this plan respects** (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared core data model; no mode depends on another mode's internals; the core API stays language-neutral so upper layers can use other languages. This node is therefore a **framework under many modes**, not a mode. It owns three things only:

1. *The graph as data*: nodes, typed ports, edges, parameters, subgraphs, and a versioned text file form (the contract with every other repo and every other language).
2. *The evaluator*: lazy, cached, dirty-tracked, with no knowledge of what a node computes.
3. *The editor model*: commands, undo, selection and a draw-list view, with no knowledge of what a graph is for.

What a node *means* (math, image, later shader, geometry, audio) lives in a **kind**: a plug-in table of node types registered with the framework. The framework never names a kind; the math and image kinds in this plan are the two proofs that it does not need to. A later mode (procedural geometry, node 3.6; compositor, 3.15; block simulation, 3.22) adds a kind and nothing else. Because a graph document is meant to live inside the shared core scene, its file form (section 5, check n10) is versioned from the first commit, and a change to it is a cross-shard change.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test nodegraph`; a program goes through `broadsword run nodegraph -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program. The programs write their results to stdout, never to files of their own, so the program's folder (which differs between `projects/nodegraph` and a task worktree) never matters.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test therefore looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 1.7 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only the rule forms `last line == X` and `contains X`; every other `PASS:` text it prints as "judge by hand".
- A rule starting `(human)` needs Lazlo and is never run by an agent and never counts as passed until Lazlo says so. A check marked (quiet board) is timing: run it only while no build, test or review is running (check `broadsword status`) and rerun it, never average over a busy board. No check in this node needs a window, a GPU, a tablet or any hardware: everything runs headless, so none is marked (desktop).
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.

### Done-when line 1: a 500-node graph re-evaluates only dirty nodes

"Dirty" is defined in the plan as: a node is dirty when its own parameters, its input wiring, or any upstream node's output may have changed since it last evaluated. "Re-evaluates only dirty nodes" has two halves, and both are checked: (a) every node that is not downstream of the edit runs **zero** times, and (b) the nodes that are downstream run **exactly once** each (not twice, which a naive diamond walk would do). The counts come from the evaluator's own counter of node-function calls (`EvalStats`), and the tests also count calls independently through a counter the test's own node kind keeps, so one counter cannot lie for the other.

**n1 Only dirty nodes run, on the 500-node graph, exact counts.** The test builds the 500-node graph (shape A: 50 independent chains of 10 nodes, each one a constant followed by nine add-constant nodes; section 5), evaluates every output once, edits the constant at the head of chain 7, and evaluates every output again.
```check n1
build/bin/broadsword.exe test nodegraph > scratch/n17-n1.txt 2>&1
PASS: contains test reeval_only_dirty_nodes_500 ... ok
```
The test requires: first pass 500 calls; second pass exactly 10 calls, all of them on chain 7, and every other chain's output unchanged and read from cache; a third pass with no edit 0 calls. Reason for these numbers: they follow from the graph's shape, so no threshold needs a source.

**n2 The same, as a program with the counts printed, on two graph shapes.** Shape A as above, and shape B (5 layers of 100 nodes, each node reading two nodes of the layer before it, wired by a fixed rule; section 5). For shape B the expected count is the size of the edited node's descendant set, computed by the program with its own breadth-first search that does not use the evaluator.
```check n2
build/bin/broadsword.exe run nodegraph -- cargo run --offline --release --example bench500 > scratch/n17-n2.txt 2>&1
PASS: contains bench500: ok shape=A nodes=500 first=500 after_edit=10 expected=10
```
The program prints one `bench500: ok shape=<A|B> nodes=500 first=<n> after_edit=<k> expected=<k>` line per shape (the rule above names shape A; the shape B line has the same form) and exits 1 on any mismatch. Shape B's `first` is 500 and `after_edit` equals `expected`, which the program computes and the check reads off the printed line: a reviewer must see both shapes' lines in `scratch/n17-n2.txt`.

**n3 The dirty check can fail.** The flag `--force-full` makes the evaluator ignore its dirty flags and recompute everything (a seam that only makes the engine do more work, never less, so it cannot hide a bug).
```check n3
build/bin/broadsword.exe run nodegraph -- cargo run --offline --release --example bench500 -- --force-full > scratch/n17-n3.txt 2>&1
PASS: contains bench500: FAIL shape=A after_edit=500 expected=10
```
Expected: `run: FAILED (exit 1)`. FAIL: `bench500: ok` with `--force-full` (the check cannot see a full recompute, so n1 and n2 prove nothing).

**n4 Re-evaluating is faster than recomputing (quiet board).** The program times the edit-and-reevaluate pass and a full recompute of shape A and fails if the incremental pass takes more than 50 ms or more than half the full pass.
```check n4
build/bin/broadsword.exe run nodegraph -- cargo run --offline --release --example bench500 -- --time --max-incremental-ms 50 > scratch/n17-n4.txt 2>&1
PASS: contains bench500: ok time shape=A
```
(quiet board.) Threshold reasons: 50 ms is three frames at 60 fps, a budget a graph edit in an editor should stay inside; it is a **budget, not a published benchmark**, and a placeholder. After the first quiet-board run, the node's brief replaces it with the measured value times 4 and records the measurement in `docs/nodes/1.7.md`. "At most half the full pass" is the weakest ratio that still shows caching works when 10 of 500 nodes run; the real ratio should be near 1/50. The counts in n1 to n3 are the correctness proof; this check only guards against a slow cache.

**n5 Incremental evaluation always equals a full recompute (property test).** 2000 seeded random graphs of up to 60 nodes, each hit with 20 random edits (change a parameter, add or remove an edge, add or remove a node; subgraph instances are covered by n13, not here); after every edit, the incremental result of every output must equal the result of a fresh evaluator on the same graph, and the count of calls must equal the number of dirty nodes the test computes itself. Seed and case count are printed on failure.
```check n5
build/bin/broadsword.exe test nodegraph > scratch/n17-n5.txt 2>&1
PASS: contains test incremental_equals_full_recompute ... ok
```
Reason: a cache bug is the classic way this framework goes wrong (a stale value that is never noticed in a hand-picked case). 2000 x 20 is about 40,000 comparisons for under a second of CPU; the number is a starting value.

**n6 Dirty propagation marks exactly the downstream set; evaluation is lazy; a shared node runs once.** Four tests in one run.
```check n6
build/bin/broadsword.exe test nodegraph > scratch/n17-n6.txt 2>&1
PASS: contains test dirty_marks_exactly_downstream ... ok
```
The same run must also print `test demand_one_output_evaluates_only_its_upstream ... ok` (asking for one output runs only the dirty nodes it depends on, and a second output's dirty nodes stay dirty), `test diamond_node_evaluated_once ... ok` and `test unchanged_graph_second_eval_zero_calls ... ok`. The reviewer reads all four lines in `scratch/n17-n6.txt`.

**n7 A deep graph does not overflow the stack.** A chain of 20,000 add-constant nodes evaluates, then a change at its head re-evaluates 20,000 nodes, without recursion limits (the evaluator walks its own work list; it never calls itself per node).
```check n7
build/bin/broadsword.exe test nodegraph > scratch/n17-n7.txt 2>&1
PASS: contains test eval_chain_20000_no_stack_overflow ... ok
```
Reason for 20,000: it is 40 times the done-when's size and far beyond what a recursive walk survives on Windows' default 1 MiB main-thread stack (a recursive walk of about 100 bytes a frame fails near 10,000); a plan-time guess, to be confirmed by the first run.

**n8 A failing node is an error, not a poisoned cache or a crash.** A node function that returns an error, and one that panics, each give a named `EvalError` that names the node; the node and its downstream stay dirty; after the cause is fixed (parameter changed) the next evaluation succeeds and runs only what is still dirty.
```check n8
build/bin/broadsword.exe test nodegraph > scratch/n17-n8.txt 2>&1
PASS: contains test eval_error_and_panic_do_not_poison_cache ... ok
```

### Typed ports and graph structure (the Build line's "typed ports")

**n9 The graph refuses what must never exist.** Connecting an output to an input of a different type, creating a cycle (including a node wired to itself), giving one input two sources, connecting to a port that does not exist, and removing a node that other nodes read: each is a named error and leaves the graph unchanged. Disconnecting and removing leave no dangling edge.
```check n9
build/bin/broadsword.exe test nodegraph > scratch/n17-n9.txt 2>&1
PASS: contains test graph_rejects_invalid_edits_and_stays_unchanged ... ok
```
The same run must print `test connect_rejects_type_mismatch ... ok`, `test connect_rejects_cycle ... ok` and `test connect_rejects_second_source_on_one_input ... ok`. Each test compares the graph before and after the refused edit for equality (not only that an error came back).

**n10 The graph file format is versioned and round-trips byte for byte.** `docs/FORMAT.md` and the golden file `tests/fixtures/graph_v1.bsg` define it.
```check n10
build/bin/broadsword.exe test nodegraph > scratch/n17-n10.txt 2>&1
PASS: contains test graph_file_round_trip_byte_identical ... ok
```
The test reads the golden file, parses it and writes it back; the bytes must equal the golden file. The same run must print `test graph_file_rejects_unknown_version ... ok` (a file claiming `schema=2` is a named error) and `test graph_file_rejects_bad_input ... ok` (empty input, a wrong column count, NaN or infinity in a parameter, a CR character in a field, a Windows backslash or drive letter in a name, a duplicate node id, an edge to a missing node: each is a named error, none a panic).

### Done-when line 2: a subgraph saves as a reusable asset

A subgraph is a graph with some of its inner ports exposed as the subgraph's own inputs and outputs. It is saved as an **asset file** (same text format as a graph, `kind=subgraph`) and used by **instance nodes** in other graphs that name the asset by a relative path. "Reusable" is checked as: the same asset used twice in one graph, and used in two different graphs, with independent caches.

**n11 A subgraph saves to an asset file and loads back identically.**
```check n11
build/bin/broadsword.exe test nodegraph > scratch/n17-n11.txt 2>&1
PASS: contains test subgraph_asset_round_trip_byte_identical ... ok
```
The test saves a subgraph made from a selection of nodes in a graph (the editor's "make subgraph" command, brief N8, is not needed here: the test builds it through the graph API), reads the golden file `tests/fixtures/asset_blur_v1.bsg`, parses it and writes it back, byte for byte. The same run must print `test subgraph_asset_rejects_unknown_version ... ok`.

**n12 An instance behaves exactly like the nodes inlined.** For the same input values, a graph that uses the asset through an instance node gives the same outputs as the graph with the subgraph's nodes copied in, for both a math asset and an image asset.
```check n12
build/bin/broadsword.exe test nodegraph > scratch/n17-n12.txt 2>&1
PASS: contains test subgraph_instance_equals_inlined ... ok
```

**n13 Two instances of one asset are independent, and an edit inside the asset reaches every instance.** Changing a parameter on instance 1 re-evaluates only instance 1's inner nodes (the count is checked); changing the asset file's content and reloading marks every instance of it dirty and none of the graph's other nodes.
```check n13
build/bin/broadsword.exe test nodegraph > scratch/n17-n13.txt 2>&1
PASS: contains test subgraph_instances_have_independent_caches ... ok
```
The same run must print `test subgraph_asset_change_dirties_all_instances ... ok`.

**n14 Subgraph rules that must never be broken.** A subgraph that contains an instance of itself, directly or through another asset (a recursion that would never end), is refused with a named error at load time. An asset path that is absolute, has a drive letter, contains a backslash or a `..` part, or is empty is refused. An instance whose asset is missing is a named error that dirties nothing else. Nesting works to a depth of 8.
```check n14
build/bin/broadsword.exe test nodegraph > scratch/n17-n14.txt 2>&1
PASS: contains test subgraph_recursion_and_bad_paths_rejected ... ok
```
The same run must print `test subgraph_nesting_depth_8_evaluates ... ok`. Reason for 8: a plan-time guess for "deep enough that nobody hits it"; the limit is a setting of the framework, a named constant with a named error when exceeded, never a silent cut-off.

### Done-when line 3: two different graph types (math and image) share one editor

"Share one editor" is defined in the plan as three testable facts: (a) one `Editor` type and one set of editor commands drive both kinds; (b) the editor's source never names a kind, so a third kind needs no change to it; (c) the same scripted edit session gives the right result in both.

**n15 One editor drives both kinds, and its source names neither.**
```check n15
build/bin/broadsword.exe test nodegraph > scratch/n17-n15.txt 2>&1
PASS: contains test one_editor_two_kinds ... ok
```
The same run must print `test editor_source_names_no_kind ... ok`. That test reads `src/editor.rs`, `src/history.rs` and `src/view.rs` and fails if any contains the words `math`, `image` or `Image` (comments included, no exceptions), so a kind cannot leak into the shared editor. A mutation (put the word `Image` into `editor.rs`) must make it fail; that mutation is in brief N8's done check.

**n16 The same scripted editing session works on both kinds, as a program.** A script of editor commands (add node, set parameter, connect, move, delete, undo, redo) runs through the one editor for the math kind and for the image kind.
```check n16
build/bin/broadsword.exe run nodegraph -- cargo run --offline --release --example share_editor > scratch/n17-n16.txt 2>&1
PASS: contains share_editor: ok kinds=math,image
```
The program prints `share_editor: ok kinds=math,image commands=<n> math_result=<x> image_checksum=<n>` and exits 1 on any difference from the expected values, which the program holds as constants worked out by hand (section 5). The `commands` count is the same for both kinds.

**n17 The editor view matches golden text for both kinds.** The editor produces a draw list (boxes, ports, wires, labels, dirty markers) and a text renderer draws it into a character grid, so the view can be compared exactly without a window or a GPU.
```check n17
build/bin/broadsword.exe test nodegraph > scratch/n17-n17.txt 2>&1
PASS: contains test view_matches_golden_math_and_image ... ok
```
The tests compare the grid with `tests/fixtures/view_math.txt` and `tests/fixtures/view_image.txt` (written by hand once, committed). The same run must print `test view_marks_dirty_nodes ... ok` (a node that will re-evaluate is drawn with a `*` in its title).

**n18 Lazlo looks at the editor.**
```check n18
build/bin/broadsword.exe run nodegraph -- cargo run --offline --release --example editor_view -- --kind math > scratch/n17-n18.txt 2>&1
PASS: (human) Lazlo reads the printed grid for `--kind math`, then runs it again with `--kind image` into scratch/n17-n18-image.txt, and confirms each shows boxes with titles, labelled input and output ports, wires that join the right ports, and a `*` on exactly the nodes downstream of the last edit.
```
(human.) The example's `--kind` flag takes `math` or `image`. This replaces a window-based editor check on purpose: binding the editor to the editor shell (node 1.5) is a later step (section 8, risk R1), and a text view proves the editor model without it.

**n19 Undo returns exactly to the start.** 1000 seeded random editor commands on each kind, then undo all of them: the graph equals the starting graph (compared structurally and by its file text); then redo all of them: the graph equals the end state. Same shape as node 0.6's done-when, for the editor's own commands.
```check n19
build/bin/broadsword.exe test nodegraph > scratch/n17-n19.txt 2>&1
PASS: contains test undo_all_returns_to_start_1000_edits ... ok
```
Reason for 1000: the roadmap's own 0.6 check uses 10,000; 1000 per kind keeps this test under a second and is a starting value. The same run must print `test undo_redo_keep_cache_correct ... ok` (after undo or redo, the next evaluation equals a fresh evaluation and runs only the dirty nodes).

## 2. Home

**A new repo, `projects/nodegraph`, crate `nodegraph` (library, Rust 2021, std only), created by brief N1.** `projects/nodegraph` is its own Git repo, ignored by the Broadsword repo, like `projects/crash-sim` and `projects/render` (`broadsword.toml`, `projects_dir`). It is registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, so it does not join the Broadsword workspace. The orchestrator creates the repo and boards it as project `nodegraph` after Lazlo approves (decision D1, section 4); this plan creates nothing.

Under ADR 0001 (option a, accepted):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (check n22). The crate does not depend on `projects/render`, `projects/crash-sim` or `projects/foundation`, and the plan never links into `projects/foundation`.
- **The contract between repos is a file, plus a C ABI.** The graph and asset text format (`docs/FORMAT.md`, brief N6) is how another repo stores or replays a graph. The C ABI (`include/nodegraph.h`, brief N10) is the language-neutral surface for any other language. Nothing in either needs a Cargo link.
- **Copies, not imports, for what 0.2, 0.5 and 0.6 might one day offer.** The crate needs three small things that other nodes will also provide: a command and undo stack (0.6), a text file helper (0.5) and a small vector type for node positions (0.2). Under option (a) it keeps its own copies (`history.rs` about 100 lines; `format.rs`; two `f32` fields for a position). It does not wait for those nodes and does not import them.

**ADR 0001 triggers this node will fire, named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires when another node's code must hold a live graph in-process. The likely ones are node 1.5 (the editor shell hosting the graph editor as a panel), node 3.6 (procedural geometry), 3.15 (compositor), 3.22 (block simulation) and 2.5 (shaders as graphs), all planned in other repos. A live graph cannot go through a file. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2, Lazlo's decision), which this plan does not do. Until Lazlo decides, those nodes can only use graph files, or the C ABI if they load the library as a DLL (a build artefact, not a Cargo dependency; whether that is acceptable is decision D6, section 4: it needs a new ADR, Lazlo's call, decided together with ADR 0002, and until that ADR exists no other repo loads the DLL).
- **Trigger 2** ("a third Rust project needs the same ...") fires if the copied undo stack or text helper turns out to be the same code in three repos. Not planned.
- **Trigger 4** ("a numerics core is needed by two projects") is not fired: the math kind here is a handful of `f64` operations, not a numerics core.

ADR 0004 (ra-adr-repo-map) should list node 1.7 -> `nodegraph` with triggers 1 and 2 above.

**Fit with the product intent.** The crate has four layers, so a mode never depends on another mode and a test never needs a window:

1. *Data:* `Value`, `ValueType`, `Graph`, `Node`, `Port`, `Edge`, the file format. Portable, std only, serializable. This is the part that lives in the shared core scene.
2. *Evaluation:* `Evaluator` with the cache and dirty flags. It sees a node only as "a kind id, parameters, input values in, output values out".
3. *Kinds:* `kind.rs` defines the registration trait; `kinds/math.rs` and `kinds/image.rs` are the two proofs. A mode adds a kind and never edits layers 1, 2 or 4.
4. *Editor model:* commands, undo, selection, layout, draw list, text view. It owns no graph meaning (check n15 enforces it by reading the source).

Layers 1 and 2 are what `capi.rs` wraps for other languages. Modes receive a graph through the shell; they never share each other's kinds.

**Fixed graphs and constants**, so no number in a check has to be guessed later:

- *Shape A:* chain `c` (0..49) has a constant node `c.0` with value `c`, then nodes `c.1` to `c.9`, each adding 1 to its input. The output of chain `c` is `c + 9`. Editing chain 7's head from 7 to 100 changes its output from 16 to 109 and re-runs 10 nodes.
- *Shape B:* layer `L` (0..4) has nodes `L.0` to `L.99`; for `L` above 0, node `L.i` adds `(L-1).i` and `(L-1).((i+1) mod 100)`; layer 0 nodes are constants with value `i`. Expected descendant counts are computed by the program, never typed in.

The same 8 or 9 commands are used for both kinds, so `commands=<n>` is equal. These constants are a hand calculation, to be re-derived by brief N9.

**Every test must be able to fail.** Each brief's done check includes a **mutation step**: change one line (for example make `mark_dirty` stop at the first node, or skip the cycle check), show the named test failing, then restore it. A test that only fails to compile without the code is not enough. Check n3 is the same idea for the benchmark.

**Random numbers without a crate.** The property tests use a 64-bit linear congruential generator (constants from Knuth's MMIX, section 6) seeded with a printed number, so any failure can be replayed.

**Graph file format (draft, for N6 to write down in `docs/FORMAT.md`).** First line `schema=1`; second line `kind=graph` or `kind=subgraph`; then sections `nodes`, `edges`, and for a subgraph `exports`; one line per item, comma separated, fixed decimals so a round trip is byte identical. A node line is `id,kind,type,x,y,param=value;...`. An edge line is `from_id.port,to_id.port`. A name may not contain a comma, a semicolon, a CR or LF, a backslash or a drive letter. Draft: N6 may change it with a reason, and `docs/FORMAT.md` then wins over this paragraph.

## 8. Risks and size

**Risks, with what to do:**

- **R1 "Share one editor" is only proven for a model, not a panel.** The Done-when says "graph editor UI". This plan proves the editor model plus a text view and a human look (n18), and leaves hosting in a real dockable panel to after node 1.5. If Lazlo reads "UI" as "a window with a mouse", the node is not done by n1 to n23 alone. Cost of asking: one message with D2. Cost of not asking: a node marked done that he does not accept.
- **R2 Prerequisites.** 0.6, 1.5 and 1.6 are not started and the node prompt says to stop if a prerequisite is missing. Ask Lazlo before starting N1 whether they are waived (section 3).
- **R3 Dirty-set definition.** "Re-evaluates only dirty nodes" can be read as "only nodes downstream of the edit" (this plan) or, stronger, "stops where a recomputed value is unchanged" (early cutoff). The stronger form would make n1's counts smaller for some edits. This plan does not implement early cutoff, and says so; if Lazlo wants it, it is one more brief (an `EvalStats.cutoffs` counter and a flag) and n1's expected counts for edits that do not change a value need a case of their own.
- **R4 Counts can lie if only one counter is used.** The evaluator's own `EvalStats` is the thing under test. The plan therefore requires an independent counter in the test's own kind (section 1, intro) and the oracle's own descendant search; a brief that uses only `EvalStats` has not met n1.
- **R5 The text format is a guess.** D3. It must be stable before the shared core stores graphs in it, and a change is a cross-shard change; `schema=1` and the unknown-version test (n10, n11) exist so that a change is detected, not silent.
- **R6 Subgraph design could force changes to the evaluator.** N7 runs an inner evaluator per instance so N3's evaluator need not change; if that proves too slow for a nested asset in a big graph (each instance has its own cache and work list), the fix is an evaluator change after N3 has merged, which would break the claim split. The depth-8 limit and the 500-node check (which has no subgraph) do not test this; a later brief should time 100 instances.
- **R7 Panics and the panic strategy.** `catch_unwind` cannot catch a panic when `panic = "abort"` is set, nor a foreign unwind. N1 forbids the abort setting. A node written in another language through the C ABI cannot unwind into Rust safely; that case is out of scope and must be said in `README.md`.
- **R8 Stack use in nested instances.** Nesting depth 8 runs 8 inner evaluators; each is iterative, so stack use is small, but n7 only tests a flat 20,000-node chain. The first brief for depth 8 (N7) must test a 20,000-node chain inside an instance, not just 8 levels with a few nodes each.
- **R9 The timing budget is a guess.** n4's 50 ms is a placeholder (section 1). Until the first quiet-board run replaces it, n4 can pass or fail for a reason unrelated to correctness; n1 to n3 are the correctness proof.
- **R10 The C ABI is a surface that other languages will bind to.** Any change to it breaks every caller in every language; it is versioned in the header (a `NODEGRAPH_ABI_VERSION` constant that N10 adds) and a test checks the header's version equals the Rust constant. A first ABI will be wrong in some detail; plan on one revision once a second language actually uses it.
- **R11 ADR 0001 trigger 1** (section 2) will fire when any other node needs a live graph. The plan lets them start by using graph files or a DLL, but a live editor in the shell cannot; ADR 0002 must be decided before 1.5 can host the graph editor.

**Size:** 10 briefs (N1 to N10), roughly 250 lines each, about 2,500 changed lines in all (code, tests, fixtures and the format document) in a new repo. Allow about 3 extra fix-round tasks, since the playbook expects the first review of risky work to fail (N3, N7 and N10 are the likely ones). So about 10 merged tasks plus 3 fix rounds to reach the Done-when, plus 1 human check (n18) that only Lazlo can run, and one later brief (the panel, after 1.5; not counted) that the Done-when's "UI" may need (R1). On the harness's own yardstick (about 20 merged tasks per stage, 660 lines a task; scratch/roadmap-size.md), the 10 briefs are about half of one stage. The roadmap-size estimate for group G1 (platform) is 10k/25k/60k lines per node (scratch/roadmap-size.md), so this plan's 2,500 lines is about a tenth of the mid figure: the rest is the editor panel, more kinds and the ABI revision, which are outside the Done-when line and not planned here. With four free slots, the plan takes five waves (section 7).
