## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test scene`; a program goes through `broadsword run scene -- cargo run --offline --release --example <name> -- <flags>`. This is the same form as `docs/nodes/1.1.md` section 1.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. A program writes its result to stdout. `broadsword run scene` starts cargo in the project checkout (`projects/scene`, or the task's worktree of it), so a path the shell never resolves has to be resolved by the program, and the glTF example's flags are defined to do that: `--in <path>` is relative to the project checkout (the fixtures in `tests/fixtures/` live there), `--in-shared <path>` is relative to the Broadsword root (for `shared/models/...`), and `--out <path>` is always relative to the Broadsword root, so output lands in Broadsword's `scratch/` and never inside a project checkout. The example finds the root by walking up from its working directory to the first folder holding `broadsword.toml`, and prints `gltf_roundtrip: FAIL no broadsword.toml above <dir>` if there is none (no default).
- `broadsword test` has no name filter. It runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed` (format as in `docs/nodes/1.1.md` section 1, read from `crates/broadsword/src/` at the first brief). A check that needs one test looks for that test's own line.
- `python -I scripts/node_check.py 2.4 --list` lists these blocks and `--run <id>` runs one. It judges three rule forms only: `last line == X`, `contains X` and `exit != 0` (`scripts/node_check.py` header). Every other `PASS:` text, including every `(human)` rule, is printed as "judge by hand". Never use `--run --all` on this node: run one id at a time, and leave the `(human)` ids (d10) to Lazlo.
- A negative control (a check that must fail on purpose, d2 and d8) is written as `PASS: contains <the example's own FAIL line>`, so an example that did not build or does not know the flag cannot pass it. It still counts only when its positive twin (d1 for d2, d7 for d8) has passed with the same example.
- Timing checks are marked **(quiet board)** in the prose before the block. Run them only while no build, test or review is running (`broadsword status`), and rerun, never average over a busy board. Checks marked **(human)** need Lazlo and his hardware; an agent never runs them as passed.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Done-when line 1: 1M instances update at 60 fps

The budget is the requirement itself. 60 fps means one frame in 1/60 s = 16.667 ms = **16667 us** (arithmetic, not a benchmark). What is timed is the **CPU update** of every instance's transform for one frame, not drawing. Drawing is node 2.5, and its GPU cost is not in this check (section 4).

**d1 One million instances update within one 60 fps frame, p99.** The example creates 1000000 instances, runs 600 frames of the update, times each frame, and requires the 99th percentile frame and the mean frame to be at most the budget (the mean is there so a run of a few very slow frames cannot hide behind the p99). 600 frames is 10 seconds at 60 fps (arithmetic), long enough for 6 slow frames to move the p99 and the mean. It also checks the final transforms against a second, independent scalar implementation (a checksum), so a fast wrong update cannot pass.

```check d1
build/bin/broadsword.exe run scene -- cargo run --offline --release --example instances_bench -- --instances 1000000 --frames 600 --budget-us 16667 > scratch/n24-d1.txt 2>&1
PASS: contains instances_bench: ok instances=1000000
```

(quiet board.) The program prints `instances_bench: ok instances=1000000 frames=600 p99_us=<n> mean_us=<n> budget_us=16667 checksum=<hex>` and exits 0 only if the p99 frame and the mean frame are within budget and the checksum matches. Otherwise it prints `instances_bench: FAIL budget` or `instances_bench: FAIL checksum` and exits 1. Source of the budget: arithmetic above. There is no placeholder to replace: unlike node 1.1's d3, the number is the requirement. A stricter sub-budget, if Lazlo wants one, is a new decision and is recorded here with its measurement.

**d2 The benchmark can fail.** The same example with a budget no frame can meet.

```check d2
build/bin/broadsword.exe run scene -- cargo run --offline --release --example instances_bench -- --instances 1000000 --frames 600 --budget-us 1 > scratch/n24-d2.txt 2>&1
PASS: contains instances_bench: FAIL budget
```

(quiet board.) Expected: the run exits non-zero (`run: FAILED (exit 1)`) and the saved file contains `instances_bench: FAIL budget`. The rule is the message, not only the exit code, so a build failure or an unknown flag cannot pass it. Reason for 1 us: one million 48-byte transform writes cannot finish in 1 us on any CPU (estimate: each write is a memory access; the whole frame is far longer). FAIL: `instances_bench: ok` (the budget check cannot fail, so d1 proves nothing).

**d3 The instance update is correct on a small scene, every value.** A test sets up 1000 instances with known transforms and rotation speeds, runs the update for 10 frames, and compares every matrix element with a reference computed in the test by a plain loop. Tolerance is exact equality for values computed the same way; the test documents the one order of operations it uses.

```check d3
build/bin/broadsword.exe test scene > scratch/n24-d3.txt 2>&1
PASS: contains test instances_update_matches_reference ... ok
```

FAIL: the line is missing (no such test) or says FAILED.

## 2. Home

**A new, separate repo `projects/scene`, one library crate `scene` (Rust 2021, std only, empty `[dependencies]`, its own empty `[workspace]`), created by brief S1 after Lazlo approves the repo** (decision D1, the same step as node 1.6's D1 in `docs/nodes/1.6.md` section 2). `projects/` is ignored by the Broadsword repo, like `projects/render` and `projects/crash-sim`. The crate is registered by its `Cargo.toml` alone (`broadsword.toml`, `projects_dir`), as render is.

Under ADR 0001 (option a, Accepted, `docs/adr/0001-shared-core.md:3`):

- **No Cargo dependency (path or git) on another repo.** Check d15 enforces the empty dependency table. The crate never depends on `projects/foundation`, `projects/render`, `projects/crash-sim` or `projects/reflect`, and the plan never links into `projects/foundation`.
- **Math is a copy, not an import.** The first brief needs `Vec3`, `Mat4` and a quaternion. Render's `projects/render/src/math.rs` (f32, 172 lines, measured in ADR 0001 at `9e1060b`) has `Vec3` and `Mat4` with the operations the scene needs, so S2 copies those functions into `src/math.rs` and records the copy (source file, commit, lines) in the module doc comment of `src/math.rs`. `README.md` does not carry it. Copies are what option (a) accepts ("keep the copies per repo").
- **The scene file and the interchange formats are the contract.** Other repos read `docs/FORMAT.md` (brief S5) and the glTF or USD file, and never link this crate. The 0.5 format code (`projects/foundation`, `docs/nodes/0.5.md`: `bstext`, the `BSBN` binary encoding, the `{ data, schema }` envelope) is **not** imported. S5 reimplements the envelope rule in `src/format.rs` and writes its own fixture by hand, so the 0.5 contract is followed without a link.
- **Renderers and mode code never live here.** Node 2.5 (renderer) reads this crate's scene; it does not change the scene's types or add its own.

**ADR 0001 triggers this node fires, named now:**

- **Trigger 2 ("a third Rust project needs the same `Vec3` or the same parser") fires at S2.** Crash-sim and render already have a `Vec3`; `scene` would be the third copy. The Vec3 copy is the decision for Lazlo before S2 starts (section 3, decision D2). The default in this plan is to copy anyway, record that trigger 2 fired in ADR 0001, and not move to (d2) for one 40-line type. Lazlo may choose ADR 0002 first instead.
- **The 0.5 parser is a second case of trigger 2.** The scene file's envelope rule and migration steps are the same idea as 0.5's, written again in `src/format.rs`. Same decision (D2).
- **Trigger 1 ("a second project must run ... as a library") fires when node 2.5 (renderer) or 2.6 (animation) needs the live scene in-process,** because both are planned in other repos (`docs/adr/0004-roadmap-repo-map.md:108-109`, 2.5 W/render, 2.6 W/animation). Until ADR 0002 is decided, those nodes read the scene file or the glTF/USD files, and a live scene cannot cross a file. Node 2.5's plan must say this.
- **Node 1.6 (reflection) is the other repo the node may need.** `docs/nodes/1.6.md` section 2 plans reflection as its own repo, `projects/reflect`, and says every later node that edits core data (2.4 among them) fires trigger 1 at its first use. Section 3 gives the choice for this node.

**Fit with the product intent.** The crate has three layers, so a mode never depends on a window or a file format:

1. **Data:** `Transform`, `Node`, `Hierarchy`, `Instance`, `Layer`, `Scene`, `Mat4`, `Vec3`. Std only, no I/O.
2. **Formats:** the scene file (`src/format.rs`), glTF import and export (`src/gltf.rs`, `src/gltf_write.rs` with `src/json.rs` as its JSON reader and writer), USD (`src/usd.rs`). Each reads and writes the data layer and nothing else.
3. **Benchmarks and examples:** `examples/instances_bench.rs`, `examples/gltf_roundtrip.rs`. They use the public API only.

**The scene file (layout, for check d13; draft, S5 writes `docs/FORMAT.md`).** A text file with a first line `schema=1`, then one row per item with a kind word first: `node,<id>,<parent id or ->,<name>`; `xform,<node id>,<translation x y z as f32 bits in hex>,<rotation quat x y z w as f32 bits in hex>,<scale x y z as f32 bits in hex>`; `layer,<id>,<name>,<visible 0 or 1>`; `inst,<layer id>,<node id>,<angle as f32 bits in hex>,<speed as f32 bits in hex>`. A name is written with `%` as `%25`, `,` as `%2C` and a line feed as `%0A`, and read back the same way, so a name such as `Walls, exterior` round-trips. The instance matrix is not stored: it is rebuilt from the angle by the same function S3 uses, so "equal scenes" in d14 compares ids, angles, speeds and the rebuilt matrices. Meshes are not stored in schema 1 (the scene file holds hierarchy, transforms, layers and instances; meshes travel in glTF and USD). Floats are stored as their IEEE bits in hex, so a round trip is byte identical by construction and there is no decimal formatting to get wrong. A file with `schema=2` or any other value is a named error. A version step table (`v1 -> v2`) is empty at schema 1 and is tested by d14 when the first change lands.

**Property-style coverage, without a crate.** The transform test (d4) and the instance test (d3) generate their trees and transforms from a fixed-seed xorshift generator written in the test (std only, no `proptest`, which would be a crate under ADR 0003). 200 trees per run, the seed printed on failure. Exhaustive sweeps are not possible here (the input space is every tree), so the seed is the reproducibility handle.

**Mutation step in every brief that adds a test.** Each brief in section 7 with a numeric or ordering rule (S2, S3, S5, S8, S9) includes a mutation step: change one line (for example, swap two multiplications in the hierarchy product, or write one hex digit fewer in the scene file), show the named test failing in its output, and restore the line. This is the rule from `docs/nodes/1.1.md` section 5 and the playbook's "prove a new test can fail" (`AI_DEV_PLAYBOOK.md`, lesson 10).

## 8. Risks and size

**Risks, with what to do:**

- **R1 Prerequisites.** 1.6 is `not started` and 0.5 is `in progress` (section 3). The node prompt says to stop when a prerequisite is missing. Ask Lazlo (D3) before brief S1. Cost of asking: one message. Cost of not asking: a stopped coder.
- **R2 ADR 0001 triggers fire early.** Trigger 2 fires at S2 (third `Vec3`, third copy of the envelope rule), and trigger 1 fires when 2.5 or 2.6 needs the live scene (section 2). If Lazlo answers D2 with "ADR 0002 first", S2 waits for a decision that is not planned here, and the node's schedule moves with it.
- **R3 The 60 fps budget may not be met on this PC.** The update reads about 8 MB per frame (angles and speeds, 2 x 4 MB) and writes about 52 MB (the new angles, 4 MB, and the rebuilt matrices, 48 MB; the old matrices are not read), about 60 MB in all (arithmetic), which is 3.6 GB/s at 60 fps (arithmetic, 60 MB x 60). The PC's memory bandwidth is **not measured** in this plan. If d1 fails with a correct checksum, the first fix is to split the update across cores with `std::thread::scope` (std only, so no crate and no node 0.4 code; **estimate**), then a smaller per-instance layout. The budget itself is not loosened.
- **R4 Timing noise.** d1 can fail for a reason unrelated to correctness, when another build or a review runs (as in `docs/nodes/1.1.md` R5). Run it on a quiet board, and rerun, never average over a busy one.
- **R5 "USD round trip" may mean more than the subset.** D5 keeps the `.usda` subset (plan default). Then the Done-when line is met for the subset only, and the node must say so in `docs/nodes/2.4.md` rather than claim full USD (OpenUSD: layers, composition, USDC binary). Full USD is a C++ wrap decision for Lazlo.
- **R6 The Khronos sample may use features the importer refuses.** S7 refuses materials, animations, skins and extensions as `Unsupported`. The plan therefore picks `Triangle` (glTF-Sample-Models `2.0/Triangle`, one mesh, no material, no interleaved buffer view; **estimate from memory**, not checked: no network) so that d9 can pass inside the scope. `BoxInterleaved` was rejected because it has a material and an interleaved `byteStride` buffer view. If `Triangle` turns out to carry a feature the importer refuses, the check is changed here with the reason before it is run, never left failing. Lazlo sees this choice at D6.
- **R7 glTF field names come from memory.** Section 6 lists the spec URL as from memory. S7 and S8 must read the spec page and quote the field names they use; a wrong name shows as a failed import, not a silent one (every unknown field is a named error or an explicit skip in the brief).
- **R8 Float round trip through text.** glTF and the scene file write floats. The scene file is safe by construction (hex bits, d13). glTF writes decimals, so the writer must print the shortest decimal that reads back to the same `f32` (Rust's `Display` for floats does this, from memory; S8 proves it with d6). If not, the writer is wrong, not the check: fix the writer.
- **R9 "ECS" and "instancing" in the Build line are only partly covered.** The plan uses an arena hierarchy with indices and an instance store (sections 2 and 7), not a component-based ECS. Instancing at the file level (`EXT_mesh_gpu_instancing`) is not in the first ten briefs. Both are a decision at node start, recorded in this file: either accept the arena and the in-memory instances as the Build line's meaning, or add a brief for each.
- **R10 Scope creep into the renderer.** A "1M instances" scene invites draw code. Drawing is node 2.5 (section 4). This node's briefs must not add a window, a GPU call or a shader; any such line is a scope violation and goes to `IDEAS.md`.

**Size.** Ten briefs (S1 to S10), about 250 lines each, about 2,500 changed lines in all in a new repo (**estimate**, the same sizing method as `docs/nodes/1.1.md` section 8). Nine of the ten are needed for the Done-when line (S5 supports d13 and d14 only), and S3 and S4 are needed because S7 and S9 read the scene type, which owns the instances. Allow about 2 fix-round tasks, since the first review of S6 (the JSON reader) and S7 is likely to fail. The critical path is S1, S2, S3, S4, S7, S8: six rounds, with S6 beside S2 to S4 and S5, S9 and S10 beside S7. Human checks: d10 (Lazlo's viewer), and decisions D1 to D6 before the briefs that need them. No check is marked passed by this plan.
