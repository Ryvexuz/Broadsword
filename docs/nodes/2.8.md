## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test numerics`. The one Python command (check n2) is `python -I` on a script in the `numerics` repo's main checkout.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails. Where a check names more than one test, the PASS line names the first and the text below it lists the others, which the reviewer reads in the same file.
- `python -I scripts/node_check.py 2.8 --list` lists these blocks and `--run <id>` runs one. It judges only the rule forms `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text it prints as "judge by hand".
- A rule starting `(human)` needs Lazlo and is never run by an agent and never counts as passed until Lazlo says so. A check marked (needs SciPy) can only run once Lazlo has decided D3 (section 4). No check is timing, so none is marked (quiet board). No check needs a window, a GPU or any hardware, so none is marked (desktop).
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, fixture or test is missing.

### What "a reference test suite" and "within tolerance" mean here

The roadmap names neither the suite nor the tolerance. This plan defines both, and check n20 asks Lazlo to accept the definition.

- **The suite** is the set of fixture files `tests/fixtures/ref/<area>.ref`, one per area (`dense`, `decomp`, `sparse`, `fft`, `ode`, `ad`, `optim`), written once by `reference/gen_reference.py` (brief N3) from SciPy and NumPy, which call LAPACK for the linear algebra. Each case holds its inputs and SciPy's outputs as decimal text (Python's `repr` of a float, which round-trips exactly, read back with Rust's correctly rounded `str::parse::<f64>`). The list of cases, with a reason for each, is `reference/SUITE.md` (N3). The Rust tests never run Python: they read the committed fixtures.
- **Within tolerance** never means "equal to SciPy's digits". Two correct algorithms give different rounding, so every comparison is a bound with a reason, written once in `src/tol.rs` and `docs/TOLERANCES.md` (brief N2) and used by every area test. The bounds are in the style of LAPACK's own test programs: a *test ratio* (an error divided by `n * eps * scale`) must be at most `THRESH = 30`. The value 30 is the threshold LAPACK's test input files use, written from memory: **UNVERIFIED**, to be read from Reference-LAPACK's `TESTING/*.in` files (section 6) by brief N2 before it is frozen. Where a forward error is compared with SciPy's answer, the bound also has the condition number that the generator stored in the fixture, because a forward error is only as small as the condition number allows (LAPACK Users' Guide, chapter "Accuracy and Stability", section 6).
- Each area test also checks it ran the number of cases the fixture header states (`cases=N`), so a fixture that silently loses cases fails.

### Dense linear algebra (Build: "dense ... linear algebra")

**n3 LU with partial pivoting matches LAPACK `getrf`/`getrs` (through `scipy.linalg.lu_factor`, `lu_solve`).**
```check n3

PASS: contains test lu_solve_matches_lapack ... ok
```
For each case: backward ratio `||b - A x||_inf / (n * eps * ||A||_inf * ||x||_inf) <= THRESH`, and forward error `||x - x_ref||_inf / ||x_ref||_inf <= THRESH * n * eps * cond_inf(A)` with `cond_inf` from the fixture. The cases include well-conditioned random matrices, a Hilbert matrix of order 8 (ill-conditioned, so the forward bound is tested where it is loose and the backward one where it is not) and a matrix that needs pivoting (a zero leading entry). The same run must print `test lu_singular_is_named_error ... ok` (an exactly singular matrix gives `NumError::Singular`, never infinity or NaN) and `test lu_random_systems_backward_stable ... ok` (1000 seeded random systems of order 1 to 40, no reference needed, backward ratio at most `THRESH`; the seed is printed on failure).

**n4 Cholesky matches LAPACK `potrf` (through `scipy.linalg.cholesky`), and determinant and inverse match NumPy.**
```check n4
build/bin/broadsword.exe test numerics > scratch/n28-n4.txt 2>&1
PASS: contains test cholesky_matches_lapack ... ok
```

**n5 Symmetric eigenvalues and SVD match LAPACK `syevd` and `gesdd` (through `scipy.linalg.eigh`, `svd`); least squares matches `gelsd` (through `scipy.linalg.lstsq`).**
```check n5
build/bin/broadsword.exe test numerics > scratch/n28-n5.txt 2>&1
PASS: contains test eigh_matches_lapack ... ok
```
Eigenvalues, in ascending order: `|lambda_i - lambda_ref_i| <= THRESH * n * eps * ||A||_2` (a backward stable method moves each eigenvalue of a symmetric matrix by at most the norm of the backward error, Weyl's inequality). ### Automatic differentiation (Build: "automatic differentiation")

**n11 Gradients and Hessians match SciPy's analytic Rosenbrock derivatives; forward and reverse mode agree.**
```check n11
build/bin/broadsword.exe test numerics > scratch/n28-n11.txt 2>&1
PASS: contains test ad_gradient_matches_rosen_der ... ok
```
SciPy has no automatic differentiation, so the reference is the analytic derivative SciPy ships: `scipy.optimize.rosen_der` and `rosen_hess` at 20 points of dimension 2 to 10, plus four functions whose gradients the generator computes from hand-written NumPy formulas (`exp`, `sin`, `log`, products and quotients). Bound for gradients: each component within `THRESH * eps * (1 + |g_ref|)`, because automatic differentiation is exact up to rounding (no truncation error, unlike finite differences). Bound for Hessians, norm-wise per matrix: `max_ij |H_ij - R_ij| / (eps * (1 + max_ij |R_ij|)) <= THRESH`, where `R` is the reference matrix and `eps` (here and in the gradient bound) is the unit roundoff `2^-53`, `tol::EPS` (`pub const EPS: f64 = f64::EPSILON / 2.0;` in `src/tol.rs`). Reason: a component-wise bound fails a correct AD on an entry that cancels (case `rosen_p4_d6`, component 7, `H[1][1] = 202 + 1200*x1^2 - 400*x2 = -16.9`: ratio 71.4 against `THRESH` 30; an exact rational recomputation gives `-16.93580310450432`, and the AD error is `2.5e-14` while SciPy's, the fixture's, is `1.2e-13`, so the AD is 5 times closer to the truth). The same run must print `test ad_hessian_matches_rosen_hess ... ok`, `test forward_and_reverse_mode_agree ... ok` (both modes on 1000 seeded random expressions, within the same bound) and `test ad_domain_error_is_named ... ok` (`log` of a negative number, or `sqrt` at 0 asked for a derivative, is a named error, never NaN passing silently).

**Fixture file format (draft, for N2 to write down in `docs/FIXTURES.md`; that file then wins over this paragraph).** UTF-8 text, LF line ends, one item per line, `#` starts a comment line. The header is `format=1`, `area=<name>`, `generator=reference/gen_reference.py`, `python=`, `numpy=`, `scipy=`, `lapack=`, `cases=<N>`, in that order. Then N cases:

```
case <id>
op=<operation name, for example lu_solve>
param <name> <decimal>                      (scalars: tolerances, rcond, t_end)
in <name> <rows> <cols> <v1> <v2> ...        (real matrix or vector, row-major)
inc <name> <rows> <cols> <re1> <im1> ...      (complex, for FFT)
out <name> <rows> <cols> <v1> ...            (SciPy's result)
outc <name> <rows> <cols> <re1> <im1> ...
meta <name> <decimal>                        (cond_inf, cond_2, SciPy's own error, iterations)
end
```

Every number is Python's `repr(float)`, the shortest string that reads back to the same `f64`; Rust's `str::parse::<f64>` is correctly rounded, so the value read is bit-identical to the one SciPy produced. Case ids are unique in a file and match `[a-z0-9_]+`. Sparse inputs are triplets: three `in` lines named `<m>_rows`, `<m>_cols`, `<m>_vals` and a `param <m>_n`. Names may not contain spaces. NaN and infinity are refused in `out` and `meta` lines (n15), because a reference that is NaN tests nothing.

**Fixture contents per area** (the full case list with reasons goes in `reference/SUITE.md`, N3; sizes are plan-time choices, UNVERIFIED as to run time):

## 8. Risks and size

**Risks, with what to do:**

- **R1 SciPy is not on the PC, or Lazlo does not want it installed (D3).** Then the Done-when, as written ("match LAPACK/SciPy"), cannot be checked at all, and N3 to N10 wait. Fallbacks, both weaker and both Lazlo's call: reference values from exact rational arithmetic with Python's standard `fractions` module (as foundation's `mat.md` did for 3x3 and 4x4), which covers small dense problems only; or a reference run on another machine that has SciPy, with only the fixtures copied in. Cost of asking: one message.
- **R2 "Within tolerance" and "a reference test suite" are not defined by the roadmap.** This plan defines both, and the coder who builds the code also chose nothing: the tolerances are fixed here and in N2 before any algorithm exists, so they cannot be tuned to the code. Even so, an agent passing its own definition is not the capability Lazlo asked for until he accepts it (check n20).
- **R3 A tolerance that is too loose passes anything; one that is too tight fails correct code.** The `THRESH = 30` form has a decades-old precedent in LAPACK's own tests (once verified, N2); the other constants (`FFT_C = 10`, `ODE_FACTOR = 10`, `STIFF_FACTOR = 100`, the optimizer bounds) are reasoned guesses, marked UNVERIFIED. The mutation steps (section 5) test that bounds are tight enough to catch a real bug; a correct algorithm that fails a bound means the bound is changed in this file in a reviewed commit with a reason, never quietly in code.
- **R4 Two correct algorithms give different answers, not only different rounding.** Eigenvector signs and bases, SVD vectors, ODE step sequences and optimizer paths differ legitimately. The checks therefore compare invariants (residuals, orthogonality, error against a tighter truth, final value) wherever a direct comparison would be wrong (section 1); a brief that compares such outputs entry by entry has a test that is wrong, not code.
- **R5 The plan's Build line is open-ended.** "Dense and sparse linear algebra" has no end. The first pass covers LU, Cholesky, determinant, inverse, symmetric eigen, SVD, least squares, CSR, SpMV and PCG. Not in it: QR, the nonsymmetric eigenproblem, sparse direct solvers (sparse LU or Cholesky), sparse eigen solvers (Lanczos), banded solvers, matrix functions, `f32`. A consumer that needs one adds a brief; the Done-when as defined here does not need them. If Lazlo reads "LAPACK" as "most of LAPACK", the node is much larger (size below).
- **R6 Accuracy-first algorithms are slow.** Jacobi eigen and SVD are O(n^3) per sweep with several sweeps, and nothing here is blocked for cache or parallel. The Done-when asks only for matching outputs, so a correct but 100 times slower core passes it. A consumer needing speed (3.19 FEM, 3.20 CFD) needs later briefs: blocked kernels, tridiagonal QR, and 0.4's pool.
- **R7 A dependent needs something 2.8's Build line does not list.** Node 3.1 (rigid body) needs a contact solver (projected Gauss-Seidel on an LCP) and 2.9 needs a rank and DOF report; neither is "dense or sparse linear algebra" in the narrow sense. This plan leaves the contact solver to 3.1 (it is physics, not numerics) and gives 2.9 the SVD's rank (N5). Record the choice in ADR 0004's row when 3.1 is planned.
- **R8 Two copies of CG (ADR 0001 trigger 3).** crash-sim's n20-05 and this crate's N6 implement the same method. Check n6 holds both to the same cases, but a fix in one will not reach the other by itself; when a bug is found in either, the orchestrator boards the fix for both. This is exactly the case trigger 4 (and ADR 0002) exists for.
- **R9 The error enum is fixed in N1.** If a later brief needs a variant N1 did not create, it stops and reports (it does not edit `error.rs`), and the orchestrator boards a one-line follow-up for `error.rs`. Cost: one small extra task, preferable to overlapping claims.
- **R10 Platform maths functions.** `sin`, `cos`, `exp` and `ln` come from the platform; a different PC or toolchain can change the last bit of FFT, ODE and AD results. Check n14 claims bit-identity on one machine only. The tolerance checks are unaffected.
- **R11 Prerequisite rule.** The node prompt says to stop when a prerequisite is missing; 0.4 is not started. Ask Lazlo (D2) before N1.
- **R12 Fixture regeneration drift.** A new SciPy or NumPy can change the last digits of outputs, and a new NumPy can change `default_rng` streams for some methods. The version lines and check n2 make any change visible; regeneration is a reviewed brief (N3's README).

**Size:** 10 briefs (N1 to N10), roughly 250 changed lines each, about 2,500 lines of Rust, Python and docs in a new repo, plus generated fixtures (under 1 MB, UNVERIFIED). N2 and N8 may each split in two (the plan says how), so 10 to 12 merged tasks. Allow about 3 extra fix-round tasks, since the playbook expects the first review of risky work to fail (N2's tolerances, N5's Jacobi convergence and N8's step control are the likely ones). So **about 13 to 15 merged tasks to reach the Done-when as this plan defines it**, plus one human check (n20) and D3's one-time install, which only Lazlo can approve. With four free slots the briefs run in four waves (section 7). Beyond the Done-when, the items of R5 and R6 (QR, nonsymmetric eigen, sparse direct, Lanczos, blocked and parallel kernels, `f32`) are a rough further 8 to 15 briefs, planned by whichever consumer needs them first; this count is a plan-time estimate, UNVERIFIED.
