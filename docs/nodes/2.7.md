## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root (the one stated working directory). The plugin is never given to a program as a relative path: the example finds the built test plugin by name through the `CARGO_TARGET_DIR` environment variable (`--plugin-name`), and only the human check a14 passes an absolute path (`--plugin`), which Lazlo supplies. `scratch/` and `build/` always mean the Broadsword root ones, never a folder inside the project checkout. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test audio-dsp`. A program goes through `broadsword run audio-dsp -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/a27-<id>.txt 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite with zero tests, or without the named test, fails.
- `broadsword run` prints its job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule naming a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 2.7 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text, including every `(human)` rule, it prints as "judge by hand". A negative control (a check that must fail on purpose, a9 and a13) is written as `PASS: exit != 0`; that alone also passes when the example fails to build, so a negative control counts only when its positive twin (a8 for a9, a12 for a13) has passed with the same example. Never use `--run --all` on this node.
- A rule starting `(human)` needs Lazlo and his hardware. An agent never runs it and it never counts as passed until Lazlo says so.
- A rule ending `(quiet board)` is timing: run it only while no build, test or review is running (`broadsword status`), and rerun it rather than average over a busy board.
- A check marked **(decision D<n>)** cannot run until Lazlo has decided that item in section 4.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Thresholds: where each number comes from

Numbers are either a fact with its source, a reason stated in the check, or an **estimate** that the first quiet-board run replaces. There are no published benchmarks for "64 tracks with effects" in this plan: the roadmap names none, and none was looked up.

- Sample rate 48 kHz and block size 512 are plan choices, not facts: 48 kHz is the rate video and music work usually uses, and 512 samples is about 10.7 ms per block, a common device buffer size (**estimate**; there is no `docs/nodes/1.10.md` yet, so the device side is open, see R1).
- Float sums: a single `f32` addition has a relative rounding error of at most 2^-24 (about 6e-8), so summing 64 full-scale tracks carries an error of at most about 64 x 2^-24 = 3.8e-6 (**estimate of the bound**, reason: n times the unit roundoff).
- Biquad and delay checks compare with closed forms (section 6): the RBJ cookbook formulas and integer sample delays. Their bounds are the floating-point rounding of those formulas, stated in each check.

### Done-when line 1: 64 tracks with effects play in real time

**a1 Mixing 64 tracks matches an independent sum.** The test builds 64 seeded tracks of 4096 samples each, mixes them with the track mixer (the graph comes later, in B5), and compares every output sample with an `f64` sum of the same inputs done in the test.
```check a1
build/bin/broadsword.exe test audio-dsp > scratch/a27-a1.txt 2>&1
PASS: contains test mix_64_tracks_matches_f64_sum ... ok
```
Bound: every sample within 1e-5 of the `f64` sum (estimate of the rounding bound, see above, with margin). FAIL: the line is missing or says FAILED.

**a2 Automation lands on the exact sample.** A gain automation point at sample 137 of a 512-sample block must change the output at sample 137 and nowhere else. "Sample-accurate" means the change is at the sample index, not at the block boundary.
```check a2
build/bin/broadsword.exe test audio-dsp > scratch/a27-a2.txt 2>&1
PASS: contains test automation_applies_at_exact_sample ... ok
```
Threshold: zero samples off, because both sides are integers. A change at sample 136 or 138 fails.

**a3 A linear automation ramp is linear per sample.** A ramp from 0 to 1 over 512 samples must produce the per-sample values `i / 511` (the ramp's endpoints inclusive) to within 1e-6 (reason: f32 rounding of values below 1).
```check a3
build/bin/broadsword.exe test audio-dsp > scratch/a27-a3.txt 2>&1
PASS: contains test automation_ramp_is_linear_per_sample ... ok
```

**a4 Effects: a gain and a delay are exact, a biquad matches the RBJ formulas.** Three tests. A gain of 0.5 halves every sample exactly (0.5 is a power of two, so the product is exact). A delay of D samples outputs the input shifted by exactly D samples, zeros before. A low-pass biquad from the RBJ cookbook has DC gain 1 and Nyquist gain 0 (both follow from its formula with the sums of `b` and `a`; checked in `f64` as `|gain - 1| <= 1e-12` and `|gain| <= 1e-12`, because `(1+alpha)+(1-alpha)` need not round to exactly 2), and its coefficients equal the formula's values to 1e-12 in `f64`.
```check a4
build/bin/broadsword.exe test audio-dsp > scratch/a27-a4.txt 2>&1
PASS: contains test biquad_lowpass_matches_rbj_formula ... ok
```
The same run must also print `test gain_is_exact_for_powers_of_two ... ok` and `test delay_is_exact_integer_shift ... ok` (threshold: zero samples off, both integers). The RBJ source is in section 6 (verify).

**a5 The graph evaluates in order and refuses cycles.** A mixer graph of 64 track inputs, one bus and one master output evaluates each node after its inputs, and a graph with a cycle is a named error and never a hang.
```check a5
build/bin/broadsword.exe test audio-dsp > scratch/a27-a5.txt 2>&1
PASS: contains test graph_rejects_cycles ... ok
```
The same run must print `test graph_evaluates_in_topological_order ... ok`.

**a6 MIDI notes land on the exact sample.** A note-on at tick T, converted with a tempo and a sample rate given in the test, must start at sample `round(T * samples_per_tick)` computed in exact integer arithmetic, not in floats, so a rounding slip is caught at the sample.
```check a6
build/bin/broadsword.exe test audio-dsp > scratch/a27-a6.txt 2>&1
PASS: contains test midi_note_starts_on_exact_sample ... ok
```

**a7 The session file round-trips byte for byte.** The session (tracks, effect settings, automation points, MIDI notes) is written as text. The test reads `tests/fixtures/session_v1.txt`, parses it and writes it back; the bytes must equal the fixture. A file claiming `format=2` is a named error.
```check a7
build/bin/broadsword.exe test audio-dsp > scratch/a27-a7.txt 2>&1
PASS: contains test session_round_trip_byte_identical ... ok
```
The same run must print `test session_rejects_unknown_version ... ok`.

**a8 Real time, offline, quiet board: 64 tracks with effects render faster than they play.** The example builds 64 tracks, each with one biquad, one delay and a gain automation curve, runs 60 seconds of audio at 48 kHz in 512-sample blocks, and times each block. It prints `tracks64: ok tracks=64 effects=192 seconds=60 render_ratio_p99=<f> xruns=0` and exits 0 only if the 99th-percentile ratio of block render time to block duration is at most `--budget-ratio`. Otherwise it prints `tracks64: FAIL budget ratio_p99=<f> budget=<f>` and exits 1.
```check a8
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example tracks64 -- --tracks 64 --seconds 60 --budget-ratio 0.5 > scratch/a27-a8.txt 2>&1
PASS: contains tracks64: ok tracks=64 effects=192 seconds=60
```
(quiet board.) Threshold reason: 0.5 means half of each block's time is left free for the OS, the device and the rest of Broadsword. It is an **estimate**, not a measured value. The first quiet-board run may only tighten it: if the measured p99 times 2 is below 0.5, that value becomes the budget and the node's file records the measured p99; if it is not below 0.5, the budget stays 0.5 and a8 fails (risk R2). A render ratio at or above 1.0 is a certain dropout, so the budget is never raised, whatever a run shows.

**a9 The same example can fail.** An impossible budget (0.0001) must make the run exit non-zero.
```check a9
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example tracks64 -- --tracks 64 --seconds 60 --budget-ratio 0.0001 > scratch/a27-a9.txt 2>&1
PASS: exit != 0
```
(quiet board.) Expected: `run: FAILED (exit 1)` and the saved file contains `tracks64: FAIL budget`; read it by hand. FAIL: `tracks64: ok` (the budget cannot fail, so a8 proves nothing).

**a12 The host processes audio through the plugin, exactly.** The gain plugin is set to 0.5. The host feeds it 512 frames of a seeded signal and requires every output frame to equal half the input frame, exactly.
```check a12
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example load_plugin -- --plugin-name audio_dsp_test_gain > scratch/a27-a12.txt 2>&1
PASS: contains load_plugin: ok plugin=audio-dsp-test-gain frames=512 channels=2 out_ratio=0.5 nonzero_out=1024
```
The example finds `<name>.dll` in `$CARGO_TARGET_DIR/release/` and compares every output sample with half the input sample in code, bit for bit; if any sample differs it prints `load_plugin: FAIL sample <i> not half` and exits 1, so the printed `out_ratio` is not what decides. The test `plugin_gain_halves_signal` (in a11's suite run) checks the same property in-process. The `.dll` name is for Windows. Needs a22 first.

## 2. Home

**A new repo, `projects/audio-dsp`, crate `audio-dsp` (library, Rust 2021, std only), created by brief B1 after Lazlo approves the repo (decision D1).** `projects/audio-dsp` is its own Git repo, ignored by the Broadsword repo, like `projects/render` and `projects/crash-sim`. It is registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, so it does not join the Broadsword workspace.

Under ADR 0001 (option a, accepted):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (check a16). The crate does not depend on `projects/nodegraph` (node 1.7), `projects/render`, `projects/crash-sim` or `projects/foundation`, and the plan never links into `projects/foundation`.
- **The mixer graph is a copy, not an import.** Node 1.7's graph lives in its own repo (`docs/nodes/1.7.md` section 2). This crate keeps its own small graph of track, bus and master nodes (about 300 lines, brief B5). Two copies of a graph type is the cost option (a) accepts.
- **The contract between repos is a file.** The session format (`docs/FORMAT.md`, brief B6) is how another repo stores a session or replays one offline. For example, node 3.18 (DAW features) can replay a recorded session with no link to this crate.
- **The plugin ABI is a C ABI, not a crate link.** The gain plugin in brief B9 is a separate crate that exports the plugin entry symbol; the host finds it by path and never links it.

**ADR 0001 triggers this node will fire, named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires when the editor shell (node 1.5) or the node graph editor (1.7) must change the mixer graph of a playing session in-process. A live edit cannot go through a file while audio is running. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2, Lazlo's decision), which this plan does not assume. **Until Lazlo decides, the mixer graph can only be edited offline**, between renders, and the editor's live edit is out of this plan's first briefs (decision D6).
- **Trigger 2** ("a third Rust project needs the same ...") fires if node 1.7 and this crate end up with the same graph code in three repos. Not planned now.

ADR 0004 (`docs/adr/0004-roadmap-repo-map.md`, Proposed) should list node 2.7 -> `audio-dsp` with triggers 1 and 2 above, once it is decided.

**Layers, and the product intent.** The crate has four layers, so a mode never depends on the audio engine's internals and a test never needs a sound device:

1. *Data:* `Block` (interleaved `f32` samples, a frame count, a sample rate), `Track`, `Bus`, `Note`, `AutomationPoint`, the session format. Portable, std only.
2. *Processing:* the `Processor` trait (`prepare`, `process(&mut Block)`), the gain, delay and biquad processors, the automation evaluator, and the mixer graph's evaluation order. Pure functions of blocks; no clock, no device, no file.
3. *Plugin host:* `plugin.rs`, a CLAP-ABI host that loads a shared library and runs its processor. `cfg(windows)` only (`LoadLibrary`, `GetProcAddress`), kept in one module so no other module can call a plugin.
4. *Device sink:* the `Sink` trait that receives finished blocks. Two implementations: a null sink (for every check) and, later, node 1.10's real device sink (decision D2). The sink is the only place a real clock is read.

Layers 1 and 2 are the stable surface any mode can wrap. A mode sends blocks through the engine and reads results; it never opens a device or loads a plugin itself, which keeps "no mode depends on another mode" true for audio as well.

## 5. Test harness

| Check | Kind of test | What it compares against |
|---|---|---|
| a1 | seeded exhaustive comparison: every output sample of 64 tracks x 4096 frames | an `f64` sum of the same inputs, computed in the test; bound 1e-5 |
| a2, a3 | sample-indexed checks on a generated 512-frame block | the sample index 137 (integer); ramp values `i / 511` |
| a4 | closed-form checks | RBJ low-pass coefficients (1e-12 in `f64`); DC gain 1 and Nyquist gain 0 from the formula; exact powers of two; integer delay shift |
| a5 | structure tests on constructed graphs | the evaluation order recorded by the processors; a cycle must return a named error |
| a6 | integer arithmetic | `round(T * samples_per_tick)` computed with integers only |
| a7 | golden-file round trip | `tests/fixtures/session_v1.txt`, byte identical |
| a8, a9 | timing benchmark with a pass/fail budget, and its negative control | the budget `--budget-ratio` (0.5, estimate); 0.0001 must fail |
| a10, a14 | human checks with printed summary lines | Lazlo's ears, the device's xrun count, the third-party plugin's name |
| a11, a12, a13 | plugin ABI test with our own plugin, exact output ratio, missing-file error | the gain 0.5 is exact in binary; a missing file is an error |
| a16 | structure test reading `Cargo.toml` | an empty dependency list |

**Signals are generated, not recorded.** Every test signal is produced from a seeded xorshift generator (seed fixed and printed on failure), so no audio file is needed and nothing is downloaded. Exhaustive comparison is used wherever the space is small (a2 and a6 test every index of a block); a1 uses a seeded set of 64 x 4096 values, which is the whole of its input.

**Fixtures to make (all text, small, committed in the new repo):**

- `tests/fixtures/session_v1.txt` (brief B6): about 20 lines covering every record kind of section 5's format: three tracks, one bus, one effect of each kind, five automation points and four MIDI notes, written by hand once. Written by hand, not generated by the code under test, so the round trip proves the parser and writer agree with an independent text.
- `tests/plugin-gain/` (brief B9): the test plugin, a separate crate with its own empty `[workspace]` that builds the cdylib `audio_dsp_test_gain`. It is test code and is never shipped as part of the crate.
- No audio fixture, no recorded sound and no download.

**Session format (draft; B6 writes it down in `docs/FORMAT.md`).** First line `format=1`, then one record per line, fields separated by spaces: `track <id> <name> gain=<f> pan=<f>`, `bus <id> <name>`, `effect <track> <kind> <key>=<f> ...`, `auto <track> <param> <sample> <value>`, `note <track> <tick> <length> <key> <velocity>`. Numbers are written with six decimals (`{:.6}`) so a round trip is byte identical. Names contain no spaces, and a space or a line break in a name is a named error.

**Mutation steps (every test that could pass by accident).** Each brief shows the named test failing after one planted change, then restores the change, as the node 1.1 plan does:

- B2: skip the last track in the sum. `mix_64_tracks_matches_f64_sum` must fail.
- B3: apply automation at the block start instead of the sample. `automation_applies_at_exact_sample` must fail.
- B4: flip the sign of the biquad's `b1`. `biquad_lowpass_matches_rbj_formula` must fail.
- B6: write one decimal fewer. `session_round_trip_byte_identical` must fail.
- B5: remove the cycle check. `graph_rejects_cycles` must fail (it must fail, not hang: the test has a step limit).
- B7: compute the sample with float rounding instead of integers. `midi_note_starts_on_exact_sample` must fail on the chosen tick.
- B9: report the wrong version number from the plugin. `plugin_loads_and_reports_identity` must fail.
- B10: make the gain plugin return its input unchanged. `plugin_gain_halves_signal` and the `load_plugin` example must fail with `out_ratio=1`.

## 8. Risks and size

**Risks, with what to do:**

- **R1 Prerequisites and the device.** 1.7 and 1.10 are not started, and 1.10 has no plan file, so the "under 10 ms round trip" and the device side of done-when line 1 have no plan. B1 to B10 run on a null sink. Ask Lazlo (D1, D2) before B1 starts. Cost of asking: one message. Cost of not asking: a stopped coder, or a plan that claims a device it cannot reach.
- **R2 Real time on one thread.** Check a8 is a budget of half a block (0.5, an estimate). If 64 tracks with effects miss it on a single thread, the fix is threads (node 0.4, in progress, has a speedup example) or fewer effects per track. The budget is not raised to pass. The plan changes and says so.
- **R3 Plugin host safety.** Loading and calling a plugin is `unsafe`, and a bad plugin or a wrong ABI declaration can crash the host. B9 reads each declared struct's layout and size against the CLAP headers (verify), and B9 reads the plugin's reported version at load time (before any call), and B10 refuses to call a plugin whose version B9 rejected. Running plugins in a separate process is not planned; it is a later decision, and it would change a12.
- **R4 The third-party plugin.** Done-when line 2 names a third-party plugin, and only Lazlo can choose it (D3). Its licence, its GUI requirements or a licence key could make a14 fail for reasons outside this node. Until a14 passes, done-when line 2 is only proven for our own test plugin.
- **R5 Our test plugin is not a third-party plugin.** a12 proves the host's ABI handling against code written from the same declarations, so a misreading of the ABI would appear in both. The mitigation is the header read in R3, reviewed by a different model than the coder (AGENTS.md review rule), and a14 with a real plugin.
- **R6 Live editing of the mixer graph.** A session that is playing cannot be edited in-process until ADR 0002 is decided (D6, ADR 0001 trigger 1). The first briefs render offline. Done-when line 1 says "play in real time", which this plan meets for a session fixed when playback starts, and it says so.
- **R7 Compute is not latency.** a8 measures block compute time, not the OS, the device or the editor. It cannot show the "under 10 ms round trip" figure, which is 1.10's and needs a real device (a10). The same caveat as node 1.1's R6 applies: each output line says what it measures.
- **R8 Denormal numbers in filter tails (from memory, verify).** Some CPUs slow down sharply on very small floating-point values in filter feedback, which can push a8 over budget on quiet signals. The test signal is never silent, and flush-to-zero is not set silently, because it would change a4's results. If a8 shows it, the fix is a stated decision in this file.
- **R9 Windows-only plugin loading.** The host is `cfg(windows)` (section 2). Linux or macOS plugin loading is not planned and would need an ADR.
- **R10 The graph copy drifts.** This crate and node 1.7 each keep a graph (section 2). If they diverge, that is the ADR 0001 trigger 2 case. Not planned now.

**Size.** Ten briefs, B1 to B10, roughly 2,300 changed lines in all, counting code, tests and the format document (**estimate**, from the claim list in section 7: about 150 to 300 lines each). Allow about two fix-round tasks, because the first review of the risky briefs (B5 graph, B9 plugin loading) is likely to fail, as node 1.1 expects for its `unsafe` briefs. So about twelve tasks to merge (estimate), plus two human checks that only Lazlo can run (a10 and a14). The critical path is B1, B2, B5, B8: four rounds, with B3, B4, B6, B7, B9 and B10 beside it. On the harness's own measure of merged tasks per stage, this is a fraction of a stage, which is the planning view, not a schedule.

**Plan facts this file depends on, to be checked by the first brief that uses each:** the CLAP header names and ABI layout (B9, verify); the RBJ coefficient formulas (B4, verify); the `LoadLibraryW` signature (B9, verify); the fixed-decimal round trip (B6, a test, no outside source).
