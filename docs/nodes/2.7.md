## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test audio-dsp`. A program goes through `broadsword run audio-dsp -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/a27-<id>.txt 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite with zero tests, or without the named test, fails.
- `broadsword run` prints its job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule naming a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 2.7 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text, including every `(human)` rule, it prints as "judge by hand". A negative control (a check that must fail on purpose, a9 and a13) is written as `PASS: exit != 0`; that alone also passes when the example fails to build, so a negative control counts only when its positive twin (a8 for a9, a12 for a13) has passed with the same example. Never use `--run --all` on this node.
- A rule starting `(human)` needs Lazlo and his hardware. An agent never runs it and it never counts as passed until Lazlo says so.
- A rule ending `(quiet board)` is timing: run it only while no build, test or review is running (`broadsword status`), and rerun it rather than average over a busy board.
- A check marked **(decision D<n>)** cannot run until Lazlo has decided that item in section 4.
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example or test is missing.

### Thresholds: where each number comes from

Numbers are either a fact with its source, a reason stated in the check, or an **estimate** that the first quiet-board run replaces. There are no published benchmarks for "64 tracks with effects" in this plan: the roadmap names none, and none was looked up.

- Sample rate 48 kHz and block size 512 are plan choices, not facts: 48 kHz is the rate video and music work usually uses, and 512 samples is about 10.7 ms per block, a common device buffer size (**estimate**; there is no `docs/nodes/1.10.md` yet, so the device side is open, see R1).
- Float sums: a single `f32` addition has a relative rounding error of at most 2^-24 (about 6e-8), so summing 64 full-scale tracks carries an error of at most about 64 x 2^-24 = 3.8e-6 (**estimate of the bound**, reason: n times the unit roundoff).
- Biquad and delay checks compare with closed forms (section 6): the RBJ cookbook formulas and integer sample delays. Their bounds are the floating-point rounding of those formulas, stated in each check.

### Done-when line 1: 64 tracks with effects play in real time

**a1 Mixing 64 tracks matches an independent sum.** The test builds 64 seeded tracks of 4096 samples each, mixes them through the graph, and compares every output sample with an `f64` sum of the same inputs done in the test.
```check a1
build/bin/broadsword.exe test audio-dsp > scratch/a27-a1.txt 2>&1
PASS: contains test mix_64_tracks_matches_f64_sum ... ok
```
Bound: every sample within 1e-5 of the `f64` sum (estimate of the rounding bound, see above, with margin). FAIL: the line is missing or says FAILED.

**a2 Automation lands on the exact sample.** A gain automation point at sample 137 of a 512-sample block must change the output at sample 137 and nowhere else. "Sample-accurate" means the change is at the sample index, not at the block boundary.
```check a2
build/bin/broadsword.exe test audio-dsp > scratch/a27-a2.txt 2>&1
PASS: contains test automation_applies_at_exact_sample ... ok
```
Threshold: zero samples off, because both sides are integers. A change at sample 136 or 138 fails.

**a3 A linear automation ramp is linear per sample.** A ramp from 0 to 1 over 512 samples must produce the per-sample values `i / 511` (the ramp's endpoints inclusive) to within 1e-6 (reason: f32 rounding of values below 1).
```check a3
build/bin/broadsword.exe test audio-dsp > scratch/a27-a3.txt 2>&1
PASS: contains test automation_ramp_is_linear_per_sample ... ok
```

**a4 Effects: a gain and a delay are exact, a biquad matches the RBJ formulas.** Three tests. A gain of 0.5 halves every sample exactly (0.5 is a power of two, so the product is exact). A delay of D samples outputs the input shifted by exactly D samples, zeros before. A low-pass biquad from the RBJ cookbook has DC gain exactly 1 and Nyquist gain exactly 0 (both follow from its formula with the sums of `b` and `a`), and its coefficients equal the formula's values to 1e-12 in `f64`.
```check a4
build/bin/broadsword.exe test audio-dsp > scratch/a27-a4.txt 2>&1
PASS: contains test biquad_lowpass_matches_rbj_formula ... ok
```
The same run must also print `test gain_is_exact_for_powers_of_two ... ok` and `test delay_is_exact_integer_shift ... ok` (threshold: zero samples off, both integers). The RBJ source is in section 6 (verify).

**a5 The graph evaluates in order and refuses cycles.** A mixer graph of 64 track inputs, one bus and one master output evaluates each node after its inputs, and a graph with a cycle is a named error and never a hang.
```check a5
build/bin/broadsword.exe test audio-dsp > scratch/a27-a5.txt 2>&1
PASS: contains test graph_rejects_cycles ... ok
```
The same run must print `test graph_evaluates_in_topological_order ... ok`.

**a6 MIDI notes land on the exact sample.** A note-on at tick T, converted with a tempo and a sample rate given in the test, must start at sample `round(T * samples_per_tick)` computed in exact integer arithmetic, not in floats, so a rounding slip is caught at the sample.
```check a6
build/bin/broadsword.exe test audio-dsp > scratch/a27-a6.txt 2>&1
PASS: contains test midi_note_starts_on_exact_sample ... ok
```

**a7 The session file round-trips byte for byte.** The session (tracks, effect settings, automation points, MIDI notes) is written as text. The test reads `tests/fixtures/session_v1.txt`, parses it and writes it back; the bytes must equal the fixture. A file claiming `format=2` is a named error.
```check a7
build/bin/broadsword.exe test audio-dsp > scratch/a27-a7.txt 2>&1
PASS: contains test session_round_trip_byte_identical ... ok
```
The same run must print `test session_rejects_unknown_version ... ok`.

**a8 Real time, offline, quiet board: 64 tracks with effects render faster than they play.** The example builds 64 tracks, each with one biquad, one delay and a gain automation curve, runs 60 seconds of audio at 48 kHz in 512-sample blocks, and times each block. It prints `tracks64: ok tracks=64 effects=192 seconds=60 render_ratio_p99=<f> xruns=0` and exits 0 only if the 99th-percentile ratio of block render time to block duration is at most `--budget-ratio`. Otherwise it prints `tracks64: FAIL budget ratio_p99=<f> budget=<f>` and exits 1.
```check a8
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example tracks64 -- --tracks 64 --seconds 60 --budget-ratio 0.5 > scratch/a27-a8.txt 2>&1
PASS: contains tracks64: ok tracks=64 effects=192 seconds=60
```
(quiet board.) Threshold reason: 0.5 means half of each block's time is left free for the OS, the device and the rest of Broadsword. It is an **estimate**, not a measured value; the first quiet-board run replaces it with the measured p99 times 2, and the node's file records the measured value. A render ratio at or above 1.0 is a certain dropout, so the check cannot pass with the budget at 1.0 or above; the budget is never raised to make a run pass.

**a9 The same example can fail.** An impossible budget (0.0001) must make the run exit non-zero.
```check a9
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example tracks64 -- --tracks 64 --seconds 60 --budget-ratio 0.0001 > scratch/a27-a9.txt 2>&1
PASS: exit != 0
```
(quiet board.) Expected: `run: FAILED (exit 1)` and the saved file contains `tracks64: FAIL budget`; read it by hand. FAIL: `tracks64: ok` (the budget cannot fail, so a8 proves nothing).

**a10 Real output: 64 tracks through a real sound device for five minutes (human, decision D2).** Lazlo listens to a 64-track session played through a real output for 300 seconds, with the device's own dropout counter.
```check a10
build/bin/broadsword.exe run audio-dsp -- cargo run --offline --release --example tracks64 -- --tracks 64 --seconds 300 --device default > scratch/a27-a10.txt 2>&1
PASS: (human) Lazlo confirms the printed tracks64 line reports xruns=0 and that no dropout is audible in the 300 seconds. (decision D2: the device sink is node 1.10's and not yet planned.)
```
(human, decision D2.) Until node 1.10 has a sink, `--device default` prints `tracks64: FAIL no device sink` and exits 1; that is the expected state, not a pass. The flag exists (brief B8) so the command is the same when 1.10 lands.

### Done-when line 2: a third-party plugin loads and processes audio

The automated checks use a plugin this repo builds itself (brief B9), a small CLAP-ABI gain plugin, because a third-party plugin cannot be assumed present in a check that must run unattended. The third-party check is a14 below, a human check with a plugin Lazlo chooses (decision D3).

**a11 The host reads a plugin's identity and entry point.** The test loads the built gain plugin from `build/release/` (the shared build folder, `.cargo/config.toml` `target-dir = "build"`, as in `docs/nodes/1.1.md`), and requires the plugin to report its id and its version and to list one audio port of two channels.

## 2. Home

**A new repo, `projects/audio-dsp`, crate `audio-dsp` (library, Rust 2021, std only), created by brief B1 after Lazlo approves the repo (decision D1).** `projects/audio-dsp` is its own Git repo, ignored by the Broadsword repo, like `projects/render` and `projects/crash-sim`. It is registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, so it does not join the Broadsword workspace.

Under ADR 0001 (option a, accepted):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (check a16). The crate does not depend on `projects/nodegraph` (node 1.7), `projects/render`, `projects/crash-sim` or `projects/foundation`, and the plan never links into `projects/foundation`.
- **The mixer graph is a copy, not an import.** Node 1.7's graph lives in its own repo (`docs/nodes/1.7.md` section 2). This crate keeps its own small graph of track, bus and master nodes (about 300 lines, brief B5). Two copies of a graph type is the cost option (a) accepts.
- **The contract between repos is a file.** The session format (`docs/FORMAT.md`, brief B6) is how another repo stores a session or replays one offline. For example, node 3.18 (DAW features) can replay a recorded session with no link to this crate.
- **The plugin ABI is a C ABI, not a crate link.** The gain plugin in brief B9 is a separate crate that exports the plugin entry symbol; the host finds it by path and never links it.

**ADR 0001 triggers this node will fire, named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires when the editor shell (node 1.5) or the node graph editor (1.7) must change the mixer graph of a playing session in-process. A live edit cannot go through a file while audio is running. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2, Lazlo's decision), which this plan does not assume. **Until Lazlo decides, the mixer graph can only be edited offline**, between renders, and the editor's live edit is out of this plan's first briefs (decision D6).
- **Trigger 2** ("a third Rust project needs the same ...") fires if node 1.7 and this crate end up with the same graph code in three repos. Not planned now.

ADR 0004 (`docs/adr/0004-roadmap-repo-map.md`, Proposed) should list node 2.7 -> `audio-dsp` with triggers 1 and 2 above, once it is decided.

**Layers, and the product intent.** The crate has four layers, so a mode never depends on the audio engine's internals and a test never needs a sound device:

1. *Data:* `Block` (interleaved `f32` samples, a frame count, a sample rate), `Track`, `Bus`, `Note`, `AutomationPoint`, the session format. Portable, std only.
2. *Processing:* the `Processor` trait (`prepare`, `process(&mut Block)`), the gain, delay and biquad processors, the automation evaluator, and the mixer graph's evaluation order. Pure functions of blocks; no clock, no device, no file.
3. *Plugin host:* `plugin.rs`, a CLAP-ABI host that loads a shared library and runs its processor. `cfg(windows)` only (`LoadLibrary`, `GetProcAddress`), kept in one module so no other module can call a plugin.
4. *Device sink:* the `Sink` trait that receives finished blocks. Two implementations: a null sink (for every check) and, later, node 1.10's real device sink (decision D2). The sink is the only place a real clock is read.

Layers 1 and 2 are the stable surface any mode can wrap. A mode sends blocks through the engine and reads results; it never opens a device or loads a plugin itself, which keeps "no mode depends on another mode" true for audio as well.
