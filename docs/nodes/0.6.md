# Node 0.6: Command and undo system

Roadmap "Done when": 10,000 random edits followed by full undo returns exactly to the start state. Status: in progress.

Code and doc are in `projects/foundation` (`src/undo.rs`, `projects/foundation/docs/undo.md`); merged commit `0bb59be`.

## What is there

`Command<D>` (apply, undo, optional merge) and `History<D>` with undo, redo, merge of consecutive edits, groups with rollback, a required entry cap, and named errors.

The done-when is tested by `ten_thousand_random_edits_full_undo_and_redo` in `tests/undo.rs`: seeded, 10,000 edits (single edits, merged runs, groups), a snapshot at each entry boundary, full undo checked at every step and ending byte-identical to the start, then full redo ending byte-identical to the end. `mixed_undo_redo_walk_matches_model` walks 5 seeds of 4,000 random steps against a model. The doc lists mutation checks run for redo clear, merging, group rollback and the merge barrier after undo.

## What is left

- Atomicity of a command is a contract that `History` cannot check.
- Commands are not serialized (a design decision recorded in `undo.md`, with the way to add it later).
- No application uses `History` yet.
- No `tag:` item exists, so the row stays `in progress`.
