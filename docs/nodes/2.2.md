# Node 2.2 Brush engine: infrastructure plan and done checks

**Status: draft: rewrite when the node starts.** Written 2026-11-21 from Broadsword `66243509`, before any code. Nothing in this file has been run. Every number is quoted from a file or command output, or marked as an estimate. The briefs in section 7 are the only plan for code; the first brief that touches a fact named here must correct this file if the fact is wrong.

Node (CAPABILITY_ROADMAP.md, Part 5, lines 518-520): *Brush engine.* Build: dab-based brushes, pressure and tilt dynamics, stabilizer, smudge. Needs: 1.1, 2.1. Done when: measured stroke lag with a tablet is no worse than Krita's on the same machine. Broadsword stage: 4 (ROADMAP.md row 2.2). ROADMAP.md status today: not started.

Product intent this plan respects (Lazlo, 2026-11-20, as recorded in `docs/nodes/1.1.md`): one unified tool, where every mode reads and writes one shared core data model. The brush engine is therefore a **layer under the paint mode**, not a mode. It turns `InputEvent` pen samples (from node 1.1's format) into dabs, and writes the dabs into a raster layer (node 2.1). It never opens a window, never imports a mode, and never owns the scene. Routing events to the brush is the editor shell's job (node 1.5).

## 1. Done checks as commands

### How to run and read a check

- Conventions are those of `docs/nodes/1.1.md` section 1. Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test brush-engine`; a program goes through `broadsword run brush-engine -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter. It runs the whole suite and prints one `test <name> ... ok` line per test. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `python -I scripts/node_check.py 2.2 --list` lists these blocks, and `--run <id>` runs one (ra-node-check). It judges only `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text is printed as "judge by hand". A negative control is written `PASS: exit != 0`, and its expected output line is read by hand from the saved file. A negative control is only meaningful when its positive twin (d7 for d8) has passed with the same example.
- A rule starting `(human)` needs Lazlo and his hardware. It is never run by an agent to pass, and never counts as passed until Lazlo says so. A rule ending `(quiet board)` is timing: run it only while `broadsword status` shows no build, test or review running, and rerun it rather than average over a busy board. A rule ending `(desktop)` needs an interactive logged-in Windows desktop. A check that cannot run because a flag, file, example or test is missing is a FAIL.
- Run one id at a time. Never use `--run --all` on this node: the `(human)` and `(quiet board)` ids must not run unattended.

### Done-when: stroke lag no worse than Krita's

"Stroke lag" here means: from the moment a pen sample's hardware timestamp is read (node 1.1, `ptPerformanceCount`, QueryPerformanceCounter clock) to the moment the brush's dab is in the layer buffer the next time the window presents. It is a measurement on this PC, not a photon measurement, and it is the same definition for both apps. The method is not yet decided and is risk R1 in section 8.

**d1 The crate has no dependencies.** ADR 0001 forbids a Cargo dependency on another repo, and ADR 0003 (Proposed, not decided) is the only way to add a crate. The brush engine has none.
```check d1
build/bin/broadsword.exe test brush-engine > scratch/n22-d1.txt 2>&1
PASS: contains test cargo_toml_has_no_dependencies ... ok
```
Threshold reason: an exact structural fact, from `docs/adr/0001-shared-core.md` and `docs/adr/0003-dependency-policy.md` (status line: Proposed).

**d2 A dab stamps the reference profile exactly.** A 64-pixel round dab at full pressure, hardness 1.0 and opacity 1.0 is rendered and compared byte for byte with the committed golden file `tests/golden/round_dab_64.ppm`.
```check d2
build/bin/broadsword.exe test brush-engine > scratch/n22-d2.txt 2>&1
PASS: contains test dab_stamp_matches_reference_profile ... ok
```
Threshold reason: the golden file is written once by the brief and reviewed by hand (centre pixel full alpha, the pixel one radius out zero alpha). Byte identity is the rule because the same machine and the same arithmetic must give the same bytes. Estimate: the golden file is about 12 KB (64 x 64 pixels x 3 bytes plus a short header, computed, not measured).

**d3 Pressure maps to size and opacity by a fixed table.** Pressure 0.0 gives the minimum size, 1.0 the maximum, both curves are monotonic over the 1025 pressure values of node 1.1 (raw 0..=1024, decoded as `raw / 1024`), and the values at 0.0, 0.5 and 1.0 equal the table written in `src/pressure.rs`.
```check d3
build/bin/broadsword.exe test brush-engine > scratch/n22-d3.txt 2>&1
PASS: contains test pressure_maps_size_and_opacity ... ok
```
Threshold reason: the table is a design choice made in brief B3, not a measurement. Estimate: minimum size 1 px and maximum 64 px, from the dab size in d2. The test checks exact equality with the table, so a change to the table is a deliberate, reviewed change.

**d4 Tilt changes the dab's shape and angle.** At tilt 0,0 the dab is round. At tilt X or Y of 60 degrees it is an ellipse whose long axis follows the tilt direction. Rotation from node 1.1 (0..=359 degrees) turns the ellipse by the same angle.
```check d4
build/bin/broadsword.exe test brush-engine > scratch/n22-d4.txt 2>&1
PASS: contains test tilt_changes_ellipse_angle ... ok
```
Threshold reason: the geometry is exact (an ellipse of minor axis `cos(tilt)` times the major axis, from the standard projection of a tilted disc). Estimate: the angle tolerance is 1 degree, because the stamp is rasterised on a pixel grid.

**d5 The stabilizer's lag is bounded.** A stroke of 500 samples at a constant speed of 10 px per sample, given to the stabilizer with its default window, is followed by the output path. The output must stay within 16 px of the input at every sample after the first 16, and must reach the last input point within 1 px when the pen lifts.
```check d5
build/bin/broadsword.exe test brush-engine > scratch/n22-d5.txt 2>&1
PASS: contains test stabilizer_lag_bounded ... ok
```
Threshold reason: estimate. 16 samples is the default window (a design choice in brief B4). At a pen report rate of about 200 Hz (estimate, not measured on Lazlo's tablet), 16 samples is about 80 ms, which is the lag the stabilizer adds on purpose. The 16 px bound is also an estimate: at 10 px per sample the stabilizer's output trails by about one window of travel, and B4 sets the number in its test comment with that reason. Open point, see R3.

**d6 Smudge conserves paint.** Smudging a painted patch over blank paper, with the stroke moved across it and back, keeps the total of the colour channels of the layer within 1 level per pixel of the total before the stroke (the rounding of an 8-bit channel).
```check d6
build/bin/broadsword.exe test brush-engine > scratch/n22-d6.txt 2>&1
PASS: contains test smudge_conserves_paint_mass ... ok
```
Threshold reason: 1 level per pixel is the smallest change an 8-bit channel can show, so an exact sum would fail on rounding alone. The bound is exact arithmetic on the stated sum, not a benchmark.

**d7 A recorded stroke replays to its golden image.** The example `stroke_replay` reads the committed event-log fixture (the file format of node 1.1, `tests/fixtures/event_log_v1.csv` copied into this repo, plus the stroke fixture `tests/fixtures/stroke_v1.csv`), runs the brush, and writes the layer. It prints `stroke_replay: ok frames=<n>` only when the output equals `tests/golden/stroke_v1.ppm` byte for byte.
```check d7
build/bin/broadsword.exe run brush-engine -- cargo run --offline --release --example stroke_replay > scratch/n22-d7.txt 2>&1
PASS: contains stroke_replay: ok
```
Threshold reason: the replay is deterministic on one machine (no clock, no window, no thread). The stroke fixture is generated by a fixed script in brief B6, not recorded from a pen, so this check proves the replay path, not the pen.

**d8 The replay check can fail.** The `--corrupt-dab` flag adds 1 to one channel of every dab before the comparison.
```check d8
build/bin/broadsword.exe run brush-engine -- cargo run --offline --release --example stroke_replay -- --corrupt-dab > scratch/n22-d8.txt 2>&1
PASS: exit != 0
```
Expected: the run exits non-zero, and the saved file contains `stroke_replay: FAIL golden` (read by hand). FAIL if the output says `stroke_replay: ok`, because then d7 proves nothing. This is valid only because d7 passed with the same example.

**d9 A stroke lands in a tiled layer exactly as in a flat buffer.** The same stroke is stamped into a flat buffer and into the tile layout that node 2.1 defines (the tile format is 2.1's contract, read from its `docs/FORMAT.md` or equivalent file, not linked). The two results, read back flat, must be equal byte for byte. This is what lets 2.2 stay correct when 2.1 changes its tile size.
```check d9
build/bin/broadsword.exe test brush-engine > scratch/n22-d9.txt 2>&1
PASS: contains test stamp_into_tiles_matches_flat ... ok
```
Threshold reason: exact equality. A tile seam bug (a dab split across two tiles and stamped twice, or not at all) changes the bytes, so this check catches the class of bug the layer boundary creates.

**d10 Lag probe: the brush receives live pen samples and writes timed dabs.** The example `lag_live` reads live pen input and prints one `lag,` row per dab with its latency in microseconds, and a summary. It needs the live `InputEvent` path from node 1.1, which is a cross-repo call and fires ADR 0001 trigger 1 (section 2). It is blocked until Lazlo decides ADR 0002.
```check d10
build/bin/broadsword.exe run brush-engine -- cargo run --offline --release --example lag_live -- --strokes 30 > scratch/n22-d10.txt 2>&1
PASS: (human) Lazlo confirms the saved file has 30 strokes, a `lag,` row for every dab, and a final line `lag_live: ok strokes=30`. No dab missing a timestamp.
```
(human, desktop, quiet board, blocked on ADR 0002.) Threshold reason: 30 strokes is an estimate, enough for a stable median on one person's drawing; the same count is used for Krita in d11. It is not a published sample size.

**d11 Krita comparison: the brush is no worse than Krita on this PC.** Lazlo captures 30 strokes in Krita on this PC with the same pen, the same drawn path and the same method as d10, and writes them to `scratch/n22-krita-lag.csv` following the protocol in `docs/lag-protocol.md` (written by brief B9). The example `lag_compare` reads both files and prints `lag_compare: ok` only if the brush median lag is at most Krita's median, and the brush p90 is at most Krita's p90.
```check d11
build/bin/broadsword.exe run brush-engine -- cargo run --offline --release --example lag_compare -- --brush scratch/n22-d10.txt --krita scratch/n22-krita-lag.csv > scratch/n22-d11.txt 2>&1
PASS: contains lag_compare: ok
```
(desktop, quiet board, human capture first.) Threshold reason: the Done-when line says "no worse than Krita's", so the bound is a ratio of 1.0 on the median, with p90 added so that a fast median and a jittery tail cannot pass. Lazlo's capture comes first; the agent never fills in the Krita file. Krita version: to be recorded in the protocol when the capture is made (not pinned in this plan, see section 4).

**d12 The comparison check can fail.** The `--brush-scale 2` flag doubles every brush latency before the comparison.
```check d12
build/bin/broadsword.exe run brush-engine -- cargo run --offline --release --example lag_compare -- --brush scratch/n22-d10.txt --krita scratch/n22-krita-lag.csv --brush-scale 2 > scratch/n22-d12.txt 2>&1
PASS: exit != 0
```
Expected: the run exits non-zero, and the saved file contains `lag_compare: FAIL median` (read by hand). Valid only when d11 has passed with the same inputs.

**d13 The whole suite is green.** Every test above, and any a brief adds, passes. This is the check that gates every merge.

## 2. Home

**A new repo, `projects/brush-engine`, crate `brush-engine` (library, Rust 2021, std only), created by brief B1.** Like `projects/window-input` (the node 1.1 plan, section 2), it is its own Git repo ignored by the Broadsword repo, and it registers as a Broadsword project with its own empty `[workspace]` table, so it does not join the Broadsword workspace. Creating it needs Lazlo's approval (new repo, same as 1.1 brief W1).

Under ADR 0001 (option a, accepted, `docs/adr/0001-shared-core.md`):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (check d1). The crate does not depend on `projects/window-input`, `projects/render`, `projects/foundation` or any 2.1 crate. It never links into `projects/foundation`.
- **The brush's own math and tile buffer are copies,** kept per repo as ADR 0001 option (a) allows. The dab and tile types are small; a copy is the accepted cost.
- **Contracts are files.** The input is the event-log format of node 1.1 (`docs/FORMAT.md` in `projects/window-input`, brief W3). The output is the layer tile format of node 2.1. Both are read as files in tests (`tests/fixtures/`). That is how d7 and d9 work without any link.

**ADR 0001 triggers this node fires, named now:**

- **Trigger 1** ("a second project must run ... as a library") fires for `lag_live` (d10). A live pen stroke cannot go through a file without destroying the measurement, so the brush must receive `InputEvent` values in-process from `projects/window-input`. The move is ADR 0002 (one workload repo with a Cargo workspace, option d2), which is Lazlo's decision and is not planned here. Until he decides, d10 and d11 wait, and d7 to d9 (recorded input and tile files) proceed.
- **Trigger 1 again** if node 2.1's tiled layer must be used in-process rather than through its tile file. Not planned: B7 uses the file format only.
- **Trigger 2** ("a third Rust project needs the same ...") fires if the dab or tile code is later shared with `projects/render` or 2.1. Not planned.

ADR 0004 (`docs/adr/0004-roadmap-repo-map.md`, Proposed) should list node 2.2 as `brush-engine`, with trigger 1 above. That edit is not in this task.

**Fit with the product intent.** Three layers, as in the 1.1 plan: (1) data: `Dab`, `Stroke`, `BrushSettings` and the file formats, portable and std only; (2) maths: pure functions from pen samples to dabs and from dabs to pixels, with no window and no clock; (3) I/O: the event-log reader and the tile file reader. Layers 1 and 2 are testable with no window, so a mode can call them without Win32. Modes receive samples from the shell; the brush never opens a window itself.

## 8. Risks and size

**Risks, with what to do:**

- **R1 The lag method is not yet proved.** Stroke lag is measured from the pen's hardware timestamp to the buffer at the next present, on this PC, with no camera. Krita's lag must be measured by the same definition, but Krita is not our code and its present time is not visible to us. If the same method cannot be applied to Krita, d11 is not a fair comparison, and the node must say so rather than claim it. A camera method (high-speed video of the pen tip and the screen) is the fallback; it is a decision for Lazlo and is outside this plan.
- **R2 Prerequisites and contracts.** 1.1 and 2.1 are not started (section 3), and 2.1 needs 1.2, 1.7 and 1.11 first. B1 to B6 proceed on file contracts only; B7 needs Lazlo's decision that 2.1's tile format is fixed. If he says no, B7 and d9 wait and the node is blocked, not built around.
- **R3 The stabilizer's bound is a design choice.** d5 proves the stabilizer does what its window says. It does not prove the window is the right size for Lazlo's pen. A stabilizer adds lag on purpose, so the d11 comparison must be made with the stabilizer off, and the protocol (B9) says so. If Lazlo wants it on, that is a separate comparison.
- **R4 Live pen injection and the ADR 0002 gate.** d10 and d11 need the live pen path from node 1.1, which fires ADR 0001 trigger 1. Until ADR 0002 is accepted, only the file checks (d1 to d9) can run. The node's Done-when cannot be reached before Lazlo decides ADR 0002.
- **R5 Determinism of golden files.** d2 and d7 compare bytes on one machine. A compiler or CPU change can change `f32` rounding. If that happens, the golden file is regenerated by a deliberate, reviewed step, with the reason written next to it. It is not loosened to a tolerance silently.
- **R6 Memory of large layers.** A 16k x 16k RGBA8 layer is 1 GiB (computed). A brush that writes a flat copy of a layer would fail on a 50-layer image. B7 keeps the brush on tiles; the tile size is 2.1's choice and is a memory decision for Lazlo (section 4).
- **R7 Desktop session.** d10 and d11 fail on a locked or headless session. The plan says "fail loudly, never skip". The orchestrator should run them from the logged-in desktop and expect the failure otherwise.
- **R8 Krita changes between captures.** Krita's version and settings change its stroke pipeline. The version is recorded in `docs/lag-protocol.md` and every capture uses it. A new Krita version means a new capture, not an edit to the old one.
- **R9 The threshold reasons are estimates.** The 16 px stabilizer bound, the 1 px smudge rounding (a fact, not an estimate), the 30-stroke count and the 64 px dab size are design choices. Each is marked in section 1 and must be re-checked when its brief lands.

**Size:** 9 briefs (B1-B9), roughly 250 to 300 lines each, about 2,300 changed lines in all in a new repo, plus the document. Estimate: allow about 2 fix-round tasks, since the first review of the golden-file and tile briefs (B2, B6, B7) is likely to fail. So about 9 merged tasks plus 2 fix rounds to reach the code part of the Done-when. The gated part (B8, B9) adds 2 tasks and 2 human captures (d10, d11) that only Lazlo can run. On the harness's own measure (about 20 merged tasks per delivered stage) this is about 40% of a stage's work, an estimate. Critical path: B1, then B2, then B6 (after B3 and B4), then B8 when gated: four rounds, with B5, B7 and B9 beside them.
