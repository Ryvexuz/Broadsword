Done when: "encode/decode round-trips pass for PNG, EXR, JPEG, WAV and H.264; 4K H.264 plays in real time". The Tier 1 table (line 141) marks it `[wrap first: FFmpeg, OpenEXR]`, and the ground rule for wrap-first nodes is line 16. Broadsword stage (`CAPABILITY_ROADMAP.md:296`, `ROADMAP.md:28`): 9. `ROADMAP.md` status today: not started. Later nodes that need it (`CAPABILITY_ROADMAP.md` Part 2 and `ROADMAP.md`): 3.16 nonlinear video editing (line 196, "Needs: 1.8, 1.9" at line 714), and through the media studio 4.6; 2.1, 3.15 and 3.18 are expected readers of its image and audio files (not stated as Needs in the roadmap).

**Default this plan follows** (Lazlo, 2026-11-19, quoted in the brief): Rust crates first; a C/C++ library only where no mature crate exists, as an exception that is Lazlo's decision through ADR 0003. The result, in short (section 4): WAV and the YUV colour maths are std only; PNG, JPEG and EXR use pure-Rust crates (so OpenEXR is **not** wrapped); H.264 has no mature pure-Rust decoder, so it is the one C/C++ exception, and which library (OpenH264, FFmpeg or Windows Media Foundation) is decision D5.

**Product intent this plan respects** (Lazlo, 2026-11-20): one unified tool over one shared core data model, with a language-neutral core API. This node is a **platform capability under the modes**, not a mode. It turns bytes into plain in-memory media values (`Image`, `AudioBuffer`, `VideoFrame`) and back, owns no scene or document type, and imports no mode. Its contract with other repos is the media files themselves (PNG, EXR, JPEG, WAV, H.264 Annex B are all standard formats) plus a small C ABI (check m20).

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test mediaio`; a program goes through `broadsword run mediaio -- cargo run --offline --release --example mediacheck -- <subcommand> <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. **Each check below relies on exactly one test, and its PASS rule names that test**, so a suite that ran zero tests, or lacks the named test, fails the check. No check relies on a test it does not name.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains".
- `python -I scripts/node_check.py 1.9 --root . --list` lists these blocks and `--run <id>` runs one. It judges only `last line == X`, `contains X` and `exit != 0`, and it needs exit code 0 for every rule except `exit != 0`. Every rule below is `contains` except the (human) one, which it prints as "judge by hand".
- A rule starting `(human)`, or a check marked **(human)**, needs Lazlo: it is never run by an agent and never counts as passed until Lazlo says so. A check marked **(quiet board)** is timing: run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board.
- Programs run with the project folder as their working folder. The one check that writes a file (m19) gives `--out ../../scratch/...`, which is the Broadsword `scratch/` folder from `projects/mediaio`; inside a task worktree (`worktrees/mediaio/<id>`, one level deeper) the same check uses `../../../scratch/...`. Every other program writes only to stdout.
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.
- Words used exactly. **Lossless round trip**: decode(encode(x)) equals x in every sample, compared as bit patterns (`u8`, `u16`, `u32`, or the bits of `f16`/`f32`), so NaN payloads, infinities and `-0.0` must survive. **Lossy round trip**: the decoded result has the exact dimensions, channel count and frame count of the input, and its PSNR is at or above a stated floor. **PSNR** is computed in `f64` over 8-bit samples as 10 log10(255^2 / MSE), per plane, never over an empty image (an empty or all-equal input is a test error, not infinite PSNR). **Independent golden**: a fixture written by a short Python script that uses only the standard library and shares no code with the Rust crate, run once, its output committed with the script beside it.

### Done-when, the whole

The first half, "encode/decode round-trips pass for PNG, EXR, JPEG, WAV and H.264", is checks **m1, m4, m7, m10 and m14** (one round trip per format), with m15 adding the 4K size for H.264. The second half, "4K H.264 plays in real time", is check **m18** (quiet board), which stands on m12 (colour conversion is right) and m17 (the timing check can fail), and is looked at by a person in m19. Every other check proves a part these stand on: independent goldens, bad input, the dependency rules and the C ABI.

**Gap between the Done-when's wording and what this plan proves** (decision D7, risk R1): "plays" here means the frames are decoded and converted to RGBA on time against a 30 fps clock, headless. Showing them in a window needs node 1.1 (window) and node 1.2 (GPU), both not started. The node's final report must say that sentence; it must not call "plays in real time" met on screen.

### Part A: WAV (std only)

**m1 WAV round-trips bit for bit.** For PCM 8-bit unsigned, 16-, 24- and 32-bit signed, and 32-bit IEEE float; for 1, 2 and 6 channels; at 44,100, 48,000 and 96,000 Hz; for lengths 0, 1 and 100,003 frames: write then read returns the same format fields and the same samples, bit for bit.
```check m1
build/bin/broadsword.exe test mediaio > scratch/n19-m1.txt 2>&1
PASS: contains test wav_round_trip_bit_exact_all_formats ... ok
```
Threshold reason: none; lossless means exact. FAIL: the line is missing or says FAILED.

**m2 Our WAV writer matches an independent golden.** `scripts/gen_wav_golden.py` (Python standard library `wave` and `struct` only) writes `tests/fixtures/wav/golden_s16_stereo_48k.wav` and `golden_u8_mono_44k.wav` from a sample formula stated in the script's header. The test computes the same samples, writes them with our writer, and compares the bytes with the fixture (byte for byte); then it reads each fixture with our reader and compares the samples.
```check m2
build/bin/broadsword.exe test mediaio > scratch/n19-m2.txt 2>&1
PASS: contains test wav_writer_matches_python_wave_golden ... ok
```
Why Python's `wave`: it writes only integer PCM with the plain 44-byte header (verify), which is exactly the case where our bytes must match; float and 24-bit are covered by m1 and by the format rules in the module doc comment of `src/wav.rs`.

**m3 Bad WAV input is a named error.** A file shorter than its header, a `RIFF` size larger than the file, a missing `fmt ` or `data` chunk, a `data` size that is not a whole number of frames, a channel count of 0, a sample rate of 0, an unknown format tag, and a `fmt ` chunk that claims more than the caller's `DecodeLimits` allow each return a named `WavError`, never a panic and never a partly filled buffer.
```check m3
build/bin/broadsword.exe test mediaio > scratch/n19-m3.txt 2>&1
PASS: contains test wav_rejects_bad_input ... ok
```

### Part B: PNG (pure-Rust crate, decision D3)

**m4 PNG round-trips losslessly for every colour type.** Grey, grey with alpha, RGB, RGBA, at 8 and 16 bits, and palette at 1, 2, 4 and 8 bits; sizes 1 x 1, 7 x 3 (odd, smaller than one Adam7 pass) and 513 x 257; written then read through our `png` module gives the same pixels bit for bit and the same colour type and bit depth.
```check m4
build/bin/broadsword.exe test mediaio > scratch/n19-m4.txt 2>&1
PASS: contains test png_round_trip_lossless_all_color_types ... ok
```

**m5 PNG decodes an independent golden.** `scripts/gen_png_golden.py` (standard library `zlib`, `struct` and `binascii.crc32` only) writes small PNGs into `tests/fixtures/png/`: one per filter type 0 to 4, one Adam7-interlaced, one 16-bit, one palette with a `tRNS` chunk, one split over three `IDAT` chunks, and next to each a raw `.rgba16` file of the expected pixels. Our decoder's pixels must equal each raw file exactly. This catches a crate or wrapper bug that a round trip through the same crate cannot see.
```check m5
build/bin/broadsword.exe test mediaio > scratch/n19-m5.txt 2>&1
PASS: contains test png_decodes_independent_golden ... ok
```

**m6 Bad PNG input is a named error.** A wrong signature, a bad chunk CRC, a truncated `IDAT`, an `IHDR` with width or height 0, an invalid colour-type and bit-depth pair, and an `IHDR` whose width times height is above the caller's `DecodeLimits` (refused before any pixel buffer is allocated) each return a named `PngError`, never a panic.
```check m6
build/bin/broadsword.exe test mediaio > scratch/n19-m6.txt 2>&1
PASS: contains test png_rejects_bad_input ... ok
```

### Part C: JPEG (pure-Rust crates, decision D3)

**m7 JPEG round-trips within a PSNR floor.** Three generated 8-bit RGB images (a smooth gradient, a colour-bar chart with hard edges, and seeded noise at low amplitude over a gradient), at sizes 1 x 1, 17 x 9 (not a multiple of the 8 x 8 or 16 x 16 block) and 640 x 360, with 4:4:4 and 4:2:0 chroma, at quality 90: decode(encode(x)) has the exact width, height and channel count, and PSNR per channel at or above the floor in `tests/jpeg.rs`. Greyscale input round-trips to greyscale.
```check m7
build/bin/broadsword.exe test mediaio > scratch/n19-m7.txt 2>&1
PASS: contains test jpeg_round_trip_within_psnr_floor ... ok
```
Threshold: a starting floor of 35 dB at quality 90 for the gradient and chart, UNVERIFIED (chosen as a figure commonly quoted for high-quality JPEG; not looked up). Brief M6 measures every case, sets each floor to the measured value minus 1 dB (so a codec regression of more than 1 dB fails), and writes the measured values into this file. The noise image gets its own floor, set the same way. FAIL: any case below its floor, or any size or channel mismatch.

**m8 JPEG error falls as quality rises.** For the same images, mean squared error at quality 50 is greater than at 75, which is greater than at 95. This is the property that proves the quality setting reaches the encoder; a wrapper that ignores it would pass m7 at one setting.
```check m8
build/bin/broadsword.exe test mediaio > scratch/n19-m8.txt 2>&1
PASS: contains test jpeg_quality_orders_error ... ok
```

**m9 Bad JPEG input is a named error.** No SOI marker, a truncated scan, a frame header with 0 width, an unsupported process (for example arithmetic coding, if the decoder crate refuses it; verify), and a header above `DecodeLimits` each return a named `JpegError`, never a panic.
```check m9
build/bin/broadsword.exe test mediaio > scratch/n19-m9.txt 2>&1
PASS: contains test jpeg_rejects_bad_input ... ok
```

### Part E: H.264 (the one C/C++ exception, decision D5)

**m12 YUV to RGB conversion matches the BT.709 formula.** Std only, in `src/yuv.rs`, used by every H.264 path. For the 8-bit limited-range ("TV range", Y 16 to 235, Cb and Cr 16 to 240) BT.709 matrix: the 75% and 100% colour bars, pure black and white, and every (Y, Cb, Cr) on a 17-step grid are converted and compared with an exact `f64` evaluation of the formula in the test, rounded to nearest; 4:2:0 frames of odd width and height convert with the documented chroma siting. The full-range and BT.601 matrices are refused with a named error unless the stream says so (no silent guess).
```check m12
build/bin/broadsword.exe test mediaio > scratch/n19-m12.txt 2>&1
PASS: contains test yuv_to_rgb_matches_bt709_reference ... ok
```
Threshold: at most 1 code value per channel, because the integer fast path and the `f64` reference differ only in rounding. Why this matters: swapping BT.601 and BT.709, or full and limited range, gives a picture that decodes and plays at full speed but has the wrong colours, and no round trip notices it.

**m13 The H.264 library is present and is the pinned one.** The test asks our `h264` module for the library name and version and compares them with the version pinned in `docs/DEPENDENCIES.md` (brief M2). A missing or different library fails the test; it is never skipped.
```check m13
build/bin/broadsword.exe test mediaio > scratch/n19-m13.txt 2>&1
PASS: contains test h264_library_present_and_pinned ... ok
```
Reason: ADR 0003, Kind B: "a recorded library version in test output; one test that fails if the library is missing (no skip)".

**m14 H.264 round-trips within a PSNR floor.** A generated 640 x 360, 30-frame clip (moving colour bars, a moving gradient and a frame number drawn as digits) is encoded to an Annex B elementary stream at a stated fixed bitrate, decoded again, and compared: exactly 30 frames out, in order, with the exact width and height, and per-frame PSNR of the Y plane at or above the floor in `tests/h264.rs`.
```check m14
build/bin/broadsword.exe test mediaio > scratch/n19-m14.txt 2>&1
PASS: contains test h264_round_trip_within_psnr_floor ... ok
```
Threshold: a starting floor of 32 dB per frame on Y, UNVERIFIED (chosen; not looked up). Brief M8 measures the minimum per-frame PSNR at the chosen bitrate, sets the floor to that minimum minus 2 dB, and records both numbers here. FAIL: a frame missing, duplicated or out of order (checked by the frame-number digits, read back from the pixels), a size mismatch, or a frame below the floor.

**m15 H.264 round-trips at 4K.** The same rules at 3840 x 2160 for 3 frames (3 so the test stays short in a debug build; the speed check is m18).
```check m15
build/bin/broadsword.exe test mediaio > scratch/n19-m15.txt 2>&1
PASS: contains test h264_round_trip_4k_three_frames ... ok
```
Why its own check: an encoder or decoder level limit (H.264 levels cap the frame size; verify which level 3840 x 2160 needs and whether the chosen library supports it) shows up only at 4K.

**m16 Bad H.264 input never crashes the process.** A seeded corpus (std xorshift, seeds 1 to 5, 200 variants each) of the m14 stream with truncated NAL units, flipped bytes, a removed SPS or PPS and random garbage is fed to the decoder. Every call returns either decoded frames or a named `H264Error`; the test process survives, and no frame has a size other than the stream's.
```check m16
build/bin/broadsword.exe test mediaio > scratch/n19-m16.txt 2>&1
PASS: contains test h264_rejects_bad_input_without_crash ... ok
```
A crash inside a C library cannot be caught by Rust, so this test is the only evidence that the wrapper checks sizes and return codes before it touches the library's buffers. Error concealment (the library repairing a damaged frame) is allowed and is not an error.

### Part F: 4K H.264 plays in real time

**m17 The timing check can fail.** A test feeds the pacing and percentile code in `src/play.rs` synthetic per-frame times (all 10 ms; one at 40 ms among 600; 1% at 50 ms) and checks that it reports `dropped=0` for the first, the exact dropped count for the others, and that a p99 budget of 33.3 ms passes the first and fails the third. It also checks the clock: a measured busy wait of 5 ms reads at least 5 ms.
```check m17
build/bin/broadsword.exe test mediaio > scratch/n19-m17.txt 2>&1
PASS: contains test play_budget_check_can_fail ... ok
```
Why a test and not a second run with an impossible budget: `node_check.py` needs exit code 0 for a `contains` rule, so a run that is meant to fail cannot be judged by "contains"; and a test of the code with fixed inputs proves the check can fail without a quiet board.

**m18 (quiet board) 4K H.264 decodes and converts in real time.** The example generates a 3840 x 2160, 30 fps, 600-frame (20-second) clip in memory with the m14 pattern and our encoder (not timed), then plays it: a 30 fps clock, a start-up buffer of 8 frames, and for each frame decode plus conversion to RGBA (m12), timed per frame. A frame is **dropped** when it is ready after its presentation time.
```check m18
build/bin/broadsword.exe run mediaio -- cargo run --offline --release --example mediacheck -- play --gen-width 3840 --gen-height 2160 --frames 600 --fps 30 --bitrate-kbps 40000 --buffer-frames 8 --p99-max-ms 33.3 > scratch/n19-m18.txt 2>&1
PASS: contains play: ok width=3840 height=2160 frames=600 dropped=0
```
The program prints `play: ok width=3840 height=2160 frames=600 dropped=0 fps=30 p50_ms=<n> p99_ms=<n> max_ms=<n> library=<name> <version> threads=<n>` and exits 0 only if no frame was dropped and the p99 per-frame time is at most `--p99-max-ms`; otherwise it prints `play: FAIL ...` with the same fields and exits 1. Thresholds and their reasons:
- **33.3 ms p99** is one frame at 30 fps (1000 / 30 = 33.33 ms). **dropped=0** is "real time" with no slack.
- **30 fps** is a choice, UNVERIFIED as "the" 4K rate (decision D7): it is the lower common frame rate; 60 fps doubles the load. Brief M9 also records a 60 fps run as a measurement, not a check.
- **40,000 kbit/s** is a chosen stress bitrate, UNVERIFIED (not looked up; picked to be at the high end of 4K delivery so the decoder is not tested on an easy stream). **8 buffered frames** is a choice, UNVERIFIED (about a quarter of a second at 30 fps).
- The clip is generated, not downloaded, so the check needs no network (decision D8 covers an optional real 4K file). A generated clip is easier to decode than real footage (risk R3), and its profile is whatever our encoder makes (likely Constrained Baseline with OpenH264; verify), so the check proves real time **for that stream**, not for every 4K H.264 file.

**m19 (human) The decoded 4K frame looks right.** The example generates the same clip, decodes it, and writes frame 30 and the matching source frame as PPM images.
```check m19
build/bin/broadsword.exe run mediaio -- cargo run --offline --release --example mediacheck -- frame --gen-width 3840 --gen-height 2160 --frames 60 --fps 30 --bitrate-kbps 40000 --index 30 --out ../../scratch/n19-m19-decoded.ppm --source-out ../../scratch/n19-m19-source.ppm > scratch/n19-m19.txt 2>&1
PASS: (human) the output contains `frame: ok index=30 width=3840 height=2160`, and Lazlo opens scratch/n19-m19-decoded.ppm next to scratch/n19-m19-source.ppm and says yes to all three: (1) the colours of the bars match the source with no green or magenta cast; (2) the digits read 30 in both; (3) no visible blocks, tears or shifted stripes. Any no is a FAIL of the node.
```

### Part G: the repo rules and the language-neutral API

**m20 The C API round-trips through the C functions only.** A Rust test calls only the exported `extern "C"` functions (never the Rust types): decode a PNG from a byte buffer into a caller-supplied RGBA buffer, encode it back, encode a WAV from samples and decode it, read the library version string; then the error cases: a null pointer, a buffer too small, a freed handle, bad bytes. Every error is a named negative code, and a panic inside the library is caught at the boundary and returned as a code.
```check m20
build/bin/broadsword.exe test mediaio > scratch/n19-m20.txt 2>&1
PASS: contains test capi_round_trip_through_extern_c ... ok
```
Video through the C ABI is left to 3.16, which will know what a player needs (section 8, risk R8).

**m21 Every dependency is pinned and on the approved list.** A structure test reads `Cargo.toml` and `Cargo.lock`: every entry in `[dependencies]` and `[dev-dependencies]` is a registry crate with an exact `=x.y.z` version, its name is in the allow-list constant at the top of `tests/structure.rs` (the list Lazlo approves in D3 and D5), no entry has `path` or `git`, and no package in `Cargo.lock` has a `source` other than the crates.io registry.
```check m21
build/bin/broadsword.exe test mediaio > scratch/n19-m21.txt 2>&1
PASS: contains test structure_dependencies_pinned_and_allowed ... ok
```
Reason: ADR 0001 (no Cargo dependency on another repo) and ADR 0003 (pinned, vetted, licence-checked crates). Until brief M2 merges, the allow-list is empty and so is `[dependencies]`.

**m22 No absolute paths and no link into another repo.** The same structure test reads every `.rs`, `.py`, `.toml`, `.h` and `.md` file: none other than `tests/structure.rs` itself contains a drive-letter path (`C:` followed by a slash or backslash), `projects/foundation`, `projects/render` or `projects/crash-sim`.
```check m22

PASS: contains test structure_no_absolute_paths_or_other_repos ... ok
```
