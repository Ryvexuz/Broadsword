# Node 1.8 Timeline framework: infrastructure plan and done checks

**Status: draft: rewrite when the node starts.** Written 2026-11-19 from Broadsword `fefe8b1`, before any code. Nothing in this file has been run: every number, test name and API fact below is a plan to be confirmed by the briefs in section 7, and the first brief that touches a fact it names must correct this file if the fact is wrong.

Node (CAPABILITY_ROADMAP.md, Part 5): *Timeline framework.* Build: tracks, clips, keyframes, curves, playhead and scrubbing, generic across animation, audio and video. Needs: 1.5, 0.6. Done when: one timeline widget drives an animation track, an audio track and a video track. Broadsword stage (ROADMAP.md): 9. ROADMAP.md status today: not started. Later nodes that need it: 2.6 (animation core), 3.16 (nonlinear video editing), 3.17 (motion graphics), 3.18 (DAW features).

Product intent this plan respects (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine, and later animation, audio, video) switches the active crate group, and every mode reads and writes one shared core data model; the core API is language-neutral (C ABI or FFI-friendly, serializable data). So this node is a **shared framework under several modes**, not a mode. Tracks, clips, keyframes and curves are plain serializable data that animation, DAW and video editing all read and write; what a track *means* is supplied by a driver that the owning mode registers behind a small interface, so no mode depends on another mode's internals. Because many modes will read these types, any later change to them is a cross-shard change; that is why the file form (section 5, checks t10 to t12) is versioned from the first commit.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test timeline`; a program goes through `broadsword run timeline -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program. Programs write their results to stdout, so a program's folder (which differs between `projects/timeline` and a task worktree) never matters.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 1.8 --list` lists these blocks and `--run <id>` runs one (ra-node-check). It judges only the rule forms `last line == X` and `contains X`; every other `PASS:` text it prints as "judge by hand". All rules below use `contains`.
- A rule starting `(human)`, or a check marked (human), needs Lazlo: it is never run by an agent and never counts as passed until Lazlo says so. A check marked (quiet board) is timing: run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board.
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.
- Two words used exactly. **Independent golden**: a fixture produced by a short Python script that uses only the standard library and shares no code with the Rust crate, run once, its output committed with the script beside it; the Rust test compares against it. **Sample-accurate**: an event lands on exactly the sample index its time maps to, never one earlier or later.

### Done-when, the whole: one timeline widget drives an animation track, an audio track and a video track

Checks t13 to t21 together are the Done-when; t1 to t12 and t25 to t29 prove the parts it stands on. "Widget" here is the headless `TimelineView` of this crate: it owns the layout, hit-testing, scrubbing and a draw list, and takes input as plain data. Painting it with real GPU or window code is node 1.5's job (section 2, section 8 risk R1), so these checks prove the framework, not the finished on-screen widget. The audio and video tracks are driven by **synthetic sources** (a generated tone, a generated frame pattern), not by decoded files or a sound device, because the codecs (1.9) and the audio device layer (1.10) do not exist yet.

### Part A: time and curves

Time is an integer count of ticks, with 254,016,000,000 ticks per second (a figure the plan takes from Adobe's published Premiere Pro time base; the check below proves the property that matters, so the source is not relied on). It must divide evenly into one frame or one sample of every rate this node uses: 24, 25, 30, 50, 60, 24000/1001, 30000/1001 and 60000/1001 frames per second, and 44100 and 48000 samples per second. Floating-point seconds are never stored.

**t1 Time conversions are exact for every rate.** For each rate above, frame to ticks to frame and sample to ticks to sample round-trip for every index up to 10 minutes' worth, with no rounding.
```check t1
build/bin/broadsword.exe test timeline > scratch/n18-t1.txt 2>&1
PASS: contains test time_conversions_exact_for_all_rates ... ok
```
Threshold reason: none; it is exact integer arithmetic. FAIL: the line is missing or says FAILED. An error of one tick anywhere is a failure.

**t2 Time overflow is a named error.** Adding, subtracting and multiplying times near the `i64` limit returns `TimeError::Overflow`; a rate of zero or a negative rate is `TimeError::BadRate`; nothing panics and nothing wraps.
```check t2
build/bin/broadsword.exe test timeline > scratch/n18-t2.txt 2>&1
PASS: contains test time_overflow_is_named_error ... ok
```

**t3 Curves match an independent golden.** Linear, step (hold), cubic Bezier (the CSS `cubic-bezier(x1, y1, x2, y2)` form, solved for x by bisection or Newton) and cubic Hermite (the glTF `CUBICSPLINE` form) are sampled at 1001 points each over several key pairs, and compared with `tests/fixtures/curve_golden.csv`, which `scripts/gen_curve_golden.py` wrote.
```check t3
build/bin/broadsword.exe test timeline > scratch/n18-t3.txt 2>&1
PASS: contains test curve_matches_independent_golden ... ok
```
Threshold reason: the test allows an absolute difference of at most 1e-9, because both sides compute in `f64` and differ only in operation order; a bug in a formula moves values by far more. FAIL: any single sample outside 1e-9.

**t4 Bad curve input is a named error.** NaN or infinite key values, two keys at the same time, keys out of order, a Bezier handle whose x is outside the segment (which would make the curve fold back on itself) are each refused with a named error, and a sample outside the key range clamps to the first or last value.
```check t4
build/bin/broadsword.exe test timeline > scratch/n18-t4.txt 2>&1
PASS: contains test curve_rejects_bad_input ... ok
```

### Part B: tracks, clips and keyframes as reversible edits

Every change to a timeline is an `Edit` value that, when applied, returns its exact inverse. This is the same pattern as node 0.6 (command and undo) and is deliberately small, so 0.6 can wrap or replace it later without the timeline importing 0.6 (section 2).

**t5 Keyframe edits keep the order.** A seeded property test (5 fixed seeds, 2,000 random insert, move and delete operations each) checks after every step that a curve's keys are strictly increasing in time, with no duplicates.
```check t5
build/bin/broadsword.exe test timeline > scratch/n18-t5.txt 2>&1
PASS: contains test keyframe_edits_keep_order_property ... ok
```

**t6 Splitting then joining a clip returns the original.** For random clips and random split points (including the first and last tick, which must be refused), split followed by join gives a clip equal to the original, and the source offset of the right-hand part is exactly the left part's length.
```check t6
build/bin/broadsword.exe test timeline > scratch/n18-t6.txt 2>&1
PASS: contains test clip_split_join_round_trip ... ok
```

**t7 Clip edits refuse bad ranges and overlaps.** On one track, a clip may not overlap another; a clip with a negative or zero length, an end before its start, or a source range past the source's length is refused with a named error, and a refused edit changes nothing.
```check t7
build/bin/broadsword.exe test timeline > scratch/n18-t7.txt 2>&1
PASS: contains test clip_edits_reject_overlap_and_bad_ranges ... ok
```

**t8 10,000 random edits then full undo returns exactly to the start.** This is node 0.6's own Done-when, applied to the timeline: 5 fixed seeds, 10,000 random edits each (keyframe, clip, track add and remove, move, trim), then undo all, then compare the whole timeline with the saved start state (full equality, not a hash).
```check t8
build/bin/broadsword.exe test timeline > scratch/n18-t8.txt 2>&1
PASS: contains test random_edits_then_full_undo_10000 ... ok
```
Threshold reason: 10,000 is the number in the roadmap line for node 0.6. FAIL: any seed ends in a state that differs from the start, or any edit panics.

**t9 Redo after full undo returns the end state.** Same runs: after undoing everything, redoing everything equals the state before the undo, and a new edit after an undo clears the redo stack.
```check t9
build/bin/broadsword.exe test timeline > scratch/n18-t9.txt 2>&1
PASS: contains test redo_after_full_undo_returns_end_state ... ok
```

### Part D: one track kind at a time (the drivers)

A **driver** is the small interface that gives a track kind its meaning. The framework stores clips and keyframes; the driver turns "this track at this time" into a value (animation), a block of samples (audio) or a frame number (video). Drivers sit behind one trait whose calls pass only plain data (time ranges, buffers of numbers, ids), so the same interface can be exposed through a C ABI (Part G).

**t13 An animation track matches an independent golden.** Three channels (a position, a rotation and a scale, each with different curve types) are sampled at every frame of a 5-second clip at 30 frames per second, and compared with `tests/fixtures/anim_golden.csv` and `scripts/gen_anim_golden.py`. The target of each channel is a path string such as `car/wheel_fl/rotation_y`; the driver writes `(path, value)` pairs to a sink and never touches a scene.
```check t13
build/bin/broadsword.exe test timeline > scratch/n18-t13.txt 2>&1
PASS: contains test anim_track_matches_independent_golden ... ok
```
Threshold reason: an absolute difference of at most 1e-9 (same reason as t3).

**t14 Audio clips start and end on exactly the right sample.** One second at 48,000 Hz: a synthetic 1,000 Hz tone clip placed at tick-time 0.25 s must have sample 11,999 equal to exactly 0.0 and sample 12,000 equal to the first tone sample; the clip's end is the same, and a clip placed at a time that is not a sample boundary at 48,000 Hz is rounded by a rule the test names (round half down), with the rounding stated in `docs/FORMAT.md`.
```check t14
build/bin/broadsword.exe test timeline > scratch/n18-t14.txt 2>&1
PASS: contains test audio_clip_boundaries_sample_accurate ... ok
```

**t15 Audio output does not depend on the block size.** The same two-clip, fading timeline is rendered in blocks of 1, 64, 480, 1000 and 4096 samples and in one pass; every result is bit-identical (compared as `u32` bit patterns, not as floats).
```check t15
build/bin/broadsword.exe test timeline > scratch/n18-t15.txt 2>&1
PASS: contains test audio_block_size_independent ... ok
```
Why this matters: a real audio device asks for blocks of whatever size it likes; a renderer whose output changes with the block size clicks or drifts on a real device.

**t16 Audio matches an independent golden.** The tone is computed from the sample index (phase in `f64`, never accumulated), linear fade in and out over a stated number of samples, summed over two overlapping tracks, compared with `tests/fixtures/audio_golden.bin` (little-endian `f32`) and `scripts/gen_audio_golden.py`.
```check t16
build/bin/broadsword.exe test timeline > scratch/n18-t16.txt 2>&1
PASS: contains test audio_matches_independent_golden ... ok
```
Threshold reason: an absolute difference of at most 1e-6 per sample. `f32` has about 6e-8 of relative precision, so 1e-6 leaves room for operation-order differences and is 30 times below the size of one 16-bit step (1/32768, about 3.05e-5), so any real formula or phase error is caught and rounding noise is not.

**t17 Video frame selection is exact for every rate.** A video clip with a source frame rate of 24, 25, 30000/1001 and 60 frames per second, placed on a timeline of a different frame rate, with a trim offset: for every timeline frame of a 10-minute clip, the source frame index equals the documented rule (the source frame whose interval contains the timeline frame's start tick; ties at a boundary go to the later frame), checked against an exact integer computation in the test, with no off-by-one at the first frame, the last frame or any trim point. The synthetic source's frame `n` is a generated image that encodes `n` in its pixels, and the test reads `n` back from the pixels, so the check covers the frame actually returned, not only an index.
```check t17
build/bin/broadsword.exe test timeline > scratch/n18-t17.txt 2>&1
PASS: contains test video_frame_selection_exact_all_rates ... ok
```

**t18 The playhead follows the audio clock with no drift over one simulated hour.** A fake audio clock advances in blocks of 480 samples at 48,000 Hz for 3,600 seconds; after every block the playhead time is the audio clock's time (the audio is the master), and the video frame chosen for that playhead equals the exact rule of t17. At the end the playhead is exactly 3,600 seconds in ticks, and the largest gap between the playhead and the audio clock is 0 ticks.
```check t18
build/bin/broadsword.exe test timeline > scratch/n18-t18.txt 2>&1
PASS: contains test playhead_audio_master_no_drift_one_hour ... ok
```
Threshold reason: zero, because both sides are integers; a nonzero gap means a float crept in. The hour is the length used by node 1.10's own dropout check ("no dropouts over a one-hour run"), here done in simulated time (it takes seconds, not an hour).

### Part E: the widget

**t19 Pixel and time convert both ways.** For zoom levels from 1 pixel per second to 96,000 pixels per second (2 pixels per audio sample at 48,000 Hz, the most a waveform editor needs) and for scroll offsets at both ends of a 10-hour timeline, time to pixel to time returns the same tick to within one pixel's worth of ticks, and hit-testing a point inside a clip, on its left or right edge (trim handle), on a keyframe, on the ruler and on empty space returns the matching target.
```check t19
build/bin/broadsword.exe test timeline > scratch/n18-t19.txt 2>&1
PASS: contains test view_hit_test_round_trip ... ok
```
Threshold reason: 96,000 is a chosen stress figure, not a published number; it can be changed with a reason.

**t20 The draw list matches a golden.** A fixed timeline (the one in the v1 fixture) with a fixed view size and zoom produces a draw list (rectangles, lines and text items with integer pixel coordinates and a colour id, in a plain text format) that equals `tests/fixtures/widget_scrub.drawlist` byte for byte, for three states: playhead at the start, playhead mid-clip, and a clip being dragged.
```check t20
build/bin/broadsword.exe test timeline > scratch/n18-t20.txt 2>&1
PASS: contains test view_drawlist_matches_golden ... ok
```
The golden is written by hand-checked first run and then reviewed by eye once (t24); after that it is regression protection, not proof of looks.

**t21 One widget drives an animation, an audio and a video track.** One `TimelineView` holds one timeline with three tracks (one of each kind) and one playhead. Scripted input, as plain data (a click on the ruler, a drag of the playhead, a drag of a clip, a scrub across the whole timeline in 1,000 steps), is fed to that one view. After each step the test asks the same view for the three drivers' outputs at the playhead and compares them with t13, t16 and t17's rules: the animation value, the audio block at the playhead, and the video frame index. A clip drag also appears as one `Edit` on the undo stack, and one undo puts all three tracks back.
```check t21
build/bin/broadsword.exe test timeline > scratch/n18-t21.txt 2>&1
PASS: contains test one_widget_drives_three_track_kinds ... ok
```
FAIL: more than one view or playhead instance is used, a track kind is driven by anything other than the view's own scrub call, or any of the three outputs differs from its rule.

**t22 Scrubbing a large timeline is fast.** (quiet board.) The example builds a timeline of 100 tracks with 100,000 clips in all (generated in the program, no file), then scrubs the playhead across it and times each full evaluation of every track at the playhead.
```check t22
build/bin/broadsword.exe run timeline -- cargo run --offline --release --example scrub_bench -- --clips 100000 --p99-max-us 2000 > scratch/n18-t22.txt 2>&1
PASS: contains scrub_bench: ok clips=100000
```
The program prints `scrub_bench: ok clips=100000 tracks=100 p50_us=<n> p99_us=<n> max_us=<n>` and exits 0 only if p99 is at most `--p99-max-us`. Threshold reason: 2,000 us is one eighth of a 60 Hz frame (16,667 us), because the playhead evaluation must leave the rest of the frame to the editor shell, which has its own 60 fps target with 20 panels (node 1.5). It is a **budget, not a published benchmark**, and a placeholder: after the first quiet-board run the brief replaces it with the measured p99 times 2 and records the measurement in this file. The count of 100,000 clips is a chosen stress figure (about 10 times the clips of a long edited film, a number the plan has not looked up), not a published one.

**t23 The scrub check can fail.** Same example, an impossible budget.
```check t23
build/bin/broadsword.exe run timeline -- cargo run --offline --release --example scrub_bench -- --clips 100000 --p99-max-us 1 > scratch/n18-t23.txt 2>&1
PASS: contains scrub_bench: FAIL p99
```
(quiet board.) Expected: `run: FAILED (exit 1)`. Reason for 1 us: evaluating 100 tracks cannot take under a microsecond; if this ever prints `ok`, the clock or the percentile code is wrong. FAIL: `scrub_bench: ok` (the check cannot fail, so t22 proves nothing).

**t24 (human) The timeline looks like a timeline.** The example draws the widget with a minimal built-in software rasteriser (filled rectangles and 5 by 7 bitmap text, std only) into a PPM image of the three-track timeline, with the playhead mid-clip.
```check t24
build/bin/broadsword.exe run timeline -- cargo run --offline --release --example render_timeline -- --out scratch/n18-t24.ppm > scratch/n18-t24.txt 2>&1
PASS: contains render_timeline: ok width=1280 height=360
```
(human.) The program part passes when the line above is printed and the file exists; the check counts as passed only when Lazlo has opened `scratch/n18-t24.ppm` and said it shows three tracks, clips with their names, keyframes on the animation track, a waveform-like block on the audio track, and a visible playhead.

### Part F: the language-neutral API

The timeline's data and its calls must be reachable from other languages (Lazlo, 2026-11-20: upper layers may use languages other than Rust). The API is a C ABI: opaque handles, `#[repr(C)]` plain structs, integer error codes, and the file format as the way to move a whole timeline.

**t25 The API works through the C functions.** A Rust test calls the exported `extern "C"` functions only (never the Rust types): create a timeline, add three tracks, add clips and keys, scrub, read the animation value, an audio block and a video frame index, undo, save to a buffer, load it back, free.
```check t25
build/bin/broadsword.exe test timeline > scratch/n18-t25.txt 2>&1
PASS: contains test capi_round_trip_through_extern_c ... ok
```

**t26 The API returns errors, never panics.** A null handle, a freed handle, a handle used twice after free, a buffer too small, a bad track id and bad times each return a named negative error code; a panic inside the library is caught at the boundary and also returned as a code.
```check t26
build/bin/broadsword.exe test timeline > scratch/n18-t26.txt 2>&1
PASS: contains test capi_error_codes_not_panics ... ok
```

**t27 The header matches the exported functions.** `include/timeline.h` lists exactly the `#[no_mangle] extern "C"` functions and the `#[repr(C)]` structs in `src/capi.rs`, with the same names and field order, no more and no fewer.
```check t27
build/bin/broadsword.exe test timeline > scratch/n18-t27.txt 2>&1
PASS: contains test capi_symbols_match_header ... ok
```

**t28 A second language drives the core.** The test builds nothing itself: it finds the shared library that Cargo built next to the test program, starts `python -I tests/ctypes_smoke.py <library path>`, and the script (Python standard library `ctypes` only) creates a timeline, adds a keyframe track and a clip, scrubs, reads a value, saves and reloads, and prints `ctypes_smoke: ok value=<v>`. The Rust test passes only if Python exits 0 and printed that line with the value the Rust side expects.
```check t28
build/bin/broadsword.exe test timeline > scratch/n18-t28.txt 2>&1
PASS: contains test ctypes_smoke_python_drives_core ... ok
```
If Python is not on the PATH the test fails loudly with a named error; it is never skipped.
