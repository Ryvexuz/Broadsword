## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test mesh-kernel`; a program goes through `broadsword run mesh-kernel -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails. The same convention is used by node 1.1 (`docs/nodes/1.1.md`, section 1).
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 2.3 --list` lists these blocks and `--run <id>` runs one. It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text, including every `(human)` rule, is printed as "judge by hand". Never use `--run --all` on this node: run one id at a time.
- A negative control (a check that must fail on purpose, m12) is written as `PASS: exit != 0`. Its expected output line is read by hand from the saved file. It is only meaningful when its positive twin (m11) has passed with the same example.
- A rule starting `(human)` is never run by an agent and never counts as passed until Lazlo says so. A rule marked `(quiet board)` is timing: run it only while no build, test or review is running (check `broadsword status`), and rerun it, never average over a busy board.
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.
- Units: every size is a triangle count or a byte count; every time is in milliseconds, read from `std::time::Instant` in the example. No check compares against a published benchmark (section 6).

### Done-when line 1: a boolean on two 100k-triangle meshes is watertight

"Watertight" is defined once here so every check uses the same meaning: a closed mesh in which every undirected edge has exactly two faces with opposite orientation, every vertex's face fan is a single closed cycle (no non-manifold vertex), and the Euler characteristic V - E + F equals 2 for each connected closed component. The check is the function `is_watertight` (brief M2), and the boolean checks call it.

**m1 The crate has no dependencies.** ADR 0001 forbids a Cargo dependency (path or git) on another repo; the crate also takes no crate from crates.io in this node (section 4).
```check m1
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m1.txt 2>&1
PASS: contains test cargo_toml_has_no_dependencies ... ok
```
The test reads `Cargo.toml` and requires the `[dependencies]`, `[dev-dependencies]` and `[build-dependencies]` tables to be empty or absent. FAIL: the line is missing or says FAILED.

**m2 The mesh generators give exact triangle counts.** Every boolean check needs two closed meshes of exactly 100,000 triangles each, made by code and seeded, so the input is the same on every run (section 5).
```check m2
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m2.txt 2>&1
PASS: contains test generated_box_has_exact_triangle_count ... ok
```
The test builds a closed box subdivided into exactly 100,000 triangles and checks that `is_watertight` accepts it. A square n x n grid per box face gives 12 n^2 triangles, and 100,000 / 12 is not a whole square, so the generator cannot use a plain grid; the brief M1 fixes the method (for example, uneven rows on one face, with the count checked by the test). Threshold reason: 100,000 is the Done-when number. FAIL: the count is not exactly 100,000, or the mesh is not watertight.

**m3 The half-edge mesh round-trips.** Building a half-edge mesh from indexed triangles and writing the triangles back gives the same indexed triangles, up to the order of vertices and faces the structure defines.
```check m3
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m3.txt 2>&1
PASS: contains test halfedge_round_trip_from_triangles ... ok
```
Threshold reason: none; it is an exact round trip. FAIL: the line is missing or says FAILED.

**m4 Half-edge invariants hold on random closed meshes.** For each of 1,000 seeded closed meshes, every half-edge has a twin, every `next` cycle closes around one face, and every vertex's outgoing half-edges form one cycle. The meshes are generated by jittering the generator's vertices, so they stay closed.
```check m4
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m4.txt 2>&1
PASS: contains test halfedge_invariants_random_meshes ... ok
```
Threshold reason: 1,000 seeds is an estimate: enough to hit degree-3, degree-6 and boundary-looking vertices many times over, cheap enough to run in the foreground. FAIL: any invariant breaks, reported with its seed.

**m5 Normals and UVs match reference values.** A unit cube's face normals are exactly the six axis vectors. A UV sphere's vertex normals equal the normalised vertex positions within 1e-6. A UV attribute round-trips through the attribute store unchanged.
```check m5
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m5.txt 2>&1
PASS: contains test normals_match_reference ... ok
```
Threshold reason: 1e-6 is an estimate for f64 arithmetic on unit vectors (about 1e-15 expected; 1e-6 leaves room for `normalize` order of operations). FAIL: any normal is off by more than 1e-6.

**m6 Catmull-Clark subdivision gives the known counts.** One level on a cube gives 26 vertices, 48 edges and 24 faces; two levels give 98, 192 and 96. Both levels have Euler characteristic 2.
```check m6
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m6.txt 2>&1
PASS: contains test catmull_clark_cube_counts ... ok
```
Reference: these numbers come from the Catmull-Clark counting rules (V' = V + E + F, E' = 2E + 4F, F' = 4F for quads, starting from V=8, E=12, F=6). They are arithmetic from those rules, not a measured result; the rules and their citation are in section 6. FAIL: any count or the Euler characteristic differs.

**m7 Isotropic remeshing gives edges in a band.** Remeshing a 100,000-triangle sphere to a target edge length L leaves every edge within [0.6 L, 1.5 L] after the final pass.
```check m7
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m7.txt 2>&1
PASS: contains test remesh_edge_lengths_within_band ... ok
```
Threshold reason: estimate. The band is a plan choice, not a published number; the first brief that runs it (M5) records the measured spread and replaces the band with a reason. FAIL: any edge outside the band, or the output is not watertight.

**m8 The orientation predicate is exact on near-degenerate input.** Points that lie almost exactly on a plane are classified correctly for every case in a fixed list (including exactly coplanar points, and points one ulp off the plane). A floating-point determinant that gets one of these wrong fails the test.
```check m8
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m8.txt 2>&1
PASS: contains test orientation_predicate_exact_on_near_degenerate ... ok
```
Reason: a boolean that uses a plain float test can produce a mesh with cracks, which is exactly what "watertight" forbids. The exact predicates are the reason m7 and m10 can hold on coplanar faces. FAIL: any classification is wrong.

**m9 The boolean matches an analytic volume.** The union, intersection and difference of two axis-aligned boxes, each subdivided to 100,000 triangles and overlapping by a known amount, have volumes equal to the closed-form box formulas within a relative error of 1e-9.
```check m9
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m9.txt 2>&1
PASS: contains test boolean_union_volume_reference ... ok
```
Reference: exact box arithmetic (section 6, no download). Threshold reason: 1e-9 relative is an estimate for f64 sums over about 100,000 triangles: round-off is about 1e-12 per term, so 1e-9 leaves margin. FAIL: any relative error above 1e-9.

**m10 The boolean result is watertight.** Union, intersection and difference of the m9 inputs each pass `is_watertight`, and each result is a single connected component (or the expected number, which the test states).
```check m10
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m10.txt 2>&1
PASS: contains test boolean_result_watertight ... ok
```
This is the test form of the Done-when line; m11 is the form at the Done-when size. FAIL: any result fails `is_watertight`.

**m11 The Done-when boolean, at 100k triangles per input, is watertight (positive run).** The example builds two generated 100,000-triangle meshes (m2's generator), runs their union, prints the result and the time it took.
```check m11
build/bin/broadsword.exe run mesh-kernel -- cargo run --offline --release --example boolean_bench -- --tris 100000 > scratch/n23-m11.txt 2>&1
PASS: contains boolean_bench: ok tris_a=100000 tris_b=100000 watertight=true
```

The program prints `boolean_bench: ok tris_a=<n> tris_b=<n> watertight=true ms=<n>` and exits 0 only if the result passes `is_watertight`; otherwise it prints `boolean_bench: FAIL <reason>` and exits 1. The `ms=` field is a record, not a gate, at this stage: the first quiet-board run writes it to `docs/nodes/2.3.md` and no timing budget is set until then (estimate: none yet; R5 in section 8). (quiet board) for the time it prints; the pass rule itself does not depend on the board.

### Done-when line 2: the modifier stack is fully non-destructive and undoable

"Non-destructive" means: evaluating the stack never changes the base mesh; the base mesh's bytes are the same before and after any number of evaluations, and changing a modifier's settings re-evaluates from the untouched base. "Undoable" follows node 0.6's standard, applied to the stack: 10,000 random stack edits followed by full undo return exactly to the starting state.

**m13 Evaluating the stack leaves the base mesh untouched.** The test builds a base mesh and a stack of subdivision, remesh and boolean modifiers, evaluates it several times and compares the base's serialised bytes before and after.
```check m13
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m13.txt 2>&1
PASS: contains test modifier_stack_leaves_base_untouched ... ok
```
Threshold reason: exact byte equality; no tolerance. FAIL: any byte differs.

**m14 The stack is undoable.** A seeded test makes 10,000 random stack edits (add, remove, reorder and change a setting), then undoes them all, checking the stack after every undo. The end state must equal the start state byte for byte; a redo walk back to the end must also match.
```check m14
build/bin/broadsword.exe test mesh-kernel > scratch/n23-m14.txt 2>&1
PASS: contains test modifier_stack_10000_edits_undo_to_start ... ok
```
Threshold reason: 10,000 is the node-0.6 standard (`docs/nodes/0.6.md`, line 3), so the two nodes are judged the same way. The undo log is a copy of the 0.6 pattern in this repo (section 2), not a dependency. FAIL: the end state differs or any step is unrecoverable.
