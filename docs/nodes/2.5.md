## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test realtime-render`; a program goes through `broadsword run realtime-render -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed` (the same output shape the 1.1 plan quotes from `docs/nodes/1.1.md` section 1). A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 2.5 --list` lists these blocks and `--run <id>` runs one (ra-node-check, `scripts/node_check.py` lines 3-22). It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text (every `(human)` rule, and every rule ending `(quiet board)` or `(gpu)` that is not one of the three forms) it prints as "judge by hand". A command that exits non-zero is always a FAIL unless its rule is `exit != 0`. A negative control (a check that must fail on purpose: c9, c11 and c16) is written as `PASS: exit != 0`; its expected output line is then read by hand from the saved file. Such a control is only meaningful when its positive twin has passed with the same example. Never use `--run --all` on this node while a `(human)` block is in it: run one id at a time and leave the `(human)` ids to Lazlo.
- A rule starting `(human)` needs Lazlo and his eyes or hardware. An agent never runs it and it never counts as passed until Lazlo says so.
- A check marked `(gpu.)` in its text needs a Vulkan or DX12 adapter in the PC (section 4). If there is no adapter the check fails loudly with a named error; it is never skipped. Its PASS rule is still one of the three forms above.
- A check marked `(quiet board)` in its text is timing: run it only while `broadsword status` shows no build, test or review running, and rerun it, never average over a busy board. This plan has no timing check with a pass threshold (section 8, R9).
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example, test or reference file is missing.
- Reference images (c15 and c16) are read from `reference/khronos-2.5/`, which is outside Git (the same rule `docs/nodes/REFERENCE_DATA.md` Part A sets for `reference/camry-2013/`). They do not exist until Lazlo approves the download (section 4). Until then c15 and c16 FAIL with "reference set missing", which is the correct result.

### The Done-when line: the Khronos glTF sample models match their reference renders

The Done-when line has no numbers. This plan turns it into three measurable parts, and each number below is a **draft** until the first brief that uses it measures it (section 6 says what to measure).

- **Match:** for every model in the chosen set, the renderer's image at the fixed camera and environment has a mean absolute error per 8-bit channel of at most `--tolerance-mean` and a 99th-percentile per-channel error of at most `--tolerance-p99` (values in 8-bit steps, 0-255).
- **Reference:** the reference images are produced once, outside this node, by the Khronos glTF Sample Viewer at the same camera and environment (section 6, decision D7 in section 4). The renderer never generates its own reference for c15.
- **Tolerance:** `--tolerance-mean 2` and `--tolerance-p99 16` are **estimates**. Source: none yet. Reason: anti-aliasing and the viewer's shader differ by a few steps per pixel, so 2 steps mean is a guess. Brief P4 measures the noise floor (the same render twice, and two renders of the viewer's reference), and the thresholds are then set to a value a bit above that floor. Lesson 39 applies: the floor is measured with the same arms run twice, not taken from one run.

**c1 The crate has no dependencies.** The structure test of brief P1 (section 7).
```check c1
build/bin/broadsword.exe test realtime-render > scratch/n25-c1.txt 2>&1
PASS: contains test cargo_toml_has_no_dependencies ... ok
```
Threshold reason: none needed; the test reads `Cargo.toml` and requires empty dependency tables (ADR 0001 forbids a Cargo dependency on another repo, and ADR 0003 is Proposed). FAIL: the line is missing or says FAILED.

**c2 The BRDF matches the glTF 2.0 reference formulas.** Brief P2.
```check c2
build/bin/broadsword.exe test realtime-render > scratch/n25-c2.txt 2>&1
PASS: contains test brdf_reference_values ... ok
```
The test writes the glTF 2.0 Appendix B formulas (GGX distribution, Smith height-correlated visibility, Schlick Fresnel, Lambert diffuse) in f64 and compares f32 results with a relative tolerance of 1e-5 (estimate: f32 round-off over about 20 operations is about 1e-6). Source of the formulas: section 6, row R1.

**c3 The BRDF does not create energy.** Brief P2.
```check c3
build/bin/broadsword.exe test realtime-render > scratch/n25-c3.txt 2>&1
PASS: contains test brdf_directional_albedo_bounded ... ok
```
For roughness 0.05 to 1.00 in steps of 0.05, metallic 0 and 1, the directional albedo (the integral of BRDF times cosine over the hemisphere, on a 256 by 256 grid) must not exceed 1.01. Reason: a physically based BRDF cannot reflect more light than arrives. The 0.01 margin is an estimate for the grid error; brief P2 measures it and records the value in the test.

**c4 sRGB encoding round-trips for all 256 values.** Brief P3.
```check c4
build/bin/broadsword.exe test realtime-render > scratch/n25-c4.txt 2>&1
PASS: contains test srgb_round_trip_all_256 ... ok
```
Exact: each 8-bit value encoded to linear and back returns the same value. The transfer function is the sRGB definition (section 6, row R3), so the reference is the formula, not a sample set.

**c5 The tonemapper matches its reference values.** Brief P3.
```check c5
build/bin/broadsword.exe test realtime-render > scratch/n25-c5.txt 2>&1
PASS: contains test tonemap_neutral_reference_values ... ok
```
The reference is the Khronos PBR Neutral tone mapping definition (section 6, row R4). The test compares 16 hand-chosen inputs with values computed from that definition, tolerance 1e-5 (estimate, as c2).

**c6 PPM images round-trip byte for byte, and a fault is seen.** Brief P4.
```check c6
build/bin/broadsword.exe test realtime-render > scratch/n25-c6.txt 2>&1
PASS: contains test ppm_round_trip_byte_identical ... ok
```
The reference images of c15 and the renderer's own output use binary PPM (P6), as the render repo does (`projects/render/tests/golden.rs`). The test reads a committed fixture and writes it back. Mutation step (lesson 10): change one pixel byte in the writer and show this test failing, then restore.

**c7 The comparison metric sees a one-step fault.** Brief P4.
```check c7
build/bin/broadsword.exe test realtime-render > scratch/n25-c7.txt 2>&1
PASS: contains test compare_rejects_fault_image ... ok
```
The test compares an image with itself (error 0) and with a copy where one channel of every pixel is +3 (mean error 3 is above the draft `--tolerance-mean 2`; the test asserts the comparator reports it). Reason: a metric that cannot see a 3-step shift would pass every model. Lesson 40: the same test also asserts that a +1 shift is NOT rejected at the draft tolerance, so a stricter comparator is caught too.

**c8 The CPU reference renders a sphere that matches the analytic shading.** Brief P5.
```check c8
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example cpu_sphere > scratch/n25-c8.txt 2>&1
PASS: contains cpu_sphere: ok
```
The example renders a unit sphere at a fixed camera, one directional light and no shadows with a known analytic answer (the value at each pixel from the same formulas). It prints `cpu_sphere: ok max_err=<n>` only when the largest per-channel error is at most 1 step (a quantisation bound: one 8-bit step, the smallest error an 8-bit image can show). Otherwise `cpu_sphere: FAIL` with the pixel and the error. This check tests the CPU reference that c10 and c15's comparator depend on; it does not test GPU code.

**c9 The sphere check can fail.** Negative control of c8, brief P5.
```check c9
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example cpu_sphere -- --corrupt-light > scratch/n25-c9.txt 2>&1
PASS: exit != 0
```
Expected: the run exits non-zero and the saved file contains `cpu_sphere: FAIL` (read by hand). `--corrupt-light` adds 40 steps (40/255) to the light's intensity before rendering. FAIL: `cpu_sphere: ok` (the comparison cannot see a visibly wrong light), which would make c8 proof of nothing.

**c10 The GPU sphere matches the CPU reference.** Brief P6, gated (gpu): needs ADR 0003 accepted and a pinned wgpu (section 4, D2).
```check c10
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example gpu_sphere > scratch/n25-c10.txt 2>&1
PASS: contains gpu_sphere: ok
```
(gpu.) The example renders the c8 scene on the GPU offscreen (no window) and compares it with the CPU reference of c8 using the comparator of c7. It prints `gpu_sphere: ok adapter=<name> max_err=<n>` only when the mean error is at most 2 steps and the 99th-percentile error at most 16 steps (the drafts of section 1). `adapter=<name>` is printed so that a run on a different GPU is visible in the log. Threshold reason: the same as the Done-when draft; a GPU and a CPU compute the same formula in different precision, so a bound of one step (c8) is too strict across two precisions. Brief P6 measures this value and replaces the draft if needed.

**c11 The GPU sphere check can fail.** Negative control of c10, brief P6 (gpu).
```check c11
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example gpu_sphere -- --corrupt-light > scratch/n25-c11.txt 2>&1
PASS: exit != 0
```
(gpu.) Expected: non-zero exit and `gpu_sphere: FAIL` in the file (read by hand). FAIL: `gpu_sphere: ok`. Positive twin: c10 must have passed with the same example.

**c12 Shadows: the shadow map matches the CPU reference with a box occluder.** Brief P7 (gpu).
```check c12
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example shadow_check > scratch/n25-c12.txt 2>&1
PASS: contains shadow_check: ok
```
(gpu.) A sphere on a plane with a box between the light and the plane. The example compares the GPU image with the CPU reference (c8 extended with shadows in brief P7) under the c7 comparator, and also requires the shadow's edge to be inside the box's projection (a shifted shadow map fails). Threshold: the c10 draft. Reason: shadow acne and peter-panning are the two usual faults; the mean tolerance does not see a shadow that is slightly too large, so the edge test is required.

**c13 Image-based lighting: the GPU prefiltered environment and BRDF table match the CPU generator.** Brief P8 (gpu).
```check c13
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example ibl_check > scratch/n25-c13.txt 2>&1
PASS: contains ibl_check: ok
```
(gpu.) The example prints `ibl_check: ok lut_max_err=<n> env_max_err=<n>` only when the BRDF table (as in the split-sum approximation, section 6 row R2) and the prefiltered environment mip levels each agree with the CPU generator within 2 steps, and the environment's mip 0 equals the source image exactly (estimate for the 2 steps: the table is stored in 8 bits).

**c14 The glTF reader loads the first sample set, and a bad file is a named error.** Brief P9. Gated on decision D8 (section 4: a minimal glTF reader in this repo or the 2.4 contract).
```check c14
build/bin/broadsword.exe test realtime-render > scratch/n25-c14.txt 2>&1
PASS: contains test gltf_reads_fixture_and_rejects_bad_files ... ok
```
The test reads the hand-written fixture `tests/fixtures/triangle.gltf` (one triangle, one material, base64 buffer; section 5) and a set of bad files (unknown `asset.version`, a buffer shorter than its accessor, an index out of range). Each bad file must give a named error and none may panic.

**c15 The Khronos sample models match their reference renders within tolerance.** This is the Done-when check. Brief P9 creates the example; brief P10 adds its flags. Gated on the reference set being on disk (section 4, D5 and D6).
```check c15
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example khronos_compare -- --set reference/khronos-2.5/set.txt --refs reference/khronos-2.5 --tolerance-mean 2 --tolerance-p99 16 > scratch/n25-c15.txt 2>&1
PASS: contains khronos_compare: ok
```
(gpu.) The example renders each model listed in `set.txt` at the camera and environment in `reference/khronos-2.5/MANIFEST.md`, compares it with the reference image in `--refs` under the c7 comparator, and prints one `model <name> mean=<n> p99=<n>` line per model. It prints `khronos_compare: ok models=<n>` only when every model is within both tolerances. Otherwise `khronos_compare: FAIL <model> ...` and exit 1. Thresholds: the drafts in section 1 (estimates, measured by brief P4 and P9).

**c16 A failing model is named, not hidden.** Negative control of c15, brief P9.
```check c16
build/bin/broadsword.exe run realtime-render -- cargo run --offline --release --example khronos_compare -- --set reference/khronos-2.5/set.txt --refs reference/khronos-2.5 --tolerance-mean 0 --tolerance-p99 0 > scratch/n25-c16.txt 2>&1
```

**c17 Tonemapping, TAA, bloom and the debug views work.** Brief P10 (gpu). These are in the Build line, not the Done-when line, so they get their own check.
