## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test realtime-render`; a program goes through `broadsword run realtime-render -- cargo run --offline --release --example <name> -- <flags>`.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed` (the same output shape the 1.1 plan quotes from `docs/nodes/1.1.md` section 1). A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule that names a program line is judged with "contains", because the last line is the run's own.
- `python -I scripts/node_check.py 2.5 --list` lists these blocks and `--run <id>` runs one (ra-node-check, `scripts/node_check.py` lines 3-22). It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`. Every other `PASS:` text (every `(human)` rule, and every rule ending `(quiet board)` or `(gpu)` that is not one of the three forms) it prints as "judge by hand". A command that exits non-zero is always a FAIL unless its rule is `exit != 0`. A negative control (a check that must fail on purpose: c9, c11 and c16) is written as `PASS: exit != 0`; its expected output line is then read by hand from the saved file. Such a control is only meaningful when its positive twin has passed with the same example. Never use `--run --all` on this node while a `(human)` block is in it: run one id at a time and leave the `(human)` ids to Lazlo.
- A rule starting `(human)` needs Lazlo and his eyes or hardware. An agent never runs it and it never counts as passed until Lazlo says so.
- A check marked `(gpu.)` in its text needs a Vulkan or DX12 adapter in the PC (section 4). If there is no adapter the check fails loudly with a named error; it is never skipped. Its PASS rule is still one of the three forms above.
- A check marked `(quiet board)` in its text is timing: run it only while `broadsword status` shows no build, test or review running, and rerun it, never average over a busy board. This plan has no timing check with a pass threshold (section 8, R9).
- Anything not PASS is FAIL, including a check that cannot run because a flag, file, example, test or reference file is missing.
- Reference images (c15 and c16) are read from `reference/khronos-2.5/`, which is outside Git (the same rule `docs/nodes/REFERENCE_DATA.md` Part A sets for `reference/camry-2013/`). They do not exist until Lazlo approves the download (section 4). Until then c15 and c16 FAIL with "reference set missing", which is the correct result.

### The Done-when line: the Khronos glTF sample models match their reference renders

The Done-when line has no numbers. This plan turns it into three measurable parts, and each number below is a **draft** until the first brief that uses it measures it (section 6 says what to measure).

- **Match:** for every model in the chosen set, the renderer's image at the fixed camera and environment has a mean absolute error per 8-bit channel of at most `--tolerance-mean` and a 99th-percentile per-channel error of at most `--tolerance-p99` (values in 8-bit steps, 0-255).
- **Reference:** the reference images are produced once, outside this node, by the Khronos glTF Sample Viewer at the same camera and environment (section 6, decision D7 in section 4). The renderer never generates its own reference for c15.
- **Tolerance:** `--tolerance-mean 2` and `--tolerance-p99 16` are **estimates**. Source: none yet. Reason: anti-aliasing and the viewer's shader differ by a few steps per pixel, so 2 steps mean is a guess. Brief P4 measures the noise floor (the same render twice, and two renders of the viewer's reference), and the thresholds are then set to a value a bit above that floor. Lesson 39 applies: the floor is measured with the same arms run twice, not taken from one run.

**c3 The BRDF does not create energy.** Brief P2.
```check c3

PASS: contains test brdf_directional_albedo_bounded ... ok
```

For roughness 0.05 to 1.00 in steps of 0.05, metallic 0 and 1, the directional albedo (the integral of BRDF times cosine over the hemisphere, on a 256 by 256 grid) must not exceed 1.01. Reason: a physically based BRDF cannot reflect more light than arrives. The 0.01 margin is an estimate for the grid error; brief P2 measures it and records the value in the test.

**c8 The CPU reference renders a sphere that matches the analytic shading.** Brief P5.

## 2. Home

**A new repo, `projects/realtime-render`, crate `realtime_render` (library, Rust 2021, std plus the GPU crates of section 4 once Lazlo accepts them), created by brief P1.** It is its own Git repo, ignored by the Broadsword repo, like `projects/render` (`broadsword.toml` `projects_dir = "projects"`). It is registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, as `projects/render/Cargo.toml` does (its comment and `[workspace]` are at lines 9-10, read on 2026-11-21).

Creating the repo is Lazlo's approval (decision D1 in section 4), as for node 1.2. This plan creates nothing.

Under ADR 0001 (Accepted, option a, `docs/adr/0001-shared-core.md` status line):

- **No Cargo dependency (path or git) on another repo.** The crate does not depend on `projects/render`, `projects/gpu` (the node 1.2 repo, if it exists by then), `projects/crash-sim`, `projects/foundation` or any other repo. The plan never links into `projects/foundation`. Checked by c1.
- **Copies, per repo.** Small pieces are copied from the patterns already in the repos, not imported: the `f32` vector and matrix code (pattern: `projects/render/src/math.rs`, 172 lines; ADR 0001 says the copies stay per repo), the binary PPM reader and writer (pattern: `projects/render/src/framebuffer.rs`), and the test pattern (`projects/render/tests/golden.rs`). Each copy is named in its brief.
- **The GPU layer is this repo's own.** If node 1.2's `projects/gpu` exists when this node starts, its WGSL files and its `BufferLayout` text (`docs/nodes/1.2.md` section 2) are read as the contract (files, not code). Otherwise this repo's brief P6 writes the wgpu glue itself. Both are allowed by option a. Choosing between them is a question for Lazlo, not for the brief (section 4, D2).
- **The contract between repos is a file.** The inputs are glTF 2.0 files (the Khronos sample models, section 6) and the reference PPM images (section 4, D5); the outputs are PPM images. Another repo can read the same files without a link to this crate.

**ADR 0001 triggers this node will fire, named now rather than discovered:**

- **Trigger 1** ("a second project must run ... as a library") fires in two cases. (i) If this node takes a path or git dependency on node 1.2's `projects/gpu`, the GPU code is shared by two repos. The plan does not do that: it is the choice that keeps c1 green. (ii) If node 2.4 (scene system, `docs/nodes/ORDER.md` line 46, no plan file) must hand this renderer live scene objects in-process, the renderer needs 2.4's crate. The plan avoids that too: the renderer reads glTF files itself (brief P9, own reader, decision D8). The move to one workload repo with a Cargo workspace (ADR 0002, option d2, Lazlo's decision) is what either case needs. It is not planned here.
- **Trigger 2** ("a third Rust project needs the same ...") fires if the render repo ever replaces its software rasterizer with this crate's code. Its `src/raster.rs` is a CPU rasterizer with a shadow map and one directional light (its module comment at lines 1-3, read on 2026-11-21). This node does not reuse it: the render repo draws in software into a framebuffer, and this node draws on the GPU. Not planned.

ADR 0004 (`docs/adr/0004-roadmap-repo-map.md`, Status: Proposed) should list node 2.5 as `realtime-render`, with triggers 1 and 2 above. Recorded here so that ADR 0004 revision has the input. It is not changed by this plan.

**Fit with the product intent.** The crate has four layers, so a mode never depends on the GPU and a test never needs a window or a GPU:

1. **Data:** `Camera`, `Light`, `Material` (glTF metallic-roughness values), `Mesh` (positions, normals, tangents, UVs, indices as plain `Vec` of `f32` and `u32`), `Scene` (a flat list of draws with a transform), `Settings` (tonemapper, bloom, TAA on or off, debug view). Plain data, std only, no GPU types.
2. **CPU reference:** pure functions from `Scene` and `Camera` to an `Image` (BRDF, tonemapping, sRGB, the analytic sphere of c8). Portable and std only. Every GPU result is compared with it.
3. **GPU backend:** `gpu.rs`, `shadow.rs`, `ibl.rs`, `taa.rs`, `bloom.rs`, `debug.rs` and their WGSL files, behind one `Renderer` trait so a mode can ask for a picture without knowing the backend. Offscreen only in this node; presenting to a window is node 1.1 and 1.5's job.
4. **Examples:** the checks of section 1 (`cpu_sphere`, `gpu_sphere`, `shadow_check`, `ibl_check`, `khronos_compare`, `post_check`).

Modes will call the renderer through `Renderer::render(&Scene, &Camera, &Settings) -> Image`. Modes never open a GPU device themselves, which keeps "no mode depends on another mode" true for rendering too. Multiple views of one scene are several calls with different cameras, the same idea as node 1.1's two windows.

**Fixtures to make** (small text or binary files, committed in the new repo, each made by brief P4 or P9):

- `tests/fixtures/ppm_round_trip.ppm`: a 4 by 2 P6 image, bytes written by hand (P4, for c6).
- `tests/fixtures/triangle.gltf`: one triangle with a base64 buffer, one metallic-roughness material (base colour 1, 0, 0; metallic 0.5; roughness 0.5), no textures (P9, for c14). Its numbers are written by hand from the glTF 2.0 spec's accessor rules, not generated by the reader under test.
- No scene fixture files. The sphere, the box and the plane of c8 and c12 are generated in `src/testscene.rs` from formulas, so the test scene is code that can be read, not a binary that can drift.
- Bad glTF files for c14 are strings built inside the test.
- No recorded data, no sample models in the repo. The Khronos models live only in `reference/khronos-2.5/` (outside Git, section 4 D5) and are read by path.

**Golden images.** A small set of golden PPMs (up to 64 by 64 pixels, about 12 KB each, as `projects/render/tests/golden/` does) is committed for regression of the CPU reference (brief P5) and of the GPU result (brief P6). They are regression guards, not references: they say "the output did not change", and c15 says "the output matches Khronos". A golden is re-made only with a reason written in `docs/nodes/2.5.md`.

**Mutation steps** (lesson 10: a new test must be shown to fail). Each brief that adds a test changes one line, shows the named test failing, and restores it:

- P2: square the roughness twice in the GGX term (`alpha` used where `alpha*alpha` is required); show `brdf_reference_values` failing.
- P3: move the sRGB linear break from 0.04045 to 0.0404; show `srgb_round_trip_all_256` failing.
- P4: write one byte of the PPM body wrong; show `ppm_round_trip_byte_identical` failing. Set the comparator's mean to take the maximum instead; show `compare_rejects_fault_image` failing.
- P5: flip the light's sign in the CPU sphere; show `cpu_reference_sphere_matches_analytic` failing and `cpu_sphere` printing FAIL.
- P9: read the accessor offset as zero; show `gltf_reads_fixture_and_rejects_bad_files` failing.
- P10: change the TAA blend weight to 1.0 (no history); show `post_check` failing its convergence part.

**Tests that need a GPU.** Every GPU test begins by asking for an adapter. If none is found it fails with the named error `no GPU adapter` (the same rule as `gpu_sphere`), so a suite run on a machine without a GPU is red, not green. Tests do not print success for a skipped adapter (the "never skip" rule of section 1).

**Quiet-board benchmarks.** None. Done-when has no time target, and this plan does not invent one. If the renderer's frame time is printed at all (c17's example may do so), it is a log line with no pass rule. A frame-time budget is a later decision for Lazlo, with a source, when a node needs one (section 8, R9).

**The first run of each arm is not the baseline** (lesson 39). The noise floor for c15 is measured by brief P4 and P9 by running the same comparison twice, and the second run is the one that sets the draft tolerance. The threshold is then changed in this file with the measured value and the reason, not silently in the example.
