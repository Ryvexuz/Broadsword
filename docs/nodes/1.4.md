# Node 1.4: Text and fonts (plan, ahead-work)

**Status: draft: rewrite when the node starts.** Written 2026-11-20 from `CAPABILITY_ROADMAP.md` Part 5 (node 1.4) and `ROADMAP.md` (row 1.4: `not started`, Broadsword stage 4). No code, no downloads and no repo exists yet. Everything below is a plan: the program names, flags, test names and fixture files in section 1 are the ones the briefs in section 7 create, and they are not real until those briefs merge. Every threshold is a starting value (marked), to be confirmed by the brief named next to it. Crate versions, font names and licences are written from memory and are confirmed by brief X2 before anything depends on them.

- Build (roadmap): font loading, shaping, layout, rich text rendering.
- Done when (roadmap): ligatures and mixed scripts render correctly; a one-million-line document scrolls smoothly.
- Needs (roadmap): 1.3 (2D vector renderer). See section 3: the Done-when can be met without importing 1.3.

**Product intent this plan respects** (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared core data model. So this node is a **platform capability under the modes**, not a mode. It takes plain data in (UTF-8 bytes, a span table of style ranges, font files as bytes) and gives plain data out (a layout: glyph runs with font id, glyph id and position; and CPU-rendered coverage images). It owns no scene, mesh, material or editor-document type, and it imports no mode's internals. The editor shell (node 1.5) and the code editor core (node 2.10) decide what text a panel shows; this node only turns text into glyphs and pixels. Because the layout and the span table will be read by many modes, they have a versioned, serializable form from the first commit (section 1, check 1.4.14), and any later change to them is a cross-shard change in the harness's terms. The API is **language-neutral on purpose**: the public entry points take and return bytes and opaque handles through a small C ABI, so layers above the foundation may be written in another language.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`; inside a task add `--task <id>` after the project name. Never call cargo directly. Never pipe a broadsword command: each one is redirected to a file in `scratch/` and the file is read.
- Programs run with the project folder (`projects/text`) as the working folder, so paths such as `tests/fonts` are relative to it. Output paths the programs write (`--dump`) are written as `../../scratch/...`, which resolves to the Broadsword `scratch/` folder from that working folder, never to `projects/text/scratch`.
- `broadsword run` prints its own job lines first and `--- summary ---` and `run: ok (...)` or `run: FAILED (exit N)` last. `broadsword test` ends `test: ok — N passed, 0 failed`. "PRINTS" below means the program's own lines.
- Program contract (created by briefs X1 to X10, see section 7). `textcheck` is `examples/textcheck/main.rs` in the `text` crate, with one subcommand per module file: `fonts`, `shape`, `bidi`, `mixed`, `render`, `scroll`, `abi`. Exit code 0 means PASS, 1 means a compared value broke its threshold (FAIL), 2 means a usage error or a missing file (never a silent skip). Every flag is required and has no default (a missing one is a usage error, exit 2), except the ones shown in `[brackets]`: `--disable-feature` and `--inject-fault` are given only by the planted-fault checks 1.4.4, 1.4.10 and 1.4.13, and when absent the normal path runs.
  - `fonts --dir <folder> --facts <file>`
  - `shape --cases <file> [--disable-feature <tag>]`
  - `bidi --file <file>`
  - `mixed --file <file> --fonts <folder>`
  - `render --case <ligature|mixed|rich> --golden <file> --max-diff <0-255> --max-bad-frac <fraction> --dump <folder> [--inject-fault <no-liga|no-bidi>]`
  - `scroll --lines <n> --frames <n> --window <n> --seed <n> --max-p99-ms <x> --max-frame-ms <x> --max-heap-mb <n> [--inject-fault <skip-line>]`
  - `abi --roundtrip`
- Blocks marked **[human]** need Lazlo. Blocks marked **[quiet board]** are timing and run only when no other job is running (confirm that by reading the job list under `state/jobs/` first).
- A fixture, golden file or `.ttf` named below does not exist until its brief merges. Nothing is downloaded by this plan (section 6).

### 1.4.1 Fonts load, and the facts match

```check 1.4.1
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- fonts --dir tests/fonts --facts tests/fixtures/font_facts.txt > scratch/text14-1.txt 2>&1
PASS: `run: ok`, and one line per font file `fonts file=<name> family=<text> units_per_em=<n> glyphs=<n> cmap_ok=1 facts=match` for every file named in `tests/fixtures/font_facts.txt`, followed by `fonts total=<n> mismatches=0` with n equal to the number of font files in `tests/fonts` (at least 4). An empty file list is a FAIL (n of 0).
PRINTS: one line per font and the total line.
```

Threshold reason (the 4): decision D4 needs four distinct jobs from the font set, and each job needs its own file: a Latin font with `fi`/`ffi`/`fl` ligatures, a second face of that family for the rich-text weight, an Arabic font and a Hebrew font; Devanagari makes five. Four is the least that still covers ligatures, weights and the two right-to-left scripts. It is a starting value; brief X2 sets the real list and the count follows it.

Reason: "font loading" has to be shown on real fonts. The expected `units_per_em`, glyph count and cmap lookups (a few code points mapped to glyph ids) in `font_facts.txt` are read from the font's own tables by a second, independent std-only table reader inside the test (X3), so the loader is not compared with itself.

### 1.4.12 A one-million-line document scrolls smoothly **[quiet board]**

```check 1.4.12
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- scroll --lines 1000000 --frames 600 --window 60 --seed 1 --max-p99-ms 16.7 --max-frame-ms 33.4 --max-heap-mb 1024 > scratch/text14-12.txt 2>&1
PASS: `run: ok` and the line `scroll lines=1000000 frames=600 window=60 open_ms=<a> p50_ms=<b> p99_ms=<c> max_ms=<d> peak_heap_mb=<e> shaped_max=<f> verify_mismatches=0 result=PASS` with c at most 16.7, d at most 33.4, e at most 1024, f at most 120 (the window of 60 lines plus a margin of 60: only the visible lines are shaped, never the whole document), a at most 10000 (a hung-open detector only; no target is invented for open time), and `verify_mismatches=0`.
PRINTS: the one scroll line.
```

Thresholds, and where each comes from:

- **16.7 ms p99** is one frame at 60 fps (1000 / 60 = 16.67 ms). **33.4 ms max** is two frames: a single slow frame is allowed, a long stall is not. Both are starting values: the Done-when says "smoothly" and sets no number, so this plan reads it as "60 fps with no visible stall". X9 measures the real values and may tighten them; loosening needs a reason written in `docs/NODE14_SCROLL.md`.
- **1024 MB peak heap** is a starting value. The document text is about 60 MB (1,000,000 lines of about 60 bytes), its line index is 8 MB, so a limit near ten times that catches a copy per line without failing on normal overhead. Measured by a counting global allocator in the example (std only), because std has no process-memory call.
- **A frame** means: find the visible lines from the scroll position, shape and lay out those lines (a cache may hold recent lines), build the glyph draw list, and rasterize it to a 1280 x 720 coverage buffer on the CPU. It is the CPU cost of one frame. Presenting to a window or the GPU belongs to nodes 1.1, 1.2 and 1.5; the check says so by name and does not claim them.
- **The scroll path**: 200 frames of steady scrolling (3 lines per frame), then 5 jumps to the middle and to the end, then 395 frames of random jumps and drags from a seeded generator, so the cache cannot make every frame cheap.
- **The document** is generated in memory from the seed (not stored): 1,000,000 lines of seeded text, mostly Latin with some lines containing ligature pairs and some Arabic and Hebrew lines, line length 0 to 120 characters and about 60 on average (so the text is about 60 MB). Lines are not wrapped here (code-editor style); wrapping is covered by layout tests on the visible window (section 8 names this as a limit).
- `verify_mismatches` counts frames where the text of a visible line, read back through the viewport, differs from the generator's text for that line number. It proves the virtual window shows the right lines.


## 2. Home

- **Repo and crate:** a new, separate repo `projects/text` with one library crate `text` (lib name `text`, built as both `rlib` and `cdylib` only when brief X10 adds the C ABI; before that `rlib`), the example program `textcheck` (a folder `examples/textcheck/` with one module per subcommand), and its own Cargo workspace (`[workspace]` in `Cargo.toml`, as render and crash-sim do, so it does not attach to the Broadsword workspace). Created by the orchestrator at Lazlo's approval (decision D1). No repo is created by this plan.
- **ADR 0001 (Accepted, option a):** separate repos, file formats are the contract, no Cargo dependency (path or git) on another repo without a new ADR, which is Lazlo's call. This node needs nothing from any other repo: the glyph rasterizer, the layout code and the CPU references live inside `projects/text`. In particular it does **not** import node 1.3's vector renderer even though the roadmap says 1.3 is needed; it carries its own small coverage rasterizer for glyph outlines (brief X6). That is a deliberate copy, and it is the second copy of "fill a path to coverage" in the planned repos once 1.3 exists (ADR 0001 trigger 2 counts copies of shared code across projects; the rasterizer is the one to watch). Never a link into `projects/foundation`.
- **When another repo needs this code it fires an ADR 0001 trigger.** Node 1.5 (UI shell), node 2.10 (code editor core) and node 3.17 (motion graphics text animators) all need `text` as a library. That is trigger 1 ("a second project must run ... as a library"). It means ADR 0002 and the move to option d2 (one workload repo, a Cargo workspace) before any of them depends on `text`. This plan does not plan that dependency and does not ask for it.
- **Contract with other repos is data, not types:** UTF-8 bytes, a span table (ranges with font, size, weight, italic, colour), font files as bytes, and an output layout in the versioned text wire form `bwtext 1` (check 1.4.14), documented in `docs/NODE14_ABI.md`. This is also the language-neutral surface asked for in the product intent: a small `extern "C"` API with opaque handles and byte buffers, and no Rust type across the boundary.
- **Crate-group fit:** `text` is a capability crate under the modes. Modeling, rendering and the engine are expected to reach it only through that public API and the wire form, never through its internals. The crate reads no core scene type. If the shared core later defines a text or style type, that type is converted at the border by the editor shell; this crate does not change.
- **Window, GPU and editor:** this node is checked on the CPU and headless. Presenting to a window needs node 1.1, a GPU glyph atlas needs node 1.2, and a text widget needs node 1.5. None of them is in this plan. When they need glyph data they receive it through the layout wire form or the C ABI, as plain values.

## 4. External needs

All of the following except std are decisions for Lazlo. Nothing is fetched until he approves (network access and new dependencies are "ask first"). Rust crates are preferred and are vetted, pinned and vendored; no C/C++ library is planned.

- **D1. A new repo `projects/text`** (plan only).

Crates, from the Rust registry only, exact versions pinned (`=x.y.z`), `Cargo.lock` committed, licences read on pinning:** `ttf-parser` (reads OpenType and TrueType tables, outlines, cmap, metrics), `rustybuzz` (a Rust port of HarfBuzz: OpenType shaping, ligatures, Arabic joining, Indic conjuncts), `unicode-bidi` (UAX 9 bidirectional algorithm), `unicode-segmentation` (grapheme clusters, UAX 29) and `unicode-linebreak` (line break opportunities, UAX 14, for wrapping). Font files, vendored in `tests/fonts/`:** about five open-licence fonts: one Latin serif or sans that has `fi`, `ffi` and `fl` ligatures in its GSUB table (Noto Serif is the first candidate; X2 must read its GSUB table and confirm, and pick another if it has none), one regular and one bold or italic of the same family for the rich-text case, Noto Sans Arabic (joining forms, lam-alef), Noto Sans Hebrew and Noto Sans Devanagari. Source and licence in section 6 (SIL Open Font License 1.1, from memory; X2 reads each font's own licence file and records it). The files are binary and add several MB to the repo (not measured here); the licence texts travel with them in `tests/fonts/LICENSES.md`. Downloading them is a network decision for Lazlo and a licence decision (D4 is both).
- **D5. Which scripts count as "mixed scripts":** the plan chooses Latin, Hebrew, Arabic and Devanagari (right to left, joining, and conjuncts: the three hard cases). CJK is left out because a CJK font is tens of MB and CJK needs no shaping for the Done-when; Lazlo may add it (one more font file and one more `mixed` line).
- **D6. 1.3 reuse or copy** (section 3): the plan assumes copy. It is Lazlo's call.
- **GPU access and memory (graphics-heavy: no for this node).** Everything runs on the CPU: a 1280 x 720 coverage buffer is under 1 MB and the document is about 60 MB. A GPU glyph atlas is later work (nodes 1.2 and 1.5); when that starts it is graphics-heavy, the PC shares memory between system RAM and the GPU, and Lazlo moves it first. Agents never touch the memory split.
- **Build cost:** the crates add a few dozen transitive crates (rustybuzz brings Unicode data crates). The shared build folder grows by an amount not measured here; X2's first build follows a free-space check against the 20 GB disk floor.
- **Hardware:** none. No tablet, gamepad, audio device or second PC. A browser on Lazlo's PC is used for the human check (1.4.11); no download for it.
- **Network data:** the Unicode conformance files and the HarfBuzz test data in section 6 are fetched once at X5 and X4 (a subset is copied into fixtures with its source URL and licence). That is network use and needs Lazlo's yes (D3 may cover it if he says so).

## 8. Risks and size

- **Crate APIs and font facts are from memory.** Names, licences and the claim that Noto Serif has `fi` ligatures are unchecked. Mitigation: X2 reads the pinned crates' docs and the fonts' tables before any code depends on them, and corrects this file.
- **Two readers and goldens are weaker than a person.** The Done-when says "render correctly". Checks 1.4.3 and 1.4.5 compare with other people's data, and 1.4.11 needs Lazlo. If he is not available, the node is not done; it is not passed on goldens alone.
- **"Smoothly" is read as a number the plan chose** (16.7 ms p99 CPU frame). If Lazlo means a stricter or looser reading, or means frames on screen, the threshold and the check change. The scroll check has no wrapping, no window and no GPU; a million wrapped lines need a height index (prefix sums of line heights), which is not in the Done-when and is not planned here.
- **Memory of one million lines.** If shaping caches are sized wrongly the heap limit fails. The limit is a guess until X9 measures it.
- **The rasterizer copy.** Quality (anti-aliasing, hinting, subpixel positioning) of a small fill is lower than a mature one. The Done-when needs correct glyphs, not beautiful ones. Reusing 1.3 would cost an ADR (D6).
- **ADR 0001 trigger 1 fires as soon as a second repo wants this crate.** Nodes 1.5, 2.10 and 3.17 do. The plan works for this node alone; the next node that needs `text` stalls until ADR 0002 (Lazlo). The API is data and handles, so the code needs no change when that happens.
- **Unified-tool intent.** If the shared core later fixes a text or style type, or changes the glyph run layout, that is a cross-shard change. The wire form and the ABI are the only places it appears, which limits the blast radius to X10's files. A second-language caller is not tested in this node (check 1.4.14 says so).
- **Size.** Ten briefs reach the Done-when (X1 to X10), about 2,300 changed lines in total if each stays near 230, plus the font and golden binaries. Two of them (X1, X2) are setup (skeleton, pins, fonts) and eight (X3 to X10) are code with the tests and fixtures the checks run. A usable text stack for a code editor (node 2.10) needs more: editing and an undo-friendly buffer (a rope), hit testing and caret movement, selection, vertical metrics for mixed fonts on one line, wrapping with a height index, a glyph atlas on the GPU, OpenType features beyond ligatures (kerning pairs, small caps), and emoji. A rough estimate is 8 to 12 more briefs after the Done-when, not planned here.
