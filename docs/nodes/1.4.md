# Node 1.4: Text and fonts (plan, ahead-work)

**Status: draft: rewrite when the node starts.** Written 2026-11-20 from `CAPABILITY_ROADMAP.md` Part 5 (node 1.4) and `ROADMAP.md` (row 1.4: `not started`, Broadsword stage 4). No code, no downloads and no repo exists yet. Everything below is a plan: the program names, flags, test names and fixture files in section 1 are the ones the briefs in section 7 create, and they are not real until those briefs merge. Every threshold is a starting value (marked), to be confirmed by the brief named next to it. Crate versions, font names and licences are written from memory and are confirmed by brief X2 before anything depends on them.

- Build (roadmap): font loading, shaping, layout, rich text rendering.
- Done when (roadmap): ligatures and mixed scripts render correctly; a one-million-line document scrolls smoothly.
- Needs (roadmap): 1.3 (2D vector renderer). See section 3: the Done-when can be met without importing 1.3.

**Product intent this plan respects** (Lazlo, 2026-11-20): one unified tool, where picking a mode (modeling, render, engine) switches the active crate group, and every mode reads and writes one shared core data model. So this node is a **platform capability under the modes**, not a mode. It takes plain data in (UTF-8 bytes, a span table of style ranges, font files as bytes) and gives plain data out (a layout: glyph runs with font id, glyph id and position; and CPU-rendered coverage images). It owns no scene, mesh, material or editor-document type, and it imports no mode's internals. The editor shell (node 1.5) and the code editor core (node 2.10) decide what text a panel shows; this node only turns text into glyphs and pixels. Because the layout and the span table will be read by many modes, they have a versioned, serializable form from the first commit (section 1, check 1.4.14), and any later change to them is a cross-shard change in the harness's terms. The API is **language-neutral on purpose**: the public entry points take and return bytes and opaque handles through a small C ABI, so layers above the foundation may be written in another language.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`; inside a task add `--task <id>` after the project name. Never call cargo directly. Never pipe a broadsword command: each one is redirected to a file in `scratch/` and the file is read.
- Programs run with the project folder (`projects/text`) as the working folder, so paths such as `tests/fonts` are relative to it.
- `broadsword run` prints its own job lines first and `--- summary ---` and `run: ok (...)` or `run: FAILED (exit N)` last. `broadsword test` ends `test: ok — N passed, 0 failed`. "PRINTS" below means the program's own lines.
- Program contract (created by briefs X1 to X10, see section 7). `textcheck` is `examples/textcheck/main.rs` in the `text` crate, with one subcommand per module file: `fonts`, `shape`, `bidi`, `mixed`, `render`, `scroll`, `abi`. Exit code 0 means PASS, 1 means a compared value broke its threshold (FAIL), 2 means a usage error or a missing file (never a silent skip). Every flag a check uses is required and has no default (a missing one is a usage error, exit 2).
  - `fonts --dir <folder> --facts <file>`
  - `shape --cases <file> [--disable-feature <tag>]`
  - `bidi --file <file>`
  - `mixed --file <file> --fonts <folder>`
  - `render --case <ligature|mixed|rich> --golden <file> --max-diff <0-255> --max-bad-frac <fraction> --dump <folder> [--inject-fault <no-liga|no-bidi>]`
  - `scroll --lines <n> --frames <n> --window <n> --seed <n> --max-p99-ms <x> --max-frame-ms <x> --max-heap-mb <n> [--inject-fault <skip-line>]`
  - `abi --roundtrip`
- Blocks marked **[human]** need Lazlo. Blocks marked **[quiet board]** are timing and run only when no other job is running (confirm that by reading the job list under `state/jobs/` first).
- A fixture, golden file or `.ttf` named below does not exist until its brief merges. Nothing is downloaded by this plan (section 6).

### 1.4.1 Fonts load, and the facts match

```check 1.4.1
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- fonts --dir tests/fonts --facts tests/fixtures/font_facts.txt > scratch/text14-1.txt 2>&1
PASS: `run: ok`, and one line per font file `fonts file=<name> family=<text> units_per_em=<n> glyphs=<n> cmap_ok=1 facts=match` for every file named in `tests/fixtures/font_facts.txt`, followed by `fonts total=<n> mismatches=0` with n equal to the number of font files in `tests/fonts` (at least 4). An empty file list is a FAIL (n of 0).
PRINTS: one line per font and the total line.
```

Reason: "font loading" has to be shown on real fonts. The expected `units_per_em`, glyph count and cmap lookups (a few code points mapped to glyph ids) in `font_facts.txt` are read from the font's own tables by a second, independent std-only table reader inside the test (X3), so the loader is not compared with itself.

### 1.4.3 Ligatures and shaping match the expected glyphs

```check 1.4.3
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- shape --cases tests/fixtures/shape_cases.txt > scratch/text14-3.txt 2>&1
PASS: `run: ok`, one line per case `shape case=<name> glyphs=<n> expected=<m> ids_match=1 result=PASS`, and a last line `shape total=<n> failed=0` with n at least 12. Where the expected ids come from (must be stated per case in the file): either the HarfBuzz or rustybuzz test data (section 6) for the same font, or read by hand from the font's GSUB table with the independent reader from 1.4.1 (the ligature glyph name appears in the font). A case whose expected value was copied from the code's own output is not allowed; each case line carries a `source=` field naming where it came from.
```

### 1.4.12 A one-million-line document scrolls smoothly **[quiet board]**

```check 1.4.12
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- scroll --lines 1000000 --frames 600 --window 60 --seed 1 --max-p99-ms 16.7 --max-frame-ms 33.4 --max-heap-mb 1024 > scratch/text14-12.txt 2>&1
PASS: `run: ok` and the line `scroll lines=1000000 frames=600 window=60 open_ms=<a> p50_ms=<b> p99_ms=<c> max_ms=<d> peak_heap_mb=<e> shaped_max=<f> verify_mismatches=0 result=PASS` with c at most 16.7, d at most 33.4, e at most 1024, f at most 120 (the window of 60 lines plus a margin of 60: only the visible lines are shaped, never the whole document), a at most 10000 (a hung-open detector only; no target is invented for open time), and `verify_mismatches=0`.
PRINTS: the one scroll line.
```

Thresholds, and where each comes from:

- **16.7 ms p99** is one frame at 60 fps (1000 / 60 = 16.67 ms). **33.4 ms max** is two frames: a single slow frame is allowed, a long stall is not. Both are starting values: the Done-when says "smoothly" and sets no number, so this plan reads it as "60 fps with no visible stall". X9 measures the real values and may tighten them; loosening needs a reason written in `docs/NODE14_SCROLL.md`.
- **1024 MB peak heap** is a starting value. The document text is about 60 MB (1,000,000 lines of about 60 bytes), its line index is 8 MB, so a limit near ten times that catches a copy per line without failing on normal overhead. Measured by a counting global allocator in the example (std only), because std has no process-memory call.
- **A frame** means: find the visible lines from the scroll position, shape and lay out those lines (a cache may hold recent lines), build the glyph draw list, and rasterize it to a 1280 x 720 coverage buffer on the CPU. It is the CPU cost of one frame. Presenting to a window or the GPU belongs to nodes 1.1, 1.2 and 1.5; the check says so by name and does not claim them.
- **The scroll path**: 200 frames of steady scrolling (3 lines per frame), then 5 jumps to the middle and to the end, then 395 frames of random jumps and drags from a seeded generator, so the cache cannot make every frame cheap.
- **The document** is generated in memory from the seed (not stored): 1,000,000 lines of seeded text, mostly Latin with some lines containing ligature pairs and some Arabic and Hebrew lines, line length 0 to 200 characters. Lines are not wrapped here (code-editor style); wrapping is covered by layout tests on the visible window (section 8 names this as a limit).
- `verify_mismatches` counts frames where the text of a visible line, read back through the viewport, differs from the generator's text for that line number. It proves the virtual window shows the right lines.

### 1.4.14 The layout leaves the crate as data, and the C ABI works

```check 1.4.14
build/bin/broadsword.exe run text -- cargo run --offline --release --example textcheck -- abi --roundtrip > scratch/text14-14.txt 2>&1
PASS: `run: ok` and the line `abi version=1 glyph_runs=<r> glyphs=<g> serialized_bytes=<b> roundtrip=identical null_handle=rejected` with r at least 3, g at least 40, b above 0. The program calls only the `extern "C"` functions of the crate (opaque handles, bytes in, bytes out, no Rust type crosses the boundary), serializes a layout of the mixed paragraph to the versioned wire form (`bwtext 1`, a text form with a version line), reads it back into a second layout, and compares every glyph id and position for equality. `null_handle=rejected` means a null or already-freed handle returns an error code and does not crash.
PRINTS: the one abi line.
```

Reason: product intent (Lazlo, 2026-11-20) asks for a language-neutral core API and a stable, versioned shared data form. This check proves the two things that can be proved before a second language exists. It does not prove that Python or another language can call it; that needs a runner in that language, which is a later node.
