# Node 1.3 2D vector renderer: infrastructure plan and done checks

**Status: draft: rewrite when the node starts.** Written 2026-11-20 from Broadsword `fefe8b1` and `CAPABILITY_ROADMAP.md` Part 5, before any code. Nothing in this file has been run: the program names, flags and test names in section 1 are the ones the briefs in section 7 create, and they do not exist until those briefs merge. Every number is a starting value unless it has a source.

Node (CAPABILITY_ROADMAP.md, Part 5): *2D vector renderer.* Build: GPU paths, fills, strokes, gradients, clipping. Needs: 1.2. Done when: a chosen subset of the SVG conformance suite renders within pixel tolerance (golden-image tests via 0.9). Broadsword stage: 4. ROADMAP.md status today: not started.

Product intent this plan respects (Lazlo, 2026-11-20): one unified tool where picking a mode (modeling, render, engine) switches the active crate group, every mode works on one shared core data model, and the core API stays language-neutral (C ABI or FFI-friendly, serializable data). So this node is a **rendering service that several modes call** (sketches, drawings, motion graphics, the editor shell), not a mode. Its input is plain, versioned data (a display list, section 2); it owns no scene, mesh or material type of the shared core; and its callable surface is a C-ABI function plus a text format, so a non-Rust upper layer can use it. Any change to the display-list format is a cross-shard change, so it is versioned from the first commit (check c7).

**One honest split.** The roadmap says "GPU paths". The GPU part needs node 1.2's `gpu` crate as a library, which fires ADR 0001 trigger 1 and is blocked until Lazlo decides ADR 0002 (section 2). Almost everything else (curve flattening, fill rules, strokes, gradients, clipping, the SVG-subset parser, the golden harness) does not need a GPU, and a CPU reference renderer is the thing the GPU output must later match. So the plan has two parts: checks c1 to c14 are the CPU reference and are plannable and runnable now; check c15 is the GPU backend and is **blocked** on ADR 0002 and node 1.2. The Done-when is met only when c15 passes. Passing c1 to c14 alone delivers a CPU vector renderer, and the node must say so rather than claim the Done-when.

## 1. Done checks as commands

### How to run and read a check

- Run every command from the Broadsword root. `broadsword` means `build/bin/broadsword.exe`. Inside a task, add `--task <id>` after the project name.
- Never call cargo directly. Tests go through `broadsword test vector2d`; a program goes through `broadsword run vector2d -- cargo run --offline --release --example <name> -- <flags>`. Programs run with the project folder as the working folder.
- Every command writes to a file in `scratch/` (`> scratch/<file> 2>&1`); read the file. Never pipe a broadsword command into another program.
- `broadsword test` has no name filter: it runs the whole suite and prints one `test <name> ... ok` line per test, then `test: ok - N passed, 0 failed`. A check that needs one test looks for that test's own line, so a suite that ran zero tests, or lacks the named test, fails.
- `broadsword run` prints its own job lines, then the program's lines, then `run: ok (...)` or `run: FAILED (exit N)`. A rule naming a program line is judged with "contains".
- `python -I scripts/node_check.py 1.3 --list` lists these blocks and `--run <id>` runs one. It judges only three rule forms: `last line == X`, `contains X` and `exit != 0`; every other `PASS:` text (including every `(human)` rule) is printed as "judge by hand". A command that exits non-zero is always a FAIL unless its rule is `exit != 0`, so a negative control (c13) is written as `PASS: exit != 0` and its expected output line is read by hand from the saved file; that form alone would also pass if the example failed to build, so c13 only means something once c12 has passed with the same example. `node_check.py` does not skip `(human)` or (blocked) blocks, it would run their commands, so never use `--run --all` on this node: run one id at a time and leave c14 to Lazlo and c15 until it is unblocked.
- A rule starting `(human)` needs Lazlo and is never run by an agent or counted as passed until he says so. A check marked (quiet board) is timing: run it only while `broadsword status` shows no other job, and rerun it, never average over a busy board. A check marked (blocked) cannot run until its named prerequisites exist; it is FAIL until then, never skipped.
- Anything not PASS is FAIL, including a check that cannot be run because a flag, file, example or test is missing.

### CPU reference renderer

**c1 The crate has no dependencies and no outside link.** ADR 0001 forbids a Cargo dependency (path or git) on another repo; any crate beyond std is ADR 0003's (ra-adr-deps) decision.
```check c1
build/bin/broadsword.exe test vector2d > scratch/n13-c1.txt 2>&1
PASS: contains test cargo_toml_has_no_dependencies ... ok
```
The test requires `[dependencies]`, `[dev-dependencies]` and `[build-dependencies]` to be empty or absent, and that no file under `src/` names another repo or links another crate (the strings `projects/`, `extern crate` and `broadsword`). The crate's own modules, including `src/render.rs` and paths such as `crate::render::render`, are allowed; the dependency tables being empty already keeps the external `render` and `gpu` crates out. FAIL: line missing or FAILED.

**c2 Curves flatten within a stated error.** Quadratic and cubic Beziers and arcs become line segments whose distance from the true curve is at most the requested tolerance.
```check c2
build/bin/broadsword.exe test vector2d > scratch/n13-c2.txt 2>&1
PASS: contains test flatten_error_within_tolerance ... ok
```
The test samples each curve densely (1000 points per segment) and checks every sampled point is within the tolerance of the polyline, for tolerances 0.25, 0.05 and 0.01 pixel. A second test, `flatten_rejects_nan_and_huge`, must also appear in the run: NaN, infinity and coordinates beyond 1e9 are a named error, not a panic or an endless loop. Threshold reason: 0.25 pixel keeps flattening error below the 2-of-255 pixel tolerance of c12 for normal edges; this is a reason, not a measured result, and V10 confirms it.

**c3 Fills have exact coverage and both fill rules.** Anti-aliasing is exact area coverage per pixel.
```check c3
build/bin/broadsword.exe test vector2d > scratch/n13-c3.txt 2>&1
PASS: contains test fill_known_coverage_and_rules ... ok
```
Cases worked by hand: an axis-aligned rectangle covering exactly half of a pixel gives coverage 0.5 (to 1/255); a unit square on pixel centres gives 1.0; a five-point star gives a filled centre under nonzero and a hole under even-odd; a path crossing itself, an empty path and a zero-area path give no panic.

**c4 Strokes have the right area, joins and caps.**
```check c4
build/bin/broadsword.exe test vector2d > scratch/n13-c4.txt 2>&1
PASS: contains test stroke_area_joins_caps ... ok
```
A straight stroke of width w and length L has area w*L (butt caps), w*L + w*w/2 (square caps) and w*L + pi*w*w/4 (round caps), each within 0.5 percent after rasterising at 8x supersampling; a right-angle corner has the area of the miter, bevel and round join computed by formula; the miter limit turns a sharp miter into a bevel at the limit; a width of 0, a negative width and NaN are named errors. Dashes are not in the subset (section 8).

**c5 Gradients match reference values.**
```check c5
build/bin/broadsword.exe test vector2d > scratch/n13-c5.txt 2>&1
PASS: contains test gradient_known_values ... ok
```
Linear and radial gradients with 2 and 3 stops, with pad, reflect and repeat spread, sampled at pixel centres and compared with values worked by hand from the SVG 1.1 formula (section 6); stops out of order, a stop offset outside 0..1 and a zero-length gradient vector are handled as the SVG text says or are a named error.

**c6 Clipping masks pixels.**
```check c6
build/bin/broadsword.exe test vector2d > scratch/n13-c6.txt 2>&1
PASS: contains test clip_masks_known_pixels ... ok
```
A clip path multiplies coverage: a pixel fully outside is untouched, fully inside is unchanged, and an edge pixel is scaled by the clip coverage; nested clips multiply; an empty clip draws nothing.

**c7 The display list is a versioned text file and round-trips byte for byte.**
```check c7
build/bin/broadsword.exe test vector2d > scratch/n13-c7.txt 2>&1
PASS: contains test scene_round_trip_byte_identical ... ok
```
The test reads the golden file `tests/fixtures/scene_v1.txt`, parses it and writes it back; the bytes must equal the golden file. `scene_rejects_unknown_version` (a file claiming `schema=2`) and `scene_rejects_bad_lines` (empty file, wrong field count, NaN, a CR inside a field, a Windows `\` path in a name) must also appear in the run.

**c8 The SVG subset parser accepts the subset and refuses the rest by name.**
```check c8
build/bin/broadsword.exe test vector2d > scratch/n13-c8.txt 2>&1
PASS: contains test svg_subset_parses_and_rejects_unsupported ... ok
```
Subset (to be written in `docs/SVG_SUBSET.md` by V8): `svg`, `g`, `path`, `rect`, `circle`, `ellipse`, `line`, `polyline`, `polygon`, `defs`, `linearGradient`, `radialGradient`, `clipPath`, and the attributes `transform`, `fill`, `stroke`, `stroke-width`, `stroke-linecap`, `stroke-linejoin`, `stroke-miterlimit`, `fill-rule`, `opacity`, `fill-opacity`, `stroke-opacity`, `clip-path`. Anything else (text, filters, masks, patterns, images, `use`, CSS `style` blocks) is a named `Unsupported(<name>)` error, never silently ignored: an ignored element would make a case pass for the wrong reason.

**c9 The PNG decoder reads the reference images exactly.**
```check c9
build/bin/broadsword.exe test vector2d > scratch/n13-c9.txt 2>&1
PASS: contains test png_decode_known_files ... ok
```
The golden images of an SVG suite are PNG files. The decoder (std only, inflate included) reads 8-bit RGB and RGBA, all five filter types, interlace off; fixtures are hand-assembled tiny files (stored deflate blocks) plus real suite files (V10). Interlaced, 16-bit, palette and truncated files are named errors (`png_rejects_unsupported_and_truncated` must also appear).

**c10 A scene renders to the hand-made expected image.** The compositor ties flatten, fill, stroke, paint and clip together.
```check c10
build/bin/broadsword.exe test vector2d > scratch/n13-c10.txt 2>&1
PASS: contains test render_scene_matches_hand_image ... ok
```
Three small scenes (64 x 64) with expected pixels worked by hand in `tests/fixtures/render_*.txt`: a filled rectangle with a stroked outline; a gradient-filled circle clipped by a rectangle; and 50 percent opacity over a background (source-over blend; the premultiplied maths is written in the doc comments of `src/render.rs`).

**c11 The C ABI renders the same bytes as the Rust API.** This is the language-neutral surface of the product intent.
```check c11
build/bin/broadsword.exe test vector2d > scratch/n13-c11.txt 2>&1
PASS: contains test ffi_render_matches_rust_api ... ok
```
`v2d_render(scene_text_ptr, scene_text_len, width, height, out_rgba_ptr, out_len)` is an `extern "C"` function in `src/ffi.rs`, documented in `include/vector2d.h`. The test calls it through the raw pointers and compares every byte with the Rust call; a null pointer, a too-small output buffer and an invalid scene each return a distinct non-zero error code (never a panic across the boundary). Dropping a C compiler into the test is not planned; the header is checked for matching the function by a test that reads both files (`ffi_header_matches_exports`).

**c12 The chosen SVG subset renders within pixel tolerance (CPU).** The conformance run: every case in `tests/suite/MANIFEST.txt` is rendered and compared with its reference PNG.
```check c12
build/bin/broadsword.exe run vector2d -- cargo run --offline --release --example svgcheck -- --suite tests/suite --backend cpu --max-diff 2 --max-bad-frac 0.001 --max-image-pixels 16777216 > scratch/n13-c12.txt 2>&1
PASS: contains conformance: ok backend=cpu cases=40 passed=40
```
The program prints one `case <name> bad=<n> max_diff=<d> result=PASS|FAIL` line per case and the final line above, and exits 1 on any failing case, any case in the manifest that has no reference file, and any case it skips (there is no skip). A pixel is bad when any channel differs by more than `--max-diff` (of 255); a case passes when its bad pixels are at most `--max-bad-frac` of the image. **The 40 cases, 2 and 0.001 are starting values, not sourced numbers:** 2 and 0.001 are the values node 1.2 plan starts with for its own render comparison, and a different renderer's anti-aliasing will differ from the reference on edge pixels more than that. V10 measures the real spread on the chosen cases and may write a per-case allowance in `MANIFEST.txt` with a reason for each, shown in the output; it may never lower the count of cases silently. The Done-when's "pixel tolerance" is whatever this check finally uses, so any loosening needs Lazlo.

**c13 The conformance check can fail.**
```check c13
build/bin/broadsword.exe run vector2d -- cargo run --offline --release --example svgcheck -- --suite tests/suite --backend cpu --max-diff 2 --max-bad-frac 0.001 --max-image-pixels 16777216 --inject-fault > scratch/n13-c13.txt 2>&1
PASS: exit != 0
```
Expected: the run exits non-zero (`run: FAILED (exit 1)`) and the saved file contains `conformance: FAIL` (read by hand; `node_check.py` judges only the exit code). `--inject-fault` shifts the rendered image of one case by 3 pixels before comparing (the flag is the only code that does so). If it prints `conformance: ok`, the comparison cannot see a wrong render and c12 proves nothing.

**c14 A person looks at the renders (human).** The program writes a contact sheet of every case: reference on the left, render on the right, as PPM files.
```check c14
build/bin/broadsword.exe run vector2d -- cargo run --offline --release --example svgcheck -- --suite tests/suite --backend cpu --max-diff 2 --max-bad-frac 0.001 --max-image-pixels 16777216 --sheet out > scratch/n13-c14.txt 2>&1
PASS: (human) Lazlo opens the sheets under projects/vector2d/out/ and answers in chat that each render shows the same shapes, colours and edges as its reference. The answer is recorded in evidence/.
```
(human.) Reason: a tolerance can pass two images that are both wrong the same way; a person closes that. The `out/` folder is ignored by Git.

## 2. Home

**A new repo `projects/vector2d`, crate `vector2d` (library, Rust 2021, std only), created by brief V1.** `projects/vector2d` is its own Git repo, ignored by the Broadsword repo (`broadsword.toml`, `projects_dir`), registered as a Broadsword project by a `Cargo.toml` with its own empty `[workspace]` table, as render does. Creating the repo is a step for Lazlo to approve.

Under ADR 0001 (option a, accepted):

- **No Cargo dependency (path or git) on another repo.** `[dependencies]` is empty (c1, c17). The crate does not depend on `projects/render`, `projects/crash-sim`, `projects/gpu` or `projects/foundation`, and the plan never links into `projects/foundation`. Render has its own 2D drawing code; none is imported and render is not edited.
- **The contract with other repos is data.** The display list (`docs/FORMAT.md`, V6) is a versioned text file that any repo or language can write: a list of paths with fill, stroke, gradient and clip records. A mode builds a display list from its own core data and hands it to `v2d_render` (c11). The renderer never sees a core scene type, which fits "modes are switchable crate groups over a shared core": a sketch mode, a drawing mode and a motion-graphics mode all call the same service with plain data.
- **The GPU backend fires ADR 0001 trigger 1.** It must run node 1.2's `gpu` crate as a library from a second project. Trigger 1 means ADR 0002 (one workload repo with a Cargo workspace, option d2, Lazlo's decision) before any dependency is written; this plan does not plan that dependency, and c15 is blocked on it. The alternative inside option a is to copy a small wgpu setup into this repo (the per-repo copy option a accepts), which would need its own approval for the crates (ADR 0003) and duplicates node 1.2's work; the plan does not assume it.
- **Trigger 2** ("a third Rust project needs the same ...") fires if render later replaces its own 2D drawing with this crate. Not planned.
- ADR 0004 (ra-adr-repo-map) should list node 1.3 -> `vector2d` with triggers 1 and 2.

Layout (planned):

```
projects/vector2d/
  Cargo.toml  README.md  .gitignore
  include/vector2d.h                   C declaration of the ABI (V7)
  docs/FORMAT.md  docs/SVG_SUBSET.md   display list, blend maths; the SVG subset
  src/lib.rs  geom.rs  image.rs        points, matrices, images, masks (V1)
  src/path.rs  flatten.rs  raster.rs  stroke.rs  paint.rs  clip.rs
  src/scene.rs  render.rs  ffi.rs  svg.rs  png.rs
  tests/structure.rs flatten.rs raster.rs stroke.rs paint.rs clip.rs scene.rs
        render.rs ffi.rs svg.rs png.rs
  tests/fixtures/  tests/suite/        golden files; the chosen SVG subset (V10)
  examples/svgcheck.rs
```

Layers, so a mode never depends on how pixels are made: (1) data (`geom`, `path`, `scene`, `image`); (2) CPU reference algorithms (`flatten`, `raster`, `stroke`, `paint`, `clip`, `render`), pure functions with no I/O; (3) surfaces (`ffi`, `svg`, `png`, the example). A GPU backend later implements the same `render` signature over layer 1.

## 5. Test harness

| Check | Kind of test | What it compares against |
|---|---|---|
| c1, c16, c17 | structure test reading `Cargo.toml` and `src/`; whole suite; dependency inspection | An empty dependency list. |
| c2 | property test: dense sampling of each curve, with a named tolerance; edge-input tests | The true curve from the Bezier formula. |
| c3, c4 | reference values worked by hand and by formula (areas, half-pixel coverage); supersampling cross-check (render at 8x and downsample, compare with analytic coverage) | Closed-form areas and counted pixels. |
| c5, c6 | reference values from the SVG 1.1 formulas, worked by hand at chosen pixel centres | Hand-calculated numbers in the test with their working in comments. |
| c7 | golden file, byte-identical round trip | `tests/fixtures/scene_v1.txt`, written once by hand. |
| c8 | accept and refuse tests over small SVG strings in the test file | The subset list in `docs/SVG_SUBSET.md`. |
| c9 | decode fixtures: hand-assembled (stored blocks) and real files; truncation and unsupported cases | Pixel values known from how the fixtures were made. |
| c10 | hand-made expected images | `tests/fixtures/render_*.txt`, one value per pixel, worked by hand. |
| c11 | ABI parity test and header-matches-exports test | The Rust API's bytes. |
| c12, c13 | golden-image conformance with a tolerance, and its negative control | The reference PNGs of the chosen suite. |
| c14 | human check on contact sheets | Lazlo's eyes. |
| c15 | the same conformance run on the GPU | The same references and tolerance. |

Fixtures to make: `scene_v1.txt` (V6), `render_*.txt` (V7), `png_*.png` (V9, assembled by a throw-away test helper that is itself in `tests/png.rs`, so no binary tool is needed), `tests/suite/` (V10, from the chosen suite, after approval). The only binary fixtures are the PNGs. No download for c1 to c11.

Each brief that adds a named test also runs a mutation step in its done check: change one line (for example, make a nonzero fill rule behave as even-odd, divide a gradient offset by 2, drop the miter limit, or write one decimal fewer), show the named test failing, then restore it. A test that only fails because it does not compile does not count.

Display-list format (V6 writes it into `docs/FORMAT.md`; draft): first line `schema=1`, then `canvas,<width>,<height>,<r>,<g>,<b>,<a>`, then one record per line: `path,<id>,<fill-rule>,<commands>` (commands as `M x y L x y C ... Z` with fixed decimals), `fill,<id>,<paint>`, `stroke,<id>,<paint>,<width>,<cap>,<join>,<miter>`, `clip,<id>,<clip-id>`, `grad,<id>,<kind>,<spread>,<x1>,<y1>,<x2>,<y2>,<stops...>`, with a transform on each shape record. Numbers use fixed decimals so a round trip is byte identical. This is the shared, language-neutral input.

## 8. Risks and size

**Risks, with what to do:**

- **R1 Prerequisites.** The roadmap says 1.3 needs 1.2, and 1.2 is not started. The plan treats 1.2 as needed only for c15. Ask Lazlo before V1 which order he wants (section 3). Cost of asking: one message; cost of not asking: a stopped coder.
- **R2 ADR 0001 trigger 1 and the GPU.** c15 needs `gpu` as a library. Until ADR 0002 (Lazlo) is decided, the Done-when cannot be reached, only the CPU reference. The node must say so rather than claim "GPU paths" done. This is the first thing that will stall the node.
- **R3 Tolerances are guesses.** The 2, 0.001, 40 cases and 0.25-pixel flattening are starting values. Another renderer's anti-aliasing differs from a reference on every edge pixel; if the spread is larger than expected, the question for Lazlo is whether a looser bound still means "within pixel tolerance". V10 measures it; an agent never loosens it silently.
- **R4 The suite choice and licence.** Whether the files may be committed, and which subset, is unresolved (section 6). If copying is not allowed, V10 changes to fetch-on-demand into a shared area and the check commands change.
- **R5 Subset creep.** SVG is large. A case that needs an unsupported feature must be left out of the 40 and listed in `docs/SVG_SUBSET.md` with the reason; it may not be passed by ignoring the feature (c8 refuses unknown elements). A subset chosen to be easy would make the Done-when empty, so V10 records how many suite cases exist and how many were chosen.
- **R6 The reference may be wrong in the same way.** The reference images come from another renderer, and our CPU renderer and GPU renderer could share a mistake; c14 (human) and the hand-worked values in c3 to c6 narrow this. Floating point order and fused multiply-add differ between CPU and GPU; this is why c15 uses the same pixel tolerance and not equality.
- **R7 Premultiplied alpha and colour spaces.** Blending in the wrong space (sRGB against linear) is a common silent difference from a reference. V1 must decide and document which, V7 must test it (c10 includes 50 percent opacity), and V10's measurement shows if the choice differs from the suite's.
- **R8 Stroking is the hard part.** Joins, miter limits and curve offsets have many edge cases; V4 is the likeliest to fail its first review. Plan for a fix round.
- **R9 `unsafe` at the ABI.** `ffi.rs` takes raw pointers from a caller we do not control. A wrong length or a null pointer must return an error code, never read or write out of bounds (c11 tests this); a reviewer should read the `unsafe` blocks, not only the tests.
- **R10 Display-list changes.** The format is read by every mode and, in time, by other languages. Any change is a cross-shard change; the `schema=` line exists for that reason and is versioned from V6.
- **R11 The PNG size limit.** The limit is an argument of `decode_png` and a required `svgcheck` flag (`--max-image-pixels`), so no brief edits Broadsword's `broadsword.toml` and the crate stays std only (no TOML parser, no read of another repo's file). The starting value 16777216 (4096 x 4096) in c12 to c15 is a guess, not a sourced number; the value used by the checks is recorded in `tests/suite/MANIFEST.txt` with its reason.

**Size:** 10 briefs (V1 to V10), roughly 250 lines each, about 2,500 changed lines of code, tests and documents, plus the suite data, in a new repo. Allow about 3 fix-round tasks, since the playbook expects the first review of risky work to fail (V4, V7 and V9 are the likely ones). So about 10 merged tasks and 3 fix rounds reach the CPU reference (c1 to c14), plus 1 human check (c14). The Done-when itself (c15) adds the GPU backend: 6 to 10 more briefs after node 1.2 and ADR 0002, so about 16 to 20 briefs in all. On the harness's measure (about 20 merged tasks per delivered stage) that is roughly one stage's worth of work, and a delivered "2D vector renderer" of the roadmap's meaning is not reached until the GPU part lands.
